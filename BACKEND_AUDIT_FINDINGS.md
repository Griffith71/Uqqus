# Backend audit findings

Audited 2026-09-18: a full read-through of `ruqqus/routes/`, `ruqqus/classes/`, and `ruqqus/helpers/` (~22,500 lines) looking for logical errors and inconsistencies, split across 5 parallel subsystem passes (content core, guilds/boards + moderation, users/auth/identity, admin/payments/discovery, helpers). Templates and JS were not covered by this pass.

This is a findings list for later fix work — nothing here has been changed. Check items off as they're fixed. Each item cites file:line as of this audit date; line numbers may drift as the codebase changes.

**Update 2026-10-08:** a second pass was added at the bottom ("Audit 2026-10-08"). It covers the October features (Circles, Stories, polls, muting, co-authors, deletion log, guild limits), consistency of visibility rules across the whole site, templates and JS (previously not reviewed), and contradictions between docs, schema, config and code. Its findings come from code reading only (see the status tags there); the live-site crawl and the re-check of the items above are listed as pending work at the end.

**Update 2026-10-09:** the Critical and High items of both passes were re-checked against the code and the running Docker site, and fixed; ticked items are done. See "Verification and fixes 2026-10-09" at the bottom for how, what changed, the owner's decisions, new findings and what is still open.

## Critical — security / permission bypass

- [x] **`ruqqus/helpers/security.py` `safe_compare()`** (used by `login.py:128`, `settings.py:270` to validate MFA recovery codes) — not actually constant-time: does plain `x==y` then pads total latency with a random sleep, which masks but doesn't eliminate the timing signal, and can call `gevent.sleep()` with a negative duration if the padding budget is already exceeded. The file already has the correct primitive (`hmac.compare_digest` via `validate_hash`, line 18-20) — `safe_compare` should just use that.
- [x] **`ruqqus/helpers/wrappers.py:319-320` `is_guildmaster` decorator** — checks `v.is_banned and not v.unban_utc`, which only blocks *permanent* bans. A moderator with an active **temporary** ban passes through (since `unban_utc` is truthy), and `is_guildmaster` is the only ban gate on guildmaster routes (they sit under `@auth_required`, never `@is_not_banned`). A suspended mod keeps full moderation powers for the duration of their ban.
- [x] **`ruqqus/routes/comments.py:82-119` + `264-266`** — for API requests, a mismatched `pid`/`cid` pair skips the canonical-redirect and its board-ban/NSFW gating entirely, since those checks run against `get_post(pid)` (an attacker-supplied, unrelated post) while the response still serializes the *real* comment's data. A crafted `pid` pointing at a public post can pull content from a comment that actually belongs to a banned/NSFW-gated post.
- [x] **`ruqqus/classes/board_relationships.py:24`** — the `perm_chat` column is commented out, but `Board.has_mod(v, "chat")` (`ruqqus/classes/boards.py:275`) does a raw `__dict__["perm_chat"]` lookup with no default. Any partial-permission guildmaster (not `perm_full`) running a chat mod command (`/ban`, `/kick`, `/gm`) hits an unhandled `KeyError`. Routes gated via the safer `is_guildmaster("chat")` decorator (which uses `.get()`) just silently always deny instead — two different broken behaviors from the same missing column.
- [x] **`ruqqus/routes/admin_api.py:243,267` vs `:86,124`** — `api_ban_comment`/`api_unban_comment` require only `admin_level_required(1)`, while the equivalent `ban_post`/`unban_post` require level 3. Any level-1 admin can unilaterally ban/unban any comment site-wide with content-moderator-tier access, with no ownership restriction.
- [x] **`ruqqus/routes/flagging.py`** — `api_flag_post` (line 14) and `api_flag_comment` (line 55) have no `@validate_formkey`, unlike essentially every other content-mutating POST route in the app (127 other call sites do have it). Reporting content is CSRF-exposed.

- [x] **`ruqqus/classes/boards.py:234` `Board.idlist`** — `posts.filter_by(is_pinned=False)` result is discarded, not reassigned. Pinned-post exclusion from the ranked listing is a complete no-op; pinned posts appear twice on guild pages.
- [x] **`systemprofile` (the reserved profile-post guild) leaks into public listings** — `ruqqus/routes/front.py:561-563`'s `/browse` exclusion checks a hardcoded `subcat_id != 108`, but the seed script (`scripts/wizard.py`) never sets `subcat_id` (stays at default 0), so it isn't actually excluded — contradicts the `PROFILE_BOARD_NAME`/`get_profile_board_id()` check used consistently elsewhere.
- [x] **`ruqqus/routes/search.py:230-231` guild search is broken for every logged-in user** — filters on `Submission.user_id`/`is_active`, neither of which exists on `Submission` (copy-paste from what should be a `Subscription` query). Any authenticated `+guild` search 500s; anonymous search works but doesn't exclude `systemprofile` either.
- [x] **`ruqqus/routes/front.py` `/all/comments`** lets `admin_level >= 3` bypass the banned/deleted filter for comments, while `/all` (posts, via `frontlist()`) has no such bypass at any level. Separately, **`random_comment()`** unconditionally filters NSFW/offensive/bot content regardless of viewer settings, while **`random_post()`** correctly respects the viewer's preferences.
- [x] **`ruqqus/routes/search.py:75-81`** — computes a properly `%`/`_`-escaped `url` variable for the `url:` search filter, then uses the unescaped `criteria['url']` in the actual `ilike()` call. Wildcard characters in a URL search term get interpreted as SQL wildcards instead of literal text.

# Audit 2026-10-08

Three read-only passes over the legacy app: (1) visibility and permission rules applied inconsistently across listings, single-object routes, JSON/RSS, notifications; (2) contradictions between `CLAUDE.md`, code, `schema.sql`/migrations, config, docs and tests; (3) templates, JS and the wiring from the front end to routes (never reviewed before). Nothing was changed and the running site was **not** exercised: every item comes from reading code.

Status tags: **[confirmed]** = the code was re-read a second time by the person compiling this log; **[traced]** = traced through the code by the audit pass with file:line, not yet independently re-read; **[suspected]** = plausible, intent or reachability unclear. ## Critical — privacy leak, crash on a normal action, data loss

- [x] **Anonymous author's real username is printed in the comment-permission notice** [confirmed] — `ruqqus/helpers/comment_permission.py:60` (`"Only accounts @{post.author.username} follows can comment on this post."`), shown by `routes/comments.py:377-380` and `templates/submission.html:929`, and returned in the comment POST's 403. Nothing blocks `comment_permission = 1` on an anonymous profile post (`routes/posts.py:822-824,1311`; edit path `:310,409`). Every signed-in viewer the author doesn't follow sees the name; whether you can comment also tells you whether the author follows you.
- [x] **`/random/post` and `/random/comment` redirect to Circle and private-guild items** [confirmed for `random_post`] — `ruqqus/routes/front.py:1162-1232` (`@auth_desired`, so visitors too). No `post_public`, `audience`, `Board.is_private`, block or mute filter, and `random_comment` doesn't exclude deleted comments. The `Location` header carries the post slug and guild name even though the page behind it is gated. Also `random.randint(0, total - 1)` raises `ValueError` (500) when the filtered set is empty (`:1189,1210,1229,1245`), and `random_user` has no `is_deleted`/`filter_users` (`:1237-1248`).
- [x] **Private-guild content is readable through endpoints that skip the page's privacy gate** [traced] — the gate is only in `Submission.rendered_page` (`classes/submission.py:320-324`). Not gated: `routes/posts.py:82-155` (`/api/v1/post/<pid>`, `/api/v2/submissions/<pid>[/comments]`), `routes/comments.py:62-263` (`/api/v1/comment/<cid>`, `/api/v2/comments/<cid>`, `/api/vue/comment/<cid>`), `/embed/comment/<cid>` (`comments.py:1021-1042`) and `/embed/post/<pid>` (`posts.py:1783-1793`). The `api()` wrapper only forces login for `/api/v1` and `/api/v2`, so `/api/vue/comment/<id>` and the embeds work for visitors; ids can be iterated. Circle items are protected (by `circle_guard`); ordinary private guilds are not.
- [x] **Per-item history pages ignore removal, deletion and privacy** [confirmed] — `routes/posts.py:536-564` (`/post/<pid>/history`) and `routes/comments.py:798-820` (`/comment/<cid>/history`), both `@auth_desired`. They print `ContentEditHistory.previous_*` with no `post_hidden`/`comment_hidden`, `is_banned`, `deleted_utc`, `purged_utc`, `hidden_by_guild` or `can_view` check: pre-edit text of admin-removed posts, content a guild's moderators hid, author-deleted text, private-guild text. Undoes what the deletion log enforces (`routes/deletion_log.py:50-54,77-82`). `purge_post`/`purge_comment` (`admin_api.py:174,318`) scrub only the live row.
- [x] **Delete-post modal stacks click listeners, so confirming deletes more than one post** [confirmed] — `assets/js/all_js.js:949-967`: every `delete_postModal(id)` adds a new `addEventListener("click", delete_post)` (a fresh closure over `id`) to the same shared `#deletePostButton` / `-mobile` buttons (`delete_post_modal.html:31,41`). Open Delete on post A, cancel, open it on post B, confirm: `POST /delete_post/A` and `/delete_post/B` both fire. `delete_commentModal` (`:973`) uses `.onclick =` and doesn't have this.

## High — wrong visibility, broken features users will hit
