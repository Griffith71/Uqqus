# Uqqus

Two independent apps in one repo. Do not mix imports or config between them.

|            | Path                                   | Stack                                                                                                                                                                          |
| ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| New app    | `web/`                                 | Next.js 16 App Router, React 19, TypeScript (strict), Tailwind 4 + shadcn/ui, Prisma 6 + Postgres (Supabase), Auth.js v5, Zod, Vitest, Playwright. Details in `web/CLAUDE.md`. |
| Legacy app | `ruqqus/` (+ `scripts/`, `schema.sql`) | Flask 3, SQLAlchemy 2, Jinja templates, Postgres, Redis, Matrix/Synapse chat (`synapse/`). Python 3.11 in Docker.                                                              |

Tooling: Node 22 (`.nvmrc`), Python dev tools in `.venv` (`pip install -r requirements-dev.txt`).
Env vars: copy `.env.example` (legacy) and `web/.env.example` (web) to `.env`; never commit `.env`.

## Commands

| Task                                   | Command                                                                |
| -------------------------------------- | ---------------------------------------------------------------------- |
| Everything (run before declaring done) | `bash scripts/check.sh`                                                |
| web: all checks                        | `cd web && npm run check` (typecheck, lint, format:check, test, build) |
| web: typecheck / lint / test / build   | `npm run typecheck` / `lint` / `test` / `build` (in `web/`)            |
| web: e2e smoke                         | `cd web && npm run test:e2e`                                           |
| web: fix formatting                    | `cd web && npm run format`                                             |
| legacy: lint / test                    | `.venv/Scripts/ruff check .` / `.venv/Scripts/python -m pytest -q`     |

Ruff on the legacy app is errors-only (`pyproject.toml`); there is no Python type checker.
The pre-commit hook (Husky) runs only staged-file checks: gitleaks, ruff, eslint, prettier, typecheck. CI runs the full suite.

## Terminology (applies to both apps, UI text and code names)

| Say                                                                                                                                 | Never say                                  |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **post**: always created first on the author's own profile. You cannot post to a guild, except inside a Circle guild (see below).    | "post to/in a guild", "submit to a guild"  |
| **comment**: anything that is a reply, whether on a post or on another comment.                                                     | reply, replies, replied                    |
| **forward** (forwarded, forwarding): sharing a post or comment with a guild. A forwarded comment becomes its own post in the guild. | promote, yank, crosspost, "share to guild" |
| **repost**: putting someone's post or comment on your own profile (a different feature from forwarding).                            |                                            |

Guilds only ever receive forwards, so guild settings and errors talk about _forwarding_ (e.g. "Restrict forwarding", "disallows bots from forwarding").
External contracts keep their old names on purpose: the URL `/notifications/replies`, the JSON field `replies`, DB columns such as `restricted_posting` and `promoted_by_id` (Python attributes use the new names), the `/mod/kick/...` URLs, and legacy mod-log kinds (`yank_post`, `kick_post`).
`tests/test_terminology.py` enforces this; extend its allowlist only for a real external contract.

## Post options (legacy app)

- **Who can comment?** (`submissions.comment_permission`: 0 everyone, 1 accounts the author follows, 2 Premium accounts, 3 No one) is set by the author on the post on their own profile. The rule lives in `ruqqus/helpers/comment_permission.py`: `api_comment` enforces it and `rendered_page` passes `comment_restriction` to the templates, which show a notice instead of the comment box. The author and admins are exempt from 1 and 2, **not from 3**: "No one" is literal (the notice is `CLOSED_NOTICE`, "Comments are turned off for this post.", it names nobody and is also shown to visitors through `closed_notice`, so a visitor is not invited to sign in to comment). Existing comments stay. A forwarded copy never reads it: copies follow their guild's rules (`Board.can_comment`), so a "No one" post forwarded by someone else can still be discussed in the guild copy. Do not copy the column onto a forward. **The author can change it after posting**: "Who can comment" in the post's "..." menu (card, phone sheet and post page; `partials/comment_permission_modal.html`, `assets/js/comment_permission.js`, `POST /api/post/<id>/comment_permission` in `routes/post_commenting.py`, not an edit: no history row, no `edited_utc`) or the Edit form's own "Who can comment?" field (`edit_post`). `tests/test_comment_permission.py`, `tests/test_comment_permission_route_assets.py`.
- **Content disclosure** (`paid_partnership`, `made_with_ai` on `submissions` and `comments`) is set by the author when writing or editing a post or comment, copied onto forwards (post and comment forwards), and shown as labels from the `disclosure_badges` / `disclosure_row` macros. Read the form fields with `post_fields.flag()` (an absent field keeps the stored value; "false" means off). `tests/test_content_disclosure.py` keeps schema, models, routes, templates and JS agreeing.
- **Anonymous posts and comments** (`is_anonymous` on `submissions` and `comments`): the real `author_id` stays on the row (bans, spam, reports and admin tools need it) but only the author and site admins (`admin_level >= 3`) are told who it is. **Never read `.author` / `.author_id` to show who wrote something.** Use `ruqqus/helpers/anonymity.py`: in templates `author_of(item, v)` (the author object, or a stand-in "Anonymous"), `anon_hidden(item, v)` (hide anything that would single the author out: the Submitter mark, block / exile markers, tip, block and exile buttons) and `op_badge(...)`; in JSON `anonymity.identity_hidden(self, anonymity.current_viewer())`; in queries that list ONE author's items (profile tabs, `author:` search, Following) `anonymity.hide_anonymous(Model, v)`. The flag is set at creation only (never editable), copied onto forwards, forced on when you comment on your own anonymous post, and an anonymous item cannot be tipped, heralded, distinguished or reposted by its author. Anonymous posts do not bell-notify the author's followers, the region filter does not match them through their author, and `public_post_count` / `public_comment_count` leave them out. `tests/test_anonymity.py` and `tests/test_anonymity_assets.py` enforce this; a new place that shows an author needs the same treatment.
- **Formatting extras** in post and comment markdown (`{c:red}text{/c}`, `{h:blue}text{/h}`, `==text==`, `::: center ... :::`, `[Label](url){.button}`) only accept fixed names, never CSS. `ruqqus/helpers/post_formatting.py` is the single list (colours, highlights, alignments, button class): `helpers/markdown.py` renders them, `helpers/sanitize.py` keeps no other CSS class on `span`/`mark`/`div`/`a` (never allow `style` or a free `class`), and `tests/test_post_formatting.py` checks that `main.scss` and `main_dark.scss` have a rule for every class. To add an option: add it to that list, then a rule in both stylesheets.
- **Post editor toolbar** (create and edit a post; comments keep the small toolbar): `assets/js/post_editor.js` builds it for every `<div class="post-toolbar" data-target="<textarea id>">`. The text stays plain markdown and every edit goes through `editorReplace()` in `all_js.js` (keeps browser undo/redo). Write/Preview posts to `/api/preview` (same renderer and sanitizer as a real post); Template snippets are `post_templates` rows behind `/api/post_templates` (20 per user, see `routes/post_editor.py`). The image, audio and video buttons are disabled placeholders: an uploader calls `PostEditor.register('image', fn)` to switch one on. `tests/test_post_editor_assets.py` keeps the script's colour names, its CSS classes and the two forms in step.
- **Drafts and scheduled posts** (Save draft / Schedule / Drafts on Create a post): a draft is a `post_drafts` row (never a `submissions` row, which would leak into feeds and counts) with its fields in `options` JSON. Rules are in `helpers/post_drafts.py`, endpoints in `routes/post_drafts.py`, the UI in `assets/js/post_drafts.js`. A scheduled draft is published by `scripts/publish_scheduled.py` (its own supervisord program, polling every 30s): it submits through the real `POST /api/vue/submit` in-process as the author, from the IP and region saved with the draft, so every posting rule, the posting throttle and bans apply as for the Post button. **Never copy `submit_post`'s logic into the scheduler.** A new option on the composer needs: the field in `clean_fields` / `publish_form`, the composer markup, and `post_drafts.js`'s `collect()`. Run the publisher by hand with `PYTHONPATH=. python scripts/publish_scheduled.py --once`; uploaded images are not kept in drafts.
- **Feed composer** (top of the home / all feed and of a guild page, desktop only): `templates/partials/inline_composer.html` + `assets/js/inline_composer.js`. It posts through the real `POST /api/vue/submit` (every rule, throttle and ban applies), so a new composer option needs the same three places as the drafts: the field in the partial, `post_options.html` if it is shared, and `tests/test_inline_composer_assets.py`. On a guild page the hidden `forward_guilds` field makes it post on your profile and forward to that guild; the card added to the feed comes from `GET /inpage/post_card/<id>?guild=` (your own posts only). **It carries what the full editor carries** (it drifted once: no toolbar, GIF, emoji, drafts or picture in the text): the audience pill and the poll button (`assets/js/composer_card.js`, the same ids as the full editor), the formatting toolbar and Write / Preview (`post_editor.js`, loaded by `default.html`), GIF and emoji (`commentForm('ic-body')`, the site's own modals), a picture in the text (`body_image`, only `can_upload_comment_image`), and Save draft / Schedule / Drafts (`post_drafts.js`, which reads either form **by field name**, so a new option needs its name in `collect()` once; the schedule panel and Drafts list are `partials/drafts_ui.html`, included by pages that set `composer_drafts`). **A Circle guild composer has no drafts controls**: a draft keeps no `circle_guild`, so a scheduled copy would publish as a public profile post. `tests/test_composers_offer_the_same_options.py` fails when one form has a field the other lacks.
- **Continuous feed** (`assets/js/infinite_scroll.js`): every feed still pages 25 posts with a `Prev`/`Next` control; the script hides that control **whenever it engages, with or without a next page** (it used to return early without a next page, which left a disabled Prev/Next under every feed of 25 posts or fewer and on the last page of every feed), follows the enabled `Next` link of the page, fetches that page and lifts its post cards out, so no route needs a fragment mode, and ends the feed with "You're all caught up". Keep each feed template's `ul.pagination` with a link labelled exactly `Next` and its post list in `.posts` (`tests/test_infinite_scroll_assets.py`). Newer posts come in at the top: a touch pull-down at the very top (the browser's own pull-to-reload is switched off by `html.feed-live`) and a "Show N new posts" pill, checked about every 2 minutes while the tab is visible (one feed render per open feed tab; `window.FEED_POLL_MS` overrides it in tests). Both fetch the first page of the current URL without `page` and put the cards whose `post-<id>` is not on the page above the first card; nothing refreshes on a page opened at `?page=N`. Comment lists, notifications and admin queues keep their Prev/Next. Behaviour of cards added after load is bound by `bindPostCards(root)` in `all_js.js`: a new card behaviour must be added there as well as at load.
- **Side panels** (desktop >= 992px): the navbar Notifications, Chat and Create post icons (`data-side-panel` in `default.html`) open `assets/js/side_panels.js`'s panel in place of the right sidebar and fold the left sidebar to its rail (with `classList`, never `toggle_sidebar_collapse()`, which also flips the saved preference). Each panel is a frame of the real page with `?embed=1`: `default.html` then adds `body.embedded` (no navbar or sidebars, `<base target="_top">`) and `assets/js/embedded.js` keeps tab bars and Prev/Next inside the frame. `/composer` is the Create post panel's page. `__main__.py` sends `X-Frame-Options: sameorigin` (not `deny`) only for `?embed=1` on `/notifications*`, `/chat` and `/composer`. Frames are kept (hidden) once opened so the chat keeps its Matrix connection. `header.html` (submit / settings pages) has its own navbar without the panel triggers. Chat shows the list OR the conversation below 768px (phones and the panel). `tests/test_side_panels_assets.py` keeps this in step.
- **Navbar alignment** (desktop >= 992px): the logo lines up with the left sidebar's content, the account section with the right sidebar's, and the search box is centred over the feed. `main.scss` / `main_dark.scss` hold the values for the normal 1326px block (sidebar 300 + feed 726 + sidebar 300, each side plus the 15px column gutter) and `assets/js/nav_align.js` replaces them with the real column edges through four CSS variables on `<html>` (`--nav-inset-left`, `--nav-inset-right`, `--nav-search-left`, `--nav-search-width`), so it also holds with the left sidebar folded to its rail or a side panel open. A new layout that changes a column's width needs no change as long as it uses `#sidebar-left`, the right `.sidebar` or `#side-panel`; changing the 300 / 726 / 300 widths means changing `BLOCK` in the script, the `1326px` and the folded `1091px` (65 + 726 + 300) in both stylesheets, and the row's stand-ins for the feed and right sidebar (`expects-right-sidebar`, see "Painting right the first time"). `header.html`'s navbar (Create post, settings) gets the default alignment from the CSS alone. **Chat and settings have no columns, so they are as wide as the navbar's content** (the block less the gutter on each side: 1326 - 30 = 1296px) and their edges are the logo's and the account area's: `#chat #main-content-col` (1296px, 15px side margins) and `#settings .container` (1326px, its own padding leaves 1296px), both at >= 992px, plus a 340px chat list at >= 1200px. Changing the block width means changing those two as well. `tests/test_nav_align_assets.py`.
- **Chat client** (`assets/chat_src/src`, built into `assets/js/chat_bundle.js` by the Dockerfile; locally `npm install && npm run build` there): 1:1 Matrix messages with quotes (Matrix `m.in_reply_to`; the UI says "quote", never the banned word), reactions, edit, delete, typing and "Seen". The other person is addressed by Matrix id (`otherMxidOf`), never from the room member list (it also holds the bot that created the room). Read receipts and mark-read go out once per newest message: our own receipt redraws the thread, so doing it on every draw is a request loop that trips the site's rate limit. In encrypted rooms reactions and edits reach the appservice webhook as `m.room.encrypted`; only their `m.relates_to` is readable, and `helpers/chat_events.is_new_message` uses it so they are not counted as unread messages. Not built (roadmap): attachments and voice notes (needs a decision on encrypted media vs CSAM scanning), group DMs (`chat_conversations` is pair-only), 1:1 and group calls (coturn / LiveKit), audio Spaces. `tests/test_chat_events.py`.
- **Co-authored posts** (`post_coauthors`: `post_id`, `user_id`, `invited_by_id`, `status` pending/accepted, one row per pair): the author of a post on their own profile invites up to 5 accounts (`MAX_COAUTHORS`) from the "Co-authors" field of the composer (`post_options.coauthors_field`; in the Create page, the feed composer and drafts) or from "Co-authors" in the post menu (`assets/js/coauthors.js`, sheet `partials/coauthors_modal.html`). The rules are in `helpers/coauthors.py` (`refusal`, pure): **never on an anonymous post** (`is_anonymous` is creation-only, so it can't be added later either), not yourself, not an account in a block either way (the message never says who blocked whom), not a deleted or banned account. A name that can't be invited stops the post with a 400 (`check_names`, before the `Submission` exists) instead of vanishing; `invite_names` runs once the post exists and sends the notification. The invitee answers at `/coauthor/<post>` (`routes/coauthors.py`: accept, decline, leave, remove; all POST with a form key; only the author invites or removes, only the invited account answers, a decision can't be repeated, and accepting drops an invitation that a block or anonymity has made impossible). Accepted co-authors share **one** post: the byline comes from `coauthor_line` (`partials/coauthors.html`, draws co-authors only and never reads `.author`; the author is still drawn through `author_of`), the post is listed on their profile (`User.userpagelisting`), in the Following feed of anyone following a co-author (`User.idlist`) and in `public_post_count`. Votes, comments and forwards stay on the one post and only the author edits, deletes and forwards it. Every id resolves through `primary_post_id`, so a forwarded copy shows the same names and invitations live on the original only. Still the original author only: region filter, `author:` search, curation account membership and bell notifications. Pending invitations are seen by the author only. `accepted_of()` is cached per worker for 30 s (`forget()` after a change, so other workers lag by up to that long). `routes/posts.py` must import the helper **after** `from ruqqus.classes import *`, which also brings in the module `ruqqus.classes.coauthors` and would otherwise replace it. `tests/test_coauthors.py`, `tests/test_coauthors_assets.py`.
- The option controls shared by the composer, the edit form and the comment forms live in `templates/partials/post_options.html`; the rules text in `templates/partials/posting_rules.html` (keep `help/rules.html` in step: `tests/test_posting_rules.py`).

## Word filter (legacy app)

Viewers browse at a level (`User.filter_level`: 0 Off, 1 Standard - the default and what logged-out visitors get, 2 Child). Content is never removed; it is hidden per viewer.

- Posts and comments get a stored rating when written (`word_severity`: 0 clean, 1 profanity, 2 extreme) from `ruqqus/helpers/wordfilter.py` (the matching engine, stdlib only) via `helpers/word_filter_store.py`. Standard hides 2; Child hides 1 and 2 plus anything `is_sensitive`, sensitive guilds and sensitive accounts (never an anonymous item for being one: see Sensitive accounts and All).
- **Every new listing or page must go through `ruqqus/helpers/visibility.py`**: `filter_posts` / `filter_comments` / `filter_boards` / `filter_users` on queries, `post_hidden` / `comment_hidden` / `board_hidden` / `user_hidden` for one object, `hidden_notice(v)` for a direct link. Do not read `hide_offensive` or `is_offensive`.
- Memoized id-lists must include `filter_level=viewer_level(v)` in their arguments (it is the cache key). Caching is off on localhost, so this cannot be noticed in dev.
- Anything that writes a title, body, bio, description, username or guild name must re-stamp it (`apply_post_severity`, `apply_comment_severity`, `apply_user_severity`, `apply_board_severity`).
- The word list lives in `word_filter_entries` and is edited at `/admin/word_filter` (plain words, never regex); an empty table means the built-in list in `helpers/wordfilter_seed.py`. After changing the list, re-scan (admin button or `PYTHONPATH=. python scripts/rescan_word_filter.py`).
- Schema changes are manual: `scripts/migrations/*.sql` for existing databases, mirrored in `schema.sql`.

## Linked media storage (legacy app)

Ruqqus keeps no copy of an uploaded picture, sound or video, and **storing media must cost the site nothing**: every file goes into the member's own account on another service, using that service's free allowance (the owner's rule; site-owned buckets and paid video hosts are ruled out). A member links an account once, in `/settings/media` or the first time they add a file; the browser sends the file straight to it and a post only holds a reference. Start with `ruqqus/helpers/media/rules.py` (the rules, no I/O).

- **Two shapes of provider** (`helpers/media/base.py` is the interface). _Served_ (Google Drive `gdrive.py`, OneDrive `onedrive.py`): plain storage that stays private in the member's account; Ruqqus fetches it and shows it at `/media/<id>/<token>.<ext>` (`routes/media.py`). _Hosting_ (YouTube `youtube.py`, Dailymotion `dailymotion.py`, listed in `rules.HOSTED`): the site plays the file itself and the post links to it. `dev.py` is a stand-in served provider for local testing, only with `MEDIA_DEV_PROVIDER=1` (never on a live site).
- **Which service per kind of file**: pictures and audio go to Google Drive (15 GB free) or OneDrive (5 GB free); video to YouTube or Dailymotion (Dailymotion's daily limits are the member's own: 15 videos a day; YouTube's API allows the whole site 100 uploads a day until its audit). Rejected on purpose: Imgur (blocked in the UK since September 2025, embeds included), SoundCloud (registering an app needs a paid Artist Pro account), Vimeo's free plan (1 GB), Dropbox for now (2 GB; it fits the served shape if members ask). `rules.SERVICE_ORDER` / `SERVICE_LABELS` / `PROVIDER_LABELS` / `SERVICE_HINTS` are what the composer and settings say.
- **Connecting from the composer** (`assets/js/media_upload.js`): the file is picked first (the click is what lets the browser open its file dialog), and when no linked account takes that kind yet the status line offers the site's services; the chosen one opens in a **popup** (`connect`, `?popup=1&n=<nonce>`, remembered in the session by `_remember_popup`), and the callback ends with `media_connected.html` (`_finish`), which tells the opener on three channels (BroadcastChannel, a localStorage event, `window.opener.postMessage` to this origin) because a sign-in page in between can cut the popup off (Cross-Origin-Opener-Policy); coming back to the tab also re-asks `/api/media/status`. Only a message from this origin carrying the composer's own `n` counts. The upload then carries on with the same file. A full account (507), a lost one (`need: storage`) or a Google account without YouTube access (`need: video`) is fixed in place and the upload tried again once.
- **Where each kind goes**: the member's choice is `default_for` in the account's `settings` (`_preferred`, `rules.in_order(by_kind, preferred)`), set from the "Change where … go" link under an upload (`POST /api/media/default`) or the settings page (`/settings/media/default`). An upload may name the account (`account` form field) and answers with `to` (where it went).
- **How bytes travel** is the provider's answer to `begin_upload`: one PUT (Drive, YouTube, dev); `chunk` (OneDrive's upload session: PUTs with a `Content-Range` each, 10 MiB, a multiple of 320 KiB); `form_field` + `answer` (Dailymotion: a form POST whose answer, the uploaded file's address, the browser hands back as `answer`; only providers with `wants_answer` get it, and `dailymotion.upload_address_ok` accepts only https addresses on Dailymotion's own upload servers).
- **Never serve Drive files by a Google link.** Google has no supported way to show a Drive file in an `<img>`, a shared file shows its owner's Google name (which would break pseudonymity and anonymous posts), the Drive API terms forbid using Drive as a CDN, and the Cloudflare CSAM scan only covers this site's own addresses.
- **Who sees a file** (`rules.access`): part of a live post or comment: public, `Cache-Control: public, max-age=31536000, immutable`, no session cookie (`g.skip_session_cookie`); not attached yet: its owner only, `no-store`; otherwise refused, so the site is not a free file host. Every place that saves a post's link or text, or a comment's text, calls `media.attach.sync(...)`, commits, then `media.safety.scan_later(...)`. Removing a post or comment calls `media.cdn.purge(...)`.
- **A served file is typed by its first bytes** (`rules.sniff`), sent with our own `Content-Type`, `nosniff` and a sandboxing CSP, and refused when the provider's checksum no longer matches the one recorded at upload (the owner can change the file in their storage). No SVG or HTML type, ever.
- **Uploading** (`assets/js/media_upload.js`): `POST /api/media/uploads` answers where the browser sends the bytes (a provider upload session the server opened; no credential ever reaches a browser), then `POST /api/media/uploads/<id>/complete` checks the file. Pictures are re-drawn in the browser first, which drops EXIF (location); never fall back to the original. A post's own picture travels as the `media` form field (an asset id), text pictures as `![](/media/...)`, sounds as `[audio](/media/...)`, which `helpers/sanitize.py` turns into an `<audio>` player (only for exactly this site's own sound address). No thumbnail is generated for linked media.
- **Microsoft and Dailymotion** go through `helpers/media/oauth.py` (`Service`: state, code exchange, encrypted refresh token, access tokens in Redis, revoke); `microsoft_oauth.py` (scope `Files.ReadWrite.AppFolder`, only the site's own app folder; `MICROSOFT_TENANT` defaults to `consumers`) and `dailymotion_oauth.py` (scope `manage_videos`) are its settings, with `MICROSOFT_CLIENT_ID` / `_SECRET` and `DAILYMOTION_API_KEY` / `_SECRET`; redirects `<site>/settings/media/<name>/callback`. Microsoft hands out a new refresh token with each use: `Service.access_token` writes it onto the account and sets `account._rotated`, and the routes commit it (`_keep_rotated`). A service whose keys are not set is not offered anywhere (`registry.service_configured`). `google_oauth.py` predates the shared module and keeps its own copy (its tests replace its functions).
- **Google** (`google_oauth.py`): needs `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`; redirect `<site>/settings/media/google/callback`. `drive.file` is asked for first (not a sensitive scope: only files this site created). `youtube.upload` is asked for only when a member first adds a video; it is a sensitive scope (Google must verify the app) and the API project must pass YouTube's audit, or YouTube forces every upload private, which is reported as `restricted`. The refresh token is stored encrypted (`secret_box`). `AccountLost` (access taken away at Google) marks the account `error` without writing its files off; `ProviderDown` is temporary and never cached.
- A video from a member's own channel (YouTube or Dailymotion: `rules.video_ref`) shows the channel name, so it is refused on an anonymous post (`media.attach.own_video`) and on a Circle post (`circles.post_refusal`). Drive and OneDrive media show no identity and are allowed.
- **To add a provider**: a module with a `Provider` subclass, an entry in `registry.PROVIDERS` / `ACCOUNT_OF`, its kinds in `rules.PROVIDERS` (and `rules.SERVED` if Ruqqus serves it). Posts, comments and the upload script do not change.
- Not on linked storage: avatars, banners and guild images (still the site's S3 bucket, `helpers/aws.py`), and anything uploaded before. When the site offers no linked storage, the old server-side image upload is what the composers use.
- The Google, YouTube, OneDrive and Dailymotion code is tested with each service's side faked (`tests/test_media_google.py`, `test_media_youtube.py`, `test_media_onedrive.py`, `test_media_dailymotion.py`, `test_media_oauth.py`); **none of it has been run against the real services**. The first things to check with real credentials: the browser's PUT to Google's and OneDrive's upload sessions is allowed across origins, the browser may read Dailymotion's upload answer (CORS), and Dailymotion accepts the `people` channel.
- Tests: `tests/test_media_*.py`.

## Languages (legacy app)

`ruqqus/helpers/languages.py` holds the one list of languages (`LANGUAGE_NAMES`: filters, curations, trending) and detects a post's language when it is written (`detect_language`, `py3langid`). Only languages people speak in daily life are listed: Ancient Greek, Ancient Hebrew, Latin and Volapük were taken off on purpose (`REMOVED_LANGUAGES`; Sanskrit and Esperanto stay). The detector is restricted to the list the first time it is used, so it can only answer a listed language (Latin text reads as the nearest living one); a saved choice that is no longer listed is dropped with `known_codes`. To remove another language: take it out of `LANGUAGE_NAMES`, add it to `REMOVED_LANGUAGES` and to a data migration like `scripts/migrations/2026-10-08_languages.sql` (untags its posts, strips it from curations). `tests/test_languages.py`.

## Send a post to a chat (legacy app)

The share menu of a post has **Send in chat**: a sheet with your chats and the people you follow, an optional message and one tap on Send. **Chats are end-to-end encrypted and only the browser's chat client holds the keys, so the server can never write a message for someone.** The message is sent by the chat page itself:

- `assets/js/share_chat.js` keeps `/chat?embed=1` in a frame (the side panel's own chat frame, `window.RuqqusPanels.chatFrame()`, so there is only ever one chat client per page), pings it until it says it is ready and asks it to send (`postMessage`, own origin only). `assets/chat_src/src/index.js` answers only its own parent, only into a chat in the member's **inbox** (a request waiting to be accepted is not writable), at most 2,000 characters.
- Routes (`routes/chat.py`): `GET /api/chat/share_targets?q=` (your chats, then people you follow; never anyone blocked either way, a request not yet accepted, or a name the word filter hides), `POST /api/chat/start?json=1` (the room, for someone with no chat yet; its block check and inbox-or-request rule are unchanged) and `GET /api/chat/post_preview/<id>`.
- **The card under a message** (`ui.js`): a message holding a link to one of this site's posts (matched by the page's host, either scheme) shows a card made for the **reader** by `post_preview`: their word filter, private guilds, removed and deleted posts, a notice when they may not see it, and **never the author** (an anonymous post stays anonymous). Everything is set with `textContent`. Needs a rebuild of the chat bundle (`docker compose build ruqqus`).
- "Send in chat" is hidden inside the side-panel frames (`body.embedded`). Not built: sharing a comment, sharing to a group (chats are pairs only).
- Tests: `tests/test_share_chat_assets.py`.

## Community notes (legacy app)

From the flag menu a member can **request a community note** on a post or comment ("This may be misleading or needs context"); an admin may then write a note that is shown under it to everyone. Start with `ruqqus/helpers/community_notes.py`.

- **A request is not a flag.** It is a `note_requests` row, never a `Flag`/`Report`/`CommentFlag` (those are policy reports in the admins' queue). Once per person per target, not on your own post or comment (409), at most 20 a day (429). Both flag routes now require the form key.
- **A note belongs to the primary post** (`primary_post_id`: `repost_id or id`), so a forwarded copy's requests count for the original and the note shows on every copy. Comments are kept by their own id. One live note per target (unique partial index); replacing one marks the old `removed_utc` and keeps it.
- **Admins (level 3)** use `/admin/note_requests` (most requested first; write, replace, dismiss, remove). Notes are plain text up to 600 characters, drawn escaped under the post (`submission.html`), the feed card and the comment through `partials/community_note.html`. A note says "added by <site> moderators", never which admin; the page never shows who asked; requesters get a notification with a link only. `post.json` and `comment.json` carry `community_note`.
- Which items have a note is read once per `TTL` seconds per worker (`_live_ids`), so a page of posts with no notes costs no extra query; the admin routes call `community_notes.forget()`, other workers catch up within 30 seconds.
- Tests: `tests/test_community_notes.py`, `tests/test_community_notes_assets.py`.

## Sensitive accounts and All (legacy app)

**All is everything on the site except sensitive content**, and For You, trending and a curation's whole-site pool (`curation_feed.site_pool`) follow it. "Sensitive" means upsetting topics (grief, addiction recovery): a heads-up, not a rule break. A post (`submissions.is_sensitive`), a guild (`boards.is_sensitive`) and now an **account** (`users.is_sensitive`) can be sensitive. Rules (pure, plus the SQL condition) in `ruqqus/helpers/sensitive.py`; migration `2026-10-18_sensitive_accounts.sql`, mirrored in `schema.sql`.

- **What All leaves out**: sensitive content (`hide_sensitive`, beside `hide_muted` / `hide_fewer`), unless the viewer chose to see it (`users.all_shows_sensitive`, "Show it in All and For You" in Settings > Content; off by default, never for a visitor, never on the Child filter: `shows_sensitive`). The viewer's own posts always stay. Still left out as before: guilds whose guildmasters switched on "keep us out of All" (`all_opt_out`, unless the viewer joined), banned guilds, anything not public (Circles, private guilds), blocks, mutes, "show fewer", the word filter and `hide_bot`. **No longer left out**: +general (board 1) and the categories Offensive / "kept off All" (the old kept-off list is gone).
- **Not applied** on a guild's own page, a profile, Following, search or a direct link: going there is a choice (the line mutes draw). Trending is one list for everyone, so it counts nothing sensitive (`hide_sensitive(..., None, ...)`).
- **An anonymous post is never judged by whose it is**: `hide_sensitive` and the Child filter (`visibility._not_by_sensitive_account`, `user_hidden(..., account_flag=False)` for an anonymous item) only leave a post out for its author's account when it is not anonymous, or the gap would say which anonymous posts are a sensitive account's. A sensitive account's new posts are marked sensitive when written (`sensitive.marks_post` in `submit_post`, and `edit_post` can't unmark them), anonymous or not, so they leave by their own mark.
- **A sensitive account acts like a sensitive guild**: a "Sensitive content" chip on the profile header (`.profile-x-sensitive` in both stylesheets), its new posts blurred, the whole account hidden for Child-filter viewers (`user_hidden`, `filter_users`, `filter_posts`, `filter_comments`), no ads on its posts or profile (`ads.account_allows`).
- **Who sets it**: the member ("My account is sensitive", `POST /settings/sensitive_account`) and a guild's guildmasters (the existing switch, `mod_bid_settings_sensitive`). **Admins (level 3) can force it** (`POST /admin/sensitive/user`, only below their own level; `POST /admin/sensitive/guild`, written to the guild's public mod log): `sensitive_forced` locks it on, the owner's switch is drawn disabled and refused with a 403 (`sensitive.owner_refusal`), and the account or the guild's guildmasters are told. Unlocking clears the lock only; the owner decides again.
- **Caches**: the viewer's choice and their own account flag drop that viewer's feed caches at once (`muting.clear_cached_feeds`). Other viewers' cached All / For You lists catch up within their 5 to 15 minutes when an account or guild is marked.
- `users.is_nsfw` is an old column nothing reads; it is not this flag.
- Tests: `tests/test_sensitive.py` (the rules and the filter on SQLite, the anonymous promise), `tests/test_sensitive_assets.py`.

## Muting (legacy app)

A member can mute an account (`usermutes`, `helpers/muting.py`): its posts and comments leave their feeds, searches and threads and its notifications stop. It is quiet and one-way: the account is not told and can still follow, comment and message. **A mute is not a block**: nothing that checks blocks (`any_block_exists`, comment and chat permissions) reads `usermutes`, and the two tables stay apart.

- **Wherever a feed already leaves out blocked authors it leaves out muted ones too**: `hide_muted(query, v, Model)` (All, Following, For You, guild lists, curations and what a feed server may name, search, a trending topic's posts, the notification lists and their counts). Not on a profile, a saved list or a history, and not on a search for one author: going there is a choice. A new listing needs the same line (`tests/test_muting_assets.py` checks the existing ones).
- **An anonymous post or comment is never hidden by a mute** (hiding only those would tell the muter which ones the account wrote; blocks do the same). In a thread a muted account's comment becomes "[You muted @x] Unmute" and the replies under it stay (`is_muted(item, v)` in templates).
- Bell notifications of a post skip the people who muted its author, unless the post is anonymous. Who to follow never suggests a muted account.
- `POST /settings/mute` and `/settings/unmute` (`routes/muting.py`) clear the per-viewer feed caches (`muting.clear_cached_feeds`); per-guild lists catch up within 60 seconds. Mute is offered in the post and comment menus, on profiles and in `/settings/blocks` ("Block & Mute"). Muting for a limited time is not built.
- **Muting a guild** (the old "Hide from /all"): the same quiet, one-way idea for a guild, stored in `boardblocks` (`BoardBlock`; the class kept its name so every earlier hidden guild is already a mute). Its posts leave the member's **All, For You and Following** (a guild they joined stays joined; the confirmation says so) and its bell, the guild's own page, profile posts, search for that guild and the member's subscription are untouched: going there is a choice. Where the filter is: the older inline `BoardBlock` subqueries (All `frontlist`, For You `for_you_idlist`, `/all/comments`, `/m/`, curations, search, trending, suggestions: `tests/*_assets.py` pin them, leave them) plus `muting.hide_muted_guilds(query, v, model)` for **new** listings (it is used by Following, `User.idlist`). A muted guild also stops teaching For You: `interest_subcats` ignores its subscription, its followed-account subscriptions and the votes cast in it. `POST /settings/mute_guild` and `/settings/unmute_guild` (the old `block_guild` / `unblock_guild` addresses are kept) call `muting.clear_guild_mute_caches(v)`: the per-viewer feeds, `interest_subcats` (an hour) and `comment_idlist`, so a mute shows at once instead of after the 5 to 15 minute caches. "Mute guild" is on every post card (dropdown and phone sheet, not on profile posts and not on a guild's own page, which has it in its own menu), the guild page menu and phone banner, the post page strip and Settings > Muted guilds (`/settings/filters`). **This is different from a guild's `all_opt_out`** (a guildmaster's "don't show us in All to non-members") and from a curation's "Leave out" list (it belongs to the curation, see Curation algorithms). `tests/test_guild_mute_assets.py`.
- Tests: `tests/test_muting.py`, `tests/test_muting_assets.py`.

## Bookmark folders (legacy app)

A member sorts their bookmarks into folders of their own (`bookmark_folders`, rules in `helpers/bookmark_folders.py`, routes in `routes/bookmark_folders.py`). A bookmark (`save_relationship` for a post, `comment_save_relationship` for a comment) is in **one** folder (`folder_id`) or none (unsorted); folders are private and a folder or bookmark of another member is a 404.

- **Deleting a folder never deletes a bookmark**: the routes set `folder_id` to NULL on both tables for the caller first (and the foreign keys are `ON DELETE SET NULL`). A name is unique per member ignoring case (a functional index), 40 characters, never `all` or `none` (those are views), 30 folders at most. Ids are read with `parse_id` (ASCII digits only; `str.isdigit()` also accepts other scripts' digits).
- **The Bookmarked tab** (`/history`, `routes/history.py`) takes `?folder=` (absent: all, `none`: unsorted, or an id; an id that is not the caller's is a 404) and passes it to `User.saved_idlist` / `saved_comment_idlist(folder=...)`, which filter before the usual word filter, block and mute rules. Every link on that tab (All / Posts / Comments, Prev, Next) keeps the folder: the continuous feed follows the Next link.
- **Filing happens on the History page, not in every menu.** You bookmark from a post or comment as always and sort later: on the Bookmarked tab the "…" menu of each item (post card, post page, phone actions sheet, comment menus) has "Move to folder", which opens `partials/bookmark_folder_modal.html` (`assets/js/bookmark_folders.js`): pick Unsorted or a folder, or make one. The six menu items only draw when `organise_bookmarks` is set, and only `history_bookmarked` sets it; `default.html` includes the sheet and the script on that condition too. `POST /bookmarks/move` still bookmarks the item as it files it, but only something the caller may see (`post_hidden` / `comment_hidden`) that is not removed or deleted. Do not add the item back to feeds, profiles or the post page (`tests/test_bookmark_folders_assets.py`).
- Tests: `tests/test_bookmark_folders.py` (the rules), `tests/test_bookmark_folders_assets.py` (schema, routes, ownership, listings, templates, both stylesheets).

## Circles (legacy app)

An account has one **Circle**: a private audience of its own. People are in it as **Close Friends** (the owner adds them, free) or **Subscribers** (they pay the owner's price in site coins every 30 days). Rules (pure) in `helpers/circles.py`; the database side in `helpers/circle_store.py`; routes in `routes/circles.py`; tables `circles`, `circle_members`, `circle_payments` (migration `2026-10-10_circles.sql`, mirrored in `schema.sql`).

- **Who sees what** (`circles.can_see(audience, is_author=, tier=)`): Public: everyone. Subscribers: subscribers AND close friends (friends get the paid area free). Close Friends: close friends only (a subscriber never sees those). Always the author. An audience nobody knows is seen by nobody but the author (fail closed). Audience ids: 0 public, 1 subscribers, 2 close friends, 3 Circle guild (a profile post can only choose 0-2: `parse_audience`).
- **Access is a date, not a job**: a subscriber's access is `renews_utc` (`tier_of`: strictly in the future), so when it passes they are out even if `scripts/renew_circles.py` is late or down. Cancelling keeps access until that date and stops renewals; subscribing again before it just resumes (no charge).
- **A subscriber renews at the price they signed up at** (`circle_members.price_coins`): the owner raising the price never charges existing subscribers more. A close friend has price 0 and `renews_utc` 0; adding a subscriber as a friend keeps their access and stops their payments (no refund).
- **Coins move in exactly two statements** (`circle_store._pay`): `UPDATE users SET coin_balance = coin_balance - :c WHERE id = :p AND coin_balance >= :c` (the check and the charge are one statement: a balance can never go negative and two payments cannot spend one coin) and the credit to the owner. The routes `flush()` the member's pending ORM changes first (`has_premium` renews from coins) and `refresh(v)` after, or a stale `coin_balance` would be written back. No refunds, no site fee, 1 to 100 coins per 30 days (0: Close Friends only); the owner's coins land straight on their balance.
- **Only the owner changes their own Circle**: every action uses `v.id` as the owner; the only account a request names is the other party (`_target`: unknown or deleted is a 404). A Circle is made the first time its owner sets a price or adds a friend (`ensure`); there is no off switch.
- **A block ends both Circles**: `settings_block_user` calls `circle_store.end_between` (friend rows go, subscriptions end, no refund). Messages never say who blocked whom; a renewal that ends because of a block (or a cancel) is **never** notified, only a lapse for lack of coins is, so a notice cannot reveal why.
- **Renewals**: `scripts/renew_circles.py` (own supervisord program `ruqquscircles`, hourly; `PYTHONPATH=. python scripts/renew_circles.py --once` by hand) settles each due subscriber on its own (`renew_due` commits per member).
- **UI**: Settings > **Circle** (`/settings/circle`: price, Close Friends, subscribers, coins received) and `/settings/circles` (Circles you are in, cancel); a profile's header shows "Subscribe · N coins/mo" (or "Subscribed" / "In their Circle") and its "⋯" menu "Add to / Remove from Close Friends" to a signed-in member looking at someone else (`partials/profile_header.html`, `circle_status` Jinja global).
- Stories are built on the same audiences (see **Stories** below).
- Tests: `tests/test_circles.py` (rules), `tests/test_circle_store.py` (the SQL on SQLite), `tests/test_circles_assets.py`.

### Posts made for a Circle

A post on the author's own profile is made for **Public** (the default), **Subscribers** or **Close Friends** (`submissions.audience` 0 / 1 / 2; 3 is reserved for Circle guilds). The composer field is `post_options.audience_field` (Create a post, the feed composer and drafts: `post_drafts` keeps and republishes it), read by `submit_post` as `audience`; an author changes it later from the post's menu ("Who can see this", `partials/audience_modal.html`, `POST /api/post/<id>/audience`; making a Circle post public again needs `confirm=1`, and the sheet asks). Narrowing to a Circle that would reach nobody (no Close Friends, or for Subscribers no friends and no subscribers: `_empty_audience`) also answers 409 with `confirm: true` and a sentence ("...so only you would see this post."), and the script asks "Save anyway?" and resends. The Edit form shows "Who can see this: <audience> · Change" (`.audience-open`, the same sheet). A Circle-guild post (audience 3) keeps its guild's audience and is refused here.

- **Fail closed, twice.** (1) A Circle post is stored with `post_public = false`, so every list that asks for public posts leaves it out: All, For You, search, trending, curations, guild lists, a profile's comments. (2) The one place every route reads a post or comment through guards too: `get_post` raises `CircleOnly` (a **404 subclass**, so a route that knows nothing about Circles fails closed), `get_posts` and `get_comments` drop what the viewer may not see, `get_comment` 404s. The viewer is the one passed in, else `g.v`, else nobody (`helpers/circle_guard.py`). Admins (level 4, as for private guilds) and the author always see it. `routes/errors.py` turns `CircleOnly` into a gate page (`errors/circle_gate.html`: the owner, who it is for, a Join button; never a title, text or guild; 403, `no-store`) for a page and a plain 404 for the API.
- **Only the viewer's own lists add the members' condition** (`circle_clause.for_viewer`, five sites: the Following feed `idlist`, a profile's own-posts list, saved, viewed and voted posts). Not For You, search, trending, curations, a guild, comments or reposts. `tests/test_circle_posts_assets.py` records every use of `post_public`: adding one means deciding about Circle posts there.
- **A Circle post stays between the author and the Circle**: it cannot be anonymous, have co-authors, be forwarded or reposted (and neither can a comment on it), or carry a video uploaded to the author's YouTube channel (a link anyone holding it can watch); `circles.post_refusal` is the one list, used when posting and when changing the audience (which also refuses a post that has already been forwarded, reposted or co-authored). Polls are fine.
- **Media**: a picture or sound in a Circle post (or a comment on one) is served only to the people who may see the post, `Cache-Control: no-store` and with the session read (`rules.access(..., audience, allowed)` returns `PRIVATE`, never `PUBLIC`; `attach.audience_of`); a public one stays immutable and cookie-less. Narrowing a post to a Circle purges the CDN copies.
- **Notifications** (followers and mentions) go only to people who may see the post (`circle_guard.eligible_ids`).
- A post for a Circle shows the "private post" eye with the audience in its tooltip (`Submission.private_label`); `Submission.is_public` is false for it.
- Migration `scripts/migrations/2026-10-10_circle_posts.sql`. Tests: `tests/test_circle_guard.py` and `tests/test_circle_clause.py` (real SQL on SQLite), `tests/test_circle_posts_assets.py`.

### Circle guilds

A guild can be a **Circle guild** (`boards.is_circle`, chosen with a checkbox when it is created and **never changed**): it is private for good, only its members see it, and members post **straight in** it. This is the one exception to "a post is made on your own profile first": a post made in a Circle guild (the composer on its page sends `circle_guild`) is a primary post on the guild's board with `audience = 3` and `post_public = false`, no profile copy, no forwards. It is **not on their profile** for anyone (`userpagelisting` leaves `audience = 3` out), it cannot be anonymous, co-authored, forwarded or reposted (`circles.post_refusal`, same as any Circle post), and the author's followers are not told, the guild's members are.

- **Members are approved contributors** (`ContributorRelationship`) and guildmasters, so the private-guild rules (`Board.can_view`, the contributor condition every list already has) do the listing. Membership comes two ways: a guildmaster approves someone (free, the existing Approved Contributors page) or they **pay the founder's price** in coins every 30 days (`circles.board_id`, `circle_store.subscribe_guild`; the coins go to `Board.creator_id`, the founder, who alone sets the price on the guild's **Circle** tab, `/+guild/mod/circle`; 0 means by invitation only). The pay-to-join button is `partials/circle_guild_button.html` on the guild page; `/settings/circles` lists and cancels guild memberships.
- **The guard asks the guild for audience 3** (`circle_guard.in_guild`: an active contributor or an accepted guildmaster, not exiled; admins always; the author only while they are a member). `hidden_parents` carries the board so comments follow.
- **A membership ends with its date, with the coins running out, with an exile (`exiled_from`) or when a guildmaster removes the member** (`mod_unapprove_bid_user` calls `end_guild_member`, so they are not charged again); the renewal job (`renew_due`) handles guild rows too and tells a member whose coins did not cover it, naming the guild.
- **Private for good**: the guild settings' privacy toggle refuses a Circle guild (409), and the three places that make a guild public when its last guildmaster leaves (`boards.py`, `User.ban`, delete account) skip a Circle guild.
- Migration `scripts/migrations/2026-10-10_circle_guilds.sql`. Tests: `tests/test_circle_guilds.py` (the SQL on SQLite), `tests/test_circle_guilds_assets.py`.

## Stories (legacy app)

An account can share **stories**: a picture, a text card or (public only) a YouTube video that lasts 24 hours, shown as a ring round the profile avatar, plus **Highlights** kept under the bio. Rules (pure) in `helpers/stories.py`; the database side in `helpers/story_store.py`; routes in `routes/stories.py`; tables `stories`, `story_views`, `highlights`, `highlight_stories`, `story_reports` and `media_assets.story_id` (migration `2026-10-10_stories.sql`, mirrored in `schema.sql`; no foreign keys to `users`).

- **Who may watch is decided in one place**: `story_store._allowed`, behind `watchable`, `rings`, `highlights` and `highlight_stories`. The owner always; a deleted story never; a block either way hides it (even a public story); the viewer's word filter (text is rated when made, `word_severity`); then `circle_guard.may_see(audience)`, the same rule as posts: Public, Subscribers (subscribers and close friends), Close Friends; admins only from level 4. A new place that shows a story goes through these and never selects from `stories` itself (`tests/test_stories_assets.py`).
- **Making one** (`POST /api/stories`, form key, not banned, the author is always `v.id`): `kind` image / text / video; `audience` 0 to 2 (3 and 8 are internal and refused, and the table's CHECK says the same); `text` up to 300 characters; `background` one of the fixed names in `stories.BACKGROUNDS` (the colours are `.story-bg-<name>` in **both** stylesheets: a new name needs a rule in both); `video` a YouTube id or link of which only the 11-character id is stored and drawn, and **only on a public story** (a link works for anyone who holds it, so it cannot be kept for a Circle); `media` the id of the member's own ready picture on linked storage (uploaded by `media_upload.js`, attached once by `attach_picture`, scanned by `media.safety.scan_later`). 30 a day (429).
- **A story's picture** is served by `/media/...` like any linked file but **always per viewer and `no-store`, never public-cached**: `attach.audience_of` answers `circles.STORY_OPEN` (8, internal) for a public story (any signed-in account that is not blocked either way, never a visitor) and the story's own audience otherwise; `attach.is_live` is true while the story is not deleted and is within its 24 hours or in a Highlight. An owner can still fetch their own deleted file, as for a post.
- **The ring** (`story_ring(owner, viewer)`, a Jinja global): `unseen` (gradient), `seen` (grey), `own`, or none; a visitor never gets one and the story API answers visitors with a login redirect or 401. `story_views` is one row per (story, viewer): it exists so the ring can turn grey and the owner can read a **count**. **No response and no page ever names a viewer** (the tripwire pins the only two SELECTs on that table: the viewer's own seen ids and the counts); a view is recorded only for a story the viewer may watch (a 404 otherwise).
- **Highlights** (20 a member, 50 stories each, a name up to 30 characters): made of the member's own live or past stories (`/api/stories/archive`, own only, newest 100); a Highlight keeps a story past its 24 hours; each viewer sees only the stories of it they may watch, and a Highlight with none for them is left out of the row and answers 404; deleting a story takes it out of every Highlight; deleting a Highlight keeps its stories.
- **Reporting**: "Report" in the viewer files a `story_reports` row (not a `Report` or `Flag`): once per person per story, only for a story the reporter may watch, never your own, reason up to 200 characters. Admins (level 3) work `/admin/story_reports` (remove, which takes the story out of every Highlight too, or dismiss); its "See the picture" link opens for level 4 admins and for public stories, like any Circle media.
- **UI**: `partials/story_bits.html` draws the avatar ring with its "+" and the Highlights row (`story_avatar`, `highlights_row`) in the desktop and the phone banner of `userpage.html`; `partials/story_sheets.html` holds the viewer, the story sheet and the Highlight sheet and is loaded with `assets/js/stories.js` only on pages that set `story_ui` (the profile), for signed-in members, outside the side-panel frames. The script draws only with `textContent` and checks a picture path (`/media/`), a video id and a colour name before using them. The viewer has progress bars, tap right or left, arrow keys, hold to pause and Escape; a card lasts 5 seconds (a video waits for a tap). Not built: replies to stories, stickers, a stories tray in the feed, a list of viewers.
- Tests: `tests/test_stories.py` (the rules), `tests/test_story_store.py` (the SQL on SQLite, with the media rules), `tests/test_circle_guard.py` (`STORY_OPEN`), `tests/test_stories_assets.py`.

## Deletion log (legacy app)

`GET /log/deleted` (`routes/deletion_log.py`, rules in `helpers/deletion_log.py`, `deletion_log.html`) is a **public** site-wide record of the posts and comments their authors deleted, newest first (Posts / Comments tabs, `?guild=`, `?user=`, 25 per page). Each entry shows **the text the item had when it was deleted**: the owner chose a public log WITH the text, knowing it is a public copy of what people deleted. It reads `content_edit_history` rows with `action = 'delete'` (written by `delete_post_pid` and `delete_comment`; a partial index keeps it quick, migration `2026-10-10_deletion_log.sql`). One row per deleted item: the forwards a deleted post takes down with it write none, so an entry names the guilds the post had been forwarded to.

- **What it never lists**: anything not public to begin with (`Submission.post_public` false: Circle posts and private-guild posts, and the guild must not be private or banned), anything a moderator or admin removed (`is_banned`, `hidden_by_guild`, `purged_utc`), anything an admin obliterated (the `ObliterationRecord` check, and `previous_title` / `previous_body_html` are NULL after the scrub: that scrub stays authoritative), and anything the viewer's word filter hides (`filter_posts` / `filter_comments`; the forwarded-guild names go through `filter_boards`).
- **Anonymous items** show the deleter as Anonymous (`anon_hidden(item, v)`; the name comes from the history row's actor and only when not hidden, never from `.author`) and are left out of a `?user=` list (`anonymity.hide_anonymous`). A new filter that names one author needs the same line.
- **Stored HTML is the only HTML drawn** (`media_free(previous_body_html) | safe`, sanitized when it was written; `without_media` swaps its pictures and sounds for a `[picture]` / `[sound]` marker, since deleting a post detaches its uploads and the addresses would only show broken pictures); the title and link are escaped.
- **It is a paged list, not a feed**: no `#posts` / `.posts`, so `infinite_scroll.js` does not engage; Prev / Next stay.

## One vote per post across its copies (legacy app)

A forward is an independent copy of a post in a guild (own votes and comments, `repost_id` points at the original). So that one person can't vote on the original and on every copy, a person may hold an **active** vote (`vote_type` 1 or -1) in at most one live member of a post's **family**: the original plus every row whose `repost_id` points at it (forward copies and the legacy pre-Forward resubmits). The original counts as one of the copies; a forwarded comment becomes a new post with no family. Start with `ruqqus/helpers/vote_copies.py`.

- **The vote route asks first**: `api_vote_post` calls `vote_copies.refusal(g.db, v, post, now)` after the removed/deleted/archived refusals and before anything is written, and answers `403 {"error", "voted_in"}` (the message names where the other vote is: "the original post" or "+guild"). **Taking a vote back (`x=0`) is never checked by this rule**, so it frees the person to vote on another copy (the removed / deleted / archived refusals before it still apply to every vote). A refused vote writes and commits nothing.
- **Race-safe without a schema change**: `refusal` first takes `pg_advisory_xact_lock(user, family)`, released by the route's commit, so two simultaneous votes on two copies by one account queue and the second sees the first. A unique index can't be added over the duplicate rows that already exist, which is why the rule lives in the route and not the database.
- **Live members only**: a vote on a removed or deleted copy, or one in a banned guild, doesn't count (it is out of every feed). A vote on an archived copy does (frozen but real; the message then says it can't be changed any more).
- **The post's author is exempt.** They get an automatic upvote on the original and on every forward copy (`_build_standalone_submission(auto_upvote=True)`, deliberately kept) and keep voting on all of them. Their vote is not marked as automatic, which is why the exemption is by author rather than by vote.
- **Votes cast before the rule are left alone.** The rule only refuses to add or change a vote while another active one exists in the family, so someone with votes on several copies can remove any of them but not change one. `PYTHONPATH=. python scripts/report_cross_copy_votes.py` (read-only) counts them, authors apart from everyone else.
- **On the page**: `vote_copies.attach` (in `get_post` and `get_posts`, one query per page) sets `post._voted_elsewhere`; `Submission.voted_elsewhere` is what the templates read. A post the viewer has voted on is never locked (they must be able to change or remove that vote). ## Tips (legacy app)

A tip moves coins from the tipper to the author (`gift_post_pid` / `gift_comment_pid` in `routes/paypal.py`) and is **seen on the post** as the total coins tipped (the coin in the post's action row, `partials/post_actions.html`, on the feed card and the post page; comments show theirs with a `.tip-badge`). Tips are anonymous: nothing shows who tipped. Rules in `ruqqus/helpers/tips.py`, SQL in `helpers/tips_store.py` (tested on SQLite).

- **Every tip is one `award_relationships` row with its `coins`** (the old one-per-person constraints are gone; rows from before 2026-10-13 count as 1 coin). A post keeps `tip_coins` (every coin, what it shows) and `tip_boost` (what counts for ranking), worked out again by `tips_store.recompute_post` on each tip.
- **The boost is ranking only**: `rank_hot` and `rank_best` (Postgres functions) add `tip_boost` to `upvotes - downvotes`, so tips lift a post in Hot, Best, For You and curations (`curation_feed.mix_score` counts it with votes). **Never in `score()`, `score_top`, the Top sort or the number shown on a post**: that stays an honest vote count. Tips count only from accounts at least 30 days old, not banned or deleted, not the author, and **sharing no address with the author** (`guild_limits.addresses_of`), or a second account would be a free boost (the coins come back). The coins move either way. A forward copy's tips lift that copy; the coins go to the original author.
- **The routes**: coins are read with `tips.parse_coins` (1 to 1,000, a 400 otherwise); the coins, the tip row, the post's totals and its stored `score_hot` / `score_best` are one transaction, committed **before** `send_notification` (which commits on its own). "Tip" is the coin in the action row (never on one's own, an anonymous, a removed or a deleted post, or one whose author's account is deleted; elsewhere the count shows but does nothing).
- After changing the rules, `PYTHONPATH=. python scripts/recompute_tip_boost.py --once`. Migration `2026-10-13_tips.sql`.
- Tests: `tests/test_tips.py`, `tests/test_tips_store.py`, `tests/test_tips_assets.py`.

## Curation algorithms (legacy app)

A curation can have its own algorithm: which posts it shows and in what order (`curations.algorithm`, JSON). Start with `ruqqus/helpers/feed_algorithm.py` (the rules, stdlib only).

- **Members never write code, patterns or SQL.** A spec is only ever made by `feed_algorithm.clean` (fixed names, bounded numbers, plain words) and stored with `feed_algorithm.dump`; read it with `curation.algorithm_spec`. `helpers/curation_feed.py` turns a spec into the query: words become LIKE text with their wildcards escaped (`like_pattern`), sites are checked host names. A new option needs: the name in `feed_algorithm` (`DEFAULT`, `clean`, `from_form`, `describe`), its condition in `curation_feed.apply`, and the field in `templates/curations/algorithm_form.html`.
- **What a spec holds**: source (`members`: the curation's guilds and accounts; `site`: every public post as All, with an age limit of a month or less), words a post must / must not mention (title and text), kinds of post, sites linked to, minimum votes / comments, age, things left out (bots, made with AI, paid partnership, forwarded copies), **accounts and guilds left out** (`exclude_users`, `exclude_guilds`, below), and the order: Hot, New, Top, Most discussed or the member's own mix (`MIX`: weights for votes and comments, how fast posts fade, boosts, at most N posts per author or guild on a page).
- **Who may see what is not the algorithm's business**: `_curation_ids` in `routes/curations.py` applies the word filter, private guilds and blocks before `curation_feed.apply`, for every curation. An account's anonymous posts never match through the account (`curation_feed.member_condition`), and the "per author" limit treats every anonymous post as nobody's (`feed_algorithm.spread`).
- **Leaving accounts and guilds out of ONE curation** ("Leave out these accounts / guilds" in the algorithm form; the curation's own list, **never the owner's mute list** (`usermutes`, `BoardBlock`), which is a separate thing that follows the owner): up to `MAX_EXCLUDED` (50) of each, stored as **ids** inside the algorithm JSON (a name can change hands; no table, no migration; `feed_algorithm._ids`). The route turns typed names into ids (`_left_out_ids` in `routes/curations.py`, through `search_filters.find_account` / `find_guild`, so a name the owner may not see is "No account called @x." and never confirms a private or Circle guild; an account the owner blocked is still theirs to leave out) and hands `from_form` the ids; the form shows names back (`_left_out_names`). `curation_feed.leave_out` applies it inside `apply` (every curation) and `drop_left_out` to what an outside feed server named: guilds by `board_id`, accounts through `muting.exclude_authors`, the rule under a member's mutes: **an anonymous post of an excluded account stays** (dropping only those would tell the owner which ones it wrote), a post co-authored with it goes, and its forward copies go in every guild (a copy keeps the original `author_id`). Where the account is also a member, the exclusion wins. **The public text counts only** ("Leaves out posts from 2 accounts and 1 guild.": `left_out_line`): names would expose private or Circle guilds, word-filtered names and a statement about a person. **A fork gets the rules, not the list** (`without_left_out`). It is plain filtering, so it still makes the spec non-default (the curation then uses its own `rank`, like a words-only one). `tests/test_curation_exclusions.py`.
- **Rules of one's own run under a 3 second limit** inside a savepoint (`curation_feed.limited`); a slow one shows a notice (`FeedTooSlow`), never a hung page. An own mix ranks the newest 1,000 matching posts (`MIX_POOL`).
- **Everyone who can see a curation can read its rules**: `feed_algorithm.describe` is shown on the curation page ("How this curation picks posts"). A fork copies the algorithm and the filters (not the leave-out list, which `describe` only counts). Creating a curation offers "Start from" (`PRESETS`) and lands on the edit page; the form saves without script, `assets/js/curation_algorithm.js` adds the starting points and the live preview (`/&<slug>/preview_algorithm`, which saves nothing).
- A sort the viewer asks for (`?sort=`) wins over the curation's order; a curation with no algorithm of its own behaves as before.
- **Outside feed servers** (mode `server`, as Bluesky's custom feeds; `helpers/feed_server.py`): the curation names a server that answers `GET <address>?limit=100[&cursor=...]` with `{"posts": ["<post id>", ...], "cursor": "..."}` (documented for members at `/help/feed_servers`).
  - **The server only orders.** `_server_ids` puts every id it names through `_viewable` (the same rules as any feed) before `get_posts`; a sort in the address does not apply.
  - **Nothing about the viewer is sent**, ever: `feed_server.ids_for` takes no viewer, and one list is kept for everyone in Redis (120 s; 500 posts at most; three failures in a row pause a server for 10 minutes and its last good list is shown; 30 requests a minute per host for the whole site).
  - **Every fetch of a member's address goes through `helpers/safe_fetch.py`** (bot feeds too: `helpers/feed_fetch.py` calls its `check_url`, `vetted_address` and `_Pinned` at every hop) and nothing else: https only, the usual port, no credentials, every address the name resolves to must be public, the connection goes to the address that was checked, no redirects, 3 seconds, 64 KB. A new feature that fetches an address a member typed must use it too (the older fetchers in `thumbs.py` / `embed.py` do not).
  - `FEED_SERVER_ALLOW_LOCAL=1` lifts that guard for a test server on the local machine (set in `docker-compose.yml`; never on a live site). `FEED_SERVERS_ENABLED=0` switches the feature off. An admin (level 4) can take a curation off its server from its page; the page always says, uncollapsed, that an outside server ranks it.
- Tests: `tests/test_feed_algorithm.py` (the rules), `tests/test_curation_algorithm_assets.py` (query, routes, owner-only, form, script, schema, both stylesheets), `tests/test_safe_fetch.py` (the guard, with real local sockets), `tests/test_feed_server.py` (the protocol and the state).

For members: `/help/bots`, drawn from the limits (Jinja global `bot_rules`).

- **Proposing** (Settings > Bots, `settings_bots_apply`): a member in good standing (30 days old, not suspended; `bots.owner_refusal`) proposes up to 3 at a time (`active_count`: their member bots not rejected plus their site-bot proposals still waiting); admins are held to neither the age nor the count, and may tick **Approve it now** (that is how admins make site bots). A proposal carries the kind, the name, what it posts (for the admins), a plain-text bio (no links), a **profile picture and a banner** (opened with PIL and checked: PNG, JPEG, GIF or WebP, 8 MB, `_image`; stored in the site's S3 bucket like a member's avatar, `User.set_profile` / `set_banner`, then the CSAM check with the proposer answerable), feeds and guilds. `proposed_by_id` is kept for the admins and to tell the proposer of the decision; it is never shown.
- **Who may change a bot is `bots.may_manage`** (`_manageable` in the routes, anything else a 404): an admin, any bot that is not rejected; a member, their own member bot, and a site bot they proposed **only while it waits**. Before approval an admin may also **rename** it (`admin_bot_rename`) and **change its kind** (`admin_bot_kind`: a site bot needs a feed; a member bot's owner is its proposer); both are refused once it was decided. Pictures, banner, bio, feeds and guilds are edited on the bot's page by whoever may manage it. Whoever is told of a decision is `bots.responsible_id` (the owner, or the proposer of a site bot); after approval a site bot has nobody to tell (pauses, failing feeds and admin decisions notify only member-bot owners).
- **A bot account is a `users` row made when the bot is proposed** (it reserves the name; the sign-up name rule), with `is_bot`, `bot_owner_id` (member bots only), `tos_agreed_utc` and a password hash that never verifies (`UNUSABLE_PASSWORD = "!"`). **Nobody logs into a bot**: `login_post` refuses it like a wrong password, so it is never anyone's alt (`check_for_alts` only runs at login) and the spam guard's "ban every alt" can't reach its owner. Until it is approved its profile is a 404 except to its owner or proposer and admins (`User.bot_shown_to`); a rejected or withdrawn bot's account is deleted (it never posted) and a rejected `bots` row keeps the name and the admin's note.
- **Its profile says who runs it** (`partials/profile_header.html`, `User.bot_kind`, `User.bot_owner`): "Automated by <site>" for a site bot, "Automated by @owner" for a member bot, with the robot icon; no Chat button. Every bot post carries `is_bot` (stamped from the account in `submit_post`, not only from the header), so the viewer setting **Hide bot content** (`hide_bot`) and trending's bot filter cover them.
- **One rule decides whether a bot may post**: `submit_post` asks `_bot_refusal` -> `bots.post_refusal` for every bot account, whichever way the post comes: approved (not pending, rejected or paused), for a member bot an owner who is not suspended or deleted, `BOTS_ENABLED` on, under `DAILY_CAP` (40) posts today (`bot_store.count_post` after each post). It answers 403 with `bot_refusal: "wait"` (the cap, the switch) or `"stop"`; the options a bot may never use are refused with a 400 (`option_refusal`: anonymous, a Circle audience, co-authors). Posts are public, on the bot's profile, forwarded to the bot's chosen guilds under each guild's rules (`disallowbots` now also reads the account, and is no longer case-sensitive). The posting throttle applies as to anyone.
- **Never, by account and not only by header**: comment (`api_comment`), vote (`routes/votes.py`), chat (`/api/chat/start` refuses a bot either way), take tips (both gift routes, and the tip coin in `partials/post_actions.html`), share in the creator fund (`_ELIGIBLE`), or lead a guild (`User.can_join_gms` is false and `gm_limit_refusal` answers "person", which covers every way of making a `ModRelationship`). Moderation is unchanged: report, remove, ban the bot (`User.ban`), mute or block it.
- **Feeds are its sources** (`bot_sources`, at most 5): RSS 2.0, RSS 1.0, Atom and JSON Feed. Each item becomes a **link post: its title and its link, nothing copied from the page**; an item with no title (Bluesky, Mastodon) takes the start of its text. The posted link drops its tracking parameters (`bots.clean_link`: `utm_*`, the BBC's `at_*`, click ids; `ref`, `si`, `feature` stay), but the item's key is made from the link as the feed gives it, so items seen before keep their keys. A source the bot was proposed with is approved with it; **one a member adds later waits for an admin** (`pending_sources`), one an admin adds is approved at once (`add_source(approved_by=)`); removing one is immediate. Pause and resume; **a bot an admin paused is resumed by an admin only** (`paused_by_admin`).
- **Fetching**: `helpers/feed_fetch.py` through `safe_fetch`'s guard (`check_url`, `vetted_address`, `_Pinned`) at **every** hop, at most 3 redirects, conditional GET (ETag / Last-Modified, a 304 costs nothing), 2 MB, 10 s, never this site's own host (`bots.own_host`). `safe_fetch.py` itself still follows no redirects (pinned). `FEED_SERVER_ALLOW_LOCAL=1` also lets a local test feed be read. **Parsing**: `helpers/feed_items.py`, pure, with **`defusedxml`** (entity declarations and anything external are refused: no expansion bombs, no XXE); up to 100 items, an http(s) link required, titles cleaned and cut to 280 (`bots.clean_title`).
- **The runner**: `scripts/run_bots.py` (supervisord `ruqqusbots`, every 60 s; `PYTHONPATH=. python scripts/run_bots.py --once` by hand) claims due sources (`bot_store.claim_due`, `FOR UPDATE OF s SKIP LOCKED`, a 5-minute lease) and hands each to `helpers/bot_runner.run_source` (Flask-free, tested with stand-ins). **The first read of a source marks its backlog seen and posts only its newest 3** (`FIRST_READ`); after that new items go oldest first, at most 3 a run (`PER_RUN`). An unseen item dated more than 2 days back (`bots.is_stale`, `STALE_AFTER`; undated items never are) is marked seen and never posted: the promos a feed keeps (the BBC's "Sign up now") and old stories put back. Each post goes through the real `POST /api/vue/submit`, in-process, as the bot (a one-off session), with `X-User-Type: Bot`, `no_repost=1` and **the bot's own loopback address** (`bots.loopback_for`: unique per bot, never 127.0.0.1), so bots never share the posting throttle's per-address bucket and never share an address with a member (`guild_limits.addresses_of`). What an answer means is `bot_runner.classify`: posted, duplicate (seen), wait (429/503/the cap: tried again), guild (posted again without forwarding, the reason recorded), refused (seen, the reason recorded), stop (suspended, not approved: the bot is paused and a member bot's owner told). Only a member bot asks for its owner's standing. **Each feed is read as often as it safely can be** (`bots.next_interval`, not a fixed time): never more often than `FLOOR_MINUTES` (5), nor than the feed asks (`feed_asks`: RSS `<ttl>`, `sy:updatePeriod` / `sy:updateFrequency`, kept in `bot_sources.asked_minutes` because a 304 has no body) or its server asks (`server_asks`: `Cache-Control: max-age`, `Expires`); a read with nothing new stretches the wait by half up to `QUIET_MAX_MINUTES` (60), and the first read with something new goes back to the shortest. The BBC's feed says `<ttl>15</ttl>`, so it is read every 15 minutes. `check_minutes` is the current interval and the bot's page says it (`cadence_label`). A 429 or 503 with `Retry-After` is waited for exactly (`retry_wait`, a day at most); other failed reads back off (doubling, a day at most); after 10 in a row the source pauses. Reading more often never posts more: the per-read and daily caps are unchanged. Migration `2026-10-19_feed_intervals.sql`. Seen items are kept 90 days. **Never copy `submit_post`'s logic into the runner.** `BOTS_ENABLED=0` stops it all (`.env.example`, `docker-compose.yml`).
- **Pages**: Settings > Bots (`/settings/bots`: "Your bots", "Site bots you proposed" and the proposal form, which reads each feed once to check it is one) and `/settings/bots/<name>` (`settings_bot.html`: the admins' panel with rename, kind, approve and reject while it waits; picture and banner; feeds with their state and last error, add / remove / start again, approve / reject for an admin; keys; bio and guilds; pause / resume; **Withdraw** a waiting proposal, or switch off for good: the account is deactivated and its posts stay). Every change is a POST with the form key. Admin > Bots (`/admin/bots`, linked from the admin page with a waiting count, `bots_waiting`): proposals with their kind and an **Open and edit** link, a live **Check the feed now** (`?check=<source>`), approve or reject with a note, feeds added later, running and paused bots with pause (with a reason) / resume, and **Make a site bot**. Decisions taken on a bot's page come back to it (`next=page`).
- **Bot keys** (member bots only; for X and any owner-run script; `/help/bots#keys`): **X has no feeds and its terms forbid scraping, so the site never reads X**; the owner's own script, with the owner's own X access, posts each tweet's link (drawn as X's own embed) through a key. A key is a `ClientAuth` for the bot account through one of the owner's **own** apps (`author_id == v.id`, Settings > Apps), made on the bot's page by its owner once it is approved (`_is_owner`: a member bot whose `owner_id` is the caller; admins may revoke but never create), at most `MAX_KEYS` (2): scopes identity, read, create, update, delete (`KEY_SCOPES`: never vote or guildmaster), a refresh token shown once (`no-store`), no code. The script uses the documented `POST /oauth/grant` (`grant_type=refresh`) for an hour's access token and posts with `/api/v1/submit`, which is `submit_post`, so every bot rule above applies. Revoking deletes the grant; switching the bot off deletes its keys. A member bot needs no feeds for this. Deleting or editing an app is its author's alone (`delete_oauth_app` / `edit_oauth_app` were open to anyone signed in; `tests/test_oauth_apps_assets.py`).
- Tests: `tests/test_bots.py` (rules), `tests/test_bot_store.py` (SQL), `tests/test_feed_items.py` (formats, hostile XML), `tests/test_feed_fetch.py` (local sockets: hops, 304, caps, this site), `tests/test_run_bots.py` (the runner, site bots included), `tests/test_bots_assets.py`.

## Background jobs (legacy app)

Each is its own supervisord program (`supervisord.conf`, all with `PYTHONPATH`): `publish_scheduled.py` (drafts, every 30s), `run_bots.py` (`ruqqusbots`, bot accounts' feeds, every 60s; see **Bot accounts**), `compute_trending.py` (every 5 min), `renew_circles.py` (hourly) and `recomputes.py` (`ruqqusrecomputes`, one cycle every 5 min: re-scores live posts of the last 180 days, purges the live text of posts and comments deleted over 90 days ago, guild trend ranks, region / VPN state). The purge never touches `content_edit_history`, so the public Deletion log keeps its copy. Mod actions are **not** deleted after 180 days any more (the guild mod log is a public record) until the owner decides how long logs are kept.

## Painting right the first time (legacy app)

A page must be right at its first paint: no theme swap, no sidebar folding or navbar sliding after load, nothing pushed down by a late box. `tests/test_page_paint_assets.py`.

- **Theme**: `partials/theme.html` `theme_links(light, dark)` is the only way a page loads its theme stylesheet (guild pages pass the guild's coloured pair). A saved choice (`session.dark_mode_enabled`, members and visitors alike; `theme_choice()` in `helpers/page_assets.py`) gets one `<link id="css-link">`. With no saved choice, both stylesheets are listed with a `prefers-color-scheme` media query, so the device decides. `switch_css()` in `all_js.js` reads `data-light` / `data-dark`, loads the other stylesheet before removing this one, and saves the choice. Never switch the stylesheet on load.
- **Folded left sidebar**: the `sidebar_pref=collapsed` cookie, read by `sidebar-left.html` and by `<html class="sidebar-folded">` in `default.html`. The navbar's CSS defaults cover both layouts (1326px block open, 1091px folded = 65 + 726 + 300). `nav_align.js` only fine-tunes, and the search box fades in once it has (`html.nav-align:not(.nav-aligned)`).
- **Late boxes** (Trending, Who to follow): `partials/late_boxes.html`. Each keeps the height it had last time (`localStorage late_box_h:<id>`, `fill_late_box` in `all_js.js`). A new late-loaded box gets the same treatment.
- **The row**: the server marks `#main-content-row.expects-right-sidebar` (the `sidebar` block, rendered once into `right_sidebar` at the top of `default.html`) and the stylesheets keep the feed's and the right sidebar's room until their markup has arrived. `html { scrollbar-gutter: stable }`.
- **Pictures**: a linked-media picture gets `width`/`height` from `media_assets` (`media.attach.attach_image_sizes`, one query in `get_posts` and `get_post`); others keep a placeholder height while loading.
- **Assets**: every local script and stylesheet goes through `asset_url('js/x.js')` (a content hash in `?v=`), and versioned `/assets/` answers are cached for a year (`__main__.after_request`). Never write `src="/assets/..."` by hand or a `?v=` number. `routes/static.py` compiles `main.scss` / `main_dark.scss` once per worker per change; a stylesheet that does not compile keeps the last good one, and `test_both_stylesheets_compile` runs the real libsass (the image's version, in `requirements-dev.txt`), which is older than modern CSS: no `@supports selector(...)`.

## Rules

- Run the check command before declaring any task done.
- Write tests for auth, permissions, and voting logic. Legacy code has working auth/voting
  (`ruqqus/routes/votes.py`, `helpers/wrappers.py`); add characterization tests before changing it.
- Never commit secrets, and never disable lint/type rules to silence errors; fix root causes.
  There are no lint suppressions in the code; keep it that way. Ruff selects errors only (`pyproject.toml`), and with
  the star imports undefined names show as F405, which is not selected: a NameError is not caught by lint.
- `lib/` was once gitignored; `web/src/lib/` is now tracked. Do not re-add a blanket `lib/` ignore.
- UI work: follow the taste skill while building; open the page with Playwright (desktop and mobile
  widths) and check it visually before finishing.
- Use the Emil skill (`emil-design-eng`) when polishing animations and micro-interactions.
- Run the web-design-guidelines audit on changed UI files before committing.
- **Icons are Font Awesome 6.4 Free and nothing else** (`default.html` loads it from cdnjs). Use only class names in `tests/data/fa_free_6_4_0_names.txt`: a Pro-only name (`fa-telescope`, `fa-bell-on`, `fa-lock-alt`...) draws as nothing, a font the site never loads (`"Font Awesome 5 Pro"`) falls back to whatever each system has, and a symbol character as an icon (arrows and shapes like ◀ ▶, ✖, emoji) is drawn differently on Apple and Windows (Apple colour emoji vs a box). `board_main.scss` and `board_dark.scss` are not served (guild pages are built from `main.scss` / `main_dark.scss` with the colour swapped in). `tests/test_icons_assets.py`.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:

- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
