# Uqqus

Two independent apps in one repo. Do not mix imports or config between them.

|            | Path                                   | Stack                                                                                                                                                                          |
| ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| New app    | `web/`                                 | **Parked** (2026-10-21): a Next.js 16 / Auth.js / Prisma scaffold with login only, its own database and no features. Not maintained, and not checked by CI, the pre-commit hook or `scripts/check.sh`. Details in `web/CLAUDE.md`. A future rewrite should start from the existing OAuth API (`/api/v1`, `/api/v2`), not from this. |
| Legacy app | `ruqqus/` (+ `scripts/`, `schema.sql`) | Flask 3, SQLAlchemy 2, Jinja templates, Postgres, Redis, Matrix/Synapse chat (`synapse/`). Python 3.11 in Docker.                                                              |

Tooling: Node 22 (`.nvmrc`, for the chat bundle), Python dev tools in `.venv` (`pip install -r requirements-dev.txt`). **Git hooks** (the pre-commit checks and the graph update) are installed with `sh scripts/install_hooks.sh` on a fresh clone; they used to come from `npm install` in `web/`.
Env vars: copy `.env.example` to `.env`; never commit `.env`. (`web/.env.example` is for the parked web app.)
The site's name is `SITE_NAME` (default `Laba`) and the legal entity in the terms, legal pages and footer is `COMPANY_NAME` (defaults to the site's name): templates draw them with `{{ 'SITE_NAME' | app_config }}` / `{{ 'COMPANY_NAME' | app_config }}`, never a written-out name. Addresses such as ruqqus.com in the help pages are still the old ones. The name is never shown all lowercase (the owner's rule, 2026-10): no `| lower` on it in anything a visitor reads (only an address, such as an `@handle` meta tag, may be lowercase), and the logo reads "ɸLaba".

## Terminology (applies to both apps, UI text and code names)

| Say                                                                                                                                 | Never say                                  |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **post**: always created first on the author's own profile. You cannot post to a guild, except inside a Circle guild (see below).    | "post to/in a guild", "submit to a guild"  |
| **comment**: anything that is a reply, whether on a post or on another comment.                                                     | reply, replies, replied                    |
| **forward** (forwarded, forwarding): sharing a post or comment with a guild. A forwarded comment becomes its own post in the guild. | promote, yank, crosspost, "share to guild" |
| **repost**: putting someone's post or comment on your own profile (a different feature from forwarding).                            |                                            |

Guilds only ever receive forwards, so guild settings and errors talk about _forwarding_ (e.g. "Restrict forwarding", "disallows bots from forwarding").
External contracts keep their old names on purpose: the URL `/notifications/replies`, the JSON field `replies`, DB columns such as `restricted_posting` and `promoted_by_id` (Python attributes use the new names), the `/mod/kick/...` URLs, and legacy mod-log kinds (`yank_post`, `kick_post`).
`tests/test_terminology.py` enforces this; extend its allowlist only for a real external contract.

## Word filter (legacy app)

Viewers browse at a level (`User.filter_level`: 0 Off, 1 Standard - the default and what logged-out visitors get, 2 Child). Content is never removed; it is hidden per viewer.

- Posts and comments get a stored rating when written (`word_severity`: 0 clean, 1 profanity, 2 extreme) from `ruqqus/helpers/wordfilter.py` (the matching engine, stdlib only) via `helpers/word_filter_store.py`. Standard hides 2; Child hides 1 and 2 plus anything `is_sensitive`, sensitive guilds and sensitive accounts (never an anonymous item for being one: see Sensitive accounts and All).
- **Every new listing or page must go through `ruqqus/helpers/visibility.py`**: `filter_posts` / `filter_comments` / `filter_boards` / `filter_users` on queries, `post_hidden` / `comment_hidden` / `board_hidden` / `user_hidden` for one object, `hidden_notice(v)` for a direct link. Do not read `hide_offensive` or `is_offensive`.
- Memoized id-lists must include `filter_level=viewer_level(v)` in their arguments (it is the cache key). Caching is off on localhost, so this cannot be noticed in dev.
- Anything that writes a title, body, bio, description, username or guild name must re-stamp it (`apply_post_severity`, `apply_comment_severity`, `apply_user_severity`, `apply_board_severity`).
- The word list lives in `word_filter_entries` and is edited at `/admin/word_filter` (plain words, never regex); an empty table means the built-in list in `helpers/wordfilter_seed.py`. After changing the list, re-scan (admin button or `PYTHONPATH=. python scripts/rescan_word_filter.py`).
- Schema changes: a file in `scripts/migrations/*.sql` (safe to run twice), mirrored in `schema.sql`, whose `schema_migrations` list at the end gains the file's name. `scripts/migrate.py` records what a database has applied (`--status`, `--apply`, `--baseline` once for a database migrated by hand) and the app prints the missing ones at start-up. A one-off data change in a migration runs only while the file isn't recorded (see `2026-11-02_audit_fixes.sql`).

## Linked media storage (legacy app)

Ruqqus keeps no copy of an uploaded picture, sound or video, and **storing media must cost the site nothing**: every file goes into the member's own account on another service, using that service's free allowance (the owner's rule; site-owned buckets and paid video hosts are ruled out). A member links an account once, in `/settings/media` or the first time they add a file; the browser sends the file straight to it and a post only holds a reference. Start with `ruqqus/helpers/media/rules.py` (the rules, no I/O).

- **Two shapes of provider** (`helpers/media/base.py` is the interface). _Served_ (Google Drive `gdrive.py`, OneDrive `onedrive.py`): plain storage that stays private in the member's account; Ruqqus fetches it and shows it at `/media/<id>/<token>.<ext>` (`routes/media.py`). _Hosting_ (YouTube `youtube.py`, Dailymotion `dailymotion.py`, listed in `rules.HOSTED`): the site plays the file itself and the post links to it. `dev.py` is a stand-in served provider for local testing, only with `MEDIA_DEV_PROVIDER=1` (never on a live site).
- **Which service per kind of file**: pictures and audio go to Google Drive (15 GB free) or OneDrive (5 GB free); video to YouTube or Dailymotion (Dailymotion's daily limits are the member's own: 15 videos a day; YouTube's API allows the whole site 100 uploads a day until its audit). Rejected on purpose: Imgur (blocked in the UK since September 2025, embeds included), SoundCloud (registering an app needs a paid Artist Pro account), Vimeo's free plan (1 GB), Dropbox for now (2 GB; it fits the served shape if members ask). `rules.SERVICE_ORDER` / `SERVICE_LABELS` / `PROVIDER_LABELS` / `SERVICE_HINTS` are what the composer and settings say.
- **Connecting from the composer** (`assets/js/media_upload.js`): the file is picked first (the click is what lets the browser open its file dialog), and when no linked account takes that kind yet the status line offers the site's services; the chosen one opens in a **popup** (`connect`, `?popup=1&n=<nonce>`, remembered in the session by `_remember_popup`), and the callback ends with `media_connected.html` (`_finish`), which tells the opener on three channels (BroadcastChannel, a localStorage event, `window.opener.postMessage` to this origin) because a sign-in page in between can cut the popup off (Cross-Origin-Opener-Policy); coming back to the tab also re-asks `/api/media/status`. Only a message from this origin carrying the composer's own `n` counts. The upload then carries on with the same file. A full account (507), a lost one (`need: storage`) or a Google account without YouTube access (`need: video`) is fixed in place and the upload tried again once.
- **Where each kind goes**: the member's choice is `default_for` in the account's `settings` (`_preferred`, `rules.in_order(by_kind, preferred)`), set from the "Change where … go" link under an upload (`POST /api/media/default`) or the settings page (`/settings/media/default`). An upload may name the account (`account` form field) and answers with `to` (where it went).
- **How bytes travel** is the provider's answer to `begin_upload`: one PUT (Drive, YouTube, dev); `chunk` (OneDrive's upload session: PUTs with a `Content-Range` each, 10 MiB, a multiple of 320 KiB); `form_field` + `answer` (Dailymotion: a form POST whose answer, the uploaded file's address, the browser hands back as `answer`; only providers with `wants_answer` get it, and `dailymotion.upload_address_ok` accepts only https addresses on Dailymotion's own upload servers).
- **Never serve Drive files by a Google link.** Google has no supported way to show a Drive file in an `<img>`, a shared file shows its owner's Google name (which would break pseudonymity and anonymous posts), the Drive API terms forbid using Drive as a CDN, and the Cloudflare CSAM scan only covers this site's own addresses.
- **Who sees a file** (`rules.access`): part of a live post or comment: public, `Cache-Control: public, max-age=31536000, immutable`, no session cookie (`g.skip_session_cookie`); not attached yet: its owner only, `no-store`; otherwise refused, so the site is not a free file host. Every place that saves a post's link or text, or a comment's text, calls `media.attach.sync(...)`, commits, then `media.safety.scan_later(...)`. Removing a post or comment calls `media.cdn.purge(...)`.
- **A served file is typed by its first bytes** (`rules.sniff`), sent with our own `Content-Type`, `nosniff` and a sandboxing CSP, and refused when the provider's checksum no longer matches the one recorded at upload (the owner can change the file in their storage). No SVG or HTML type, ever.
- **Uploading** (`assets/js/media_upload.js`): `POST /api/media/uploads` answers where the browser sends the bytes (a provider upload session the server opened; no credential ever reaches a browser), then `POST /api/media/uploads/<id>/complete` checks the file. Pictures are re-drawn in the browser first, which drops EXIF (location); never fall back to the original. A post's own picture travels as the `media` form field (an asset id), text pictures as `![](/media/...)`, sounds as `[audio](/media/...)`, which `helpers/sanitize.py` turns into an `<audio>` player (only for exactly this site's own sound address). No thumbnail is generated for linked media.
- **Microsoft and Dailymotion** go through `helpers/media/oauth.py` (`Service`: state, code exchange, encrypted refresh token, access tokens in Redis, revoke); `microsoft_oauth.py` (scope `Files.ReadWrite.AppFolder`, only the site's own app folder; `MICROSOFT_TENANT` defaults to `consumers`) and `dailymotion_oauth.py` (scope `manage_videos`) are its settings, with `MICROSOFT_CLIENT_ID` / `_SECRET` and `DAILYMOTION_API_KEY` / `_SECRET`; redirects `<site>/settings/media/<name>/callback`. Microsoft hands out a new refresh token with each use: `Service.access_token` writes it onto the account and sets `account._rotated`, and the routes commit it (`_keep_rotated`). A service whose keys are not set is not offered anywhere (`registry.service_configured`). `google_oauth.py` predates the shared module and keeps its own copy (its tests replace its functions).
- **Google** (`google_oauth.py`): needs `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`; redirect `<site>/settings/media/google/callback`. `drive.file` is asked for first (not a sensitive scope: only files this site created). `youtube.upload` is asked for only when a member first adds a video; it is a sensitive scope (Google must verify the app) and the API project must pass YouTube's audit, or YouTube forces every upload private, which is reported as `restricted`. The refresh token is stored encrypted (`secret_box`). `AccountLost` (access taken away at Google) marks the account `error` without writing its files off; `ProviderDown` is temporary and never cached.
- A video from a member's own channel (YouTube or Dailymotion: `rules.video_ref`) shows the channel name, so it is refused on an anonymous post (`media.attach.own_video`) and on a Circle post (`circles.post_refusal`). Drive and OneDrive media show no identity and are allowed.
- **To add a provider**: a module with a `Provider` subclass, an entry in `registry.PROVIDERS` / `ACCOUNT_OF`, its kinds in `rules.PROVIDERS` (and `rules.SERVED` if Ruqqus serves it). Posts, comments and the upload script do not change.
- Not on linked storage: avatars, banners and guild images (still the site's S3 bucket, `helpers/aws.py`), and anything uploaded before. When the site offers no linked storage, the old server-side image upload is what the composers use.
- The Google, YouTube, OneDrive and Dailymotion code is tested with each service's side faked (`tests/test_media_google.py`, `test_media_youtube.py`, `test_media_onedrive.py`, `test_media_dailymotion.py`, `test_media_oauth.py`); **none of it has been run against the real services**. The first things to check with real credentials: the browser's PUT to Google's and OneDrive's upload sessions is allowed across origins, the browser may read Dailymotion's upload answer (CORS), and Dailymotion accepts the `people` channel.
- Tests: `tests/test_media_*.py`.

## Social embeds and quote cards (legacy app)

A post that links to a post elsewhere reads **like a post quoted on X**: the member's own words first (the feed card's title, the post page's text), then a bordered **quote card** in this site's font **at the size of those words** (16px like a feed title, 14px on a phone; 14px / 21px like the post page's text: `.quote-card`, `.quote-card-full`), with who wrote it, @handle, the date, the text, a "Photo or video" line and "View on X". **No page loads a social site's script or widget**, in feeds or on the post page (the owner's choice, 2026-10-15); **a video on a social site plays in that site's plain player frame, loaded only when the reader presses play** (the owner's choice, 2026-10-16: see **Players** below). The rules (pure) are in `ruqqus/helpers/quote_cards.py`, the per-reader part is the Jinja global `quote_of(p, v)` (`helpers/jinja2.py`), and the card is `partials/quote_card.html` (`quote_card(q, p, v, full)`), drawn by `submission_listing.html` in place of the media box and by `submission.html` right under the body, before the community note. ## Group chats (legacy app)

Up to 32 people in one **end-to-end encrypted** Matrix room, made by the site's bot like a 1:1 chat (owner's choice 2026-10-16; 1:1 chats stay in `chat_conversations`, untouched). Rules (pure) in `helpers/chat_groups.py`; SQL in `helpers/chat_group_store.py` (plain `text()`, tested on SQLite); routes in `routes/chat_groups.py`; tables `chat_groups`, `chat_group_members` (migration `2026-10-22_chat_groups.sql`, mirrored in `schema.sql`).

- **Only the bot changes who is in a group** (`matrix_client.group_power_levels`: invite, kick, ban and every state event need 100; members 0 send, react, edit and delete their own). So every change is a route with its rules, a POST with the form key, and the Matrix call goes first: the database is committed only once it went through. **The bot is the room's creator and is not listed in the power levels**: from room version 12 (Synapse 1.162's default) a creator has unlimited power and Synapse refuses one in `users`.
- **Roles**: the owner (who made it), admins the owner names, members. Owner and admins add and remove; an admin never removes the owner or another admin; only the owner names admins. Anyone leaves; when the owner leaves the earliest admin to join, else the earliest member, takes over (`next_owner`), and a group with nobody who joined is closed (`deleted_utc`; its open invitations go with it).
- **Who can be added** (`add_refusal`): never yourself, a bot, a deleted or suspended account, someone in a block with whoever adds them or with **anyone already in the group** (either way: a friend of someone you blocked can't put you two together), or into a full group. A Matrix step that fails part way takes back the invites already done (`_undo`), so the room and the member list never disagree. Adds are logged (`chat_group_adds`) and the daily cap counts the log, so removing and re-adding doesn't reset it. A block is never named: one message, "@x can't be added to a group." Nobody is added unless every typed name can be. 10 new groups and 100 people added a day per account. The people search (`GET /api/chat/people`) offers people you follow and chat with (never blocked, bots, deleted, suspended, word-filtered names).
- **Where an invitation lands**: in at once only when the adder and the added follow each other (`chat_permissions.can_add_to_group_directly`; the route joins them, `join_room_as`), otherwise `invited`, in their **Requests** with "@x added you to this group" and Accept / Delete (the route joins or leaves for them). **All is everything on the site except sensitive content**, and For You, trending and a curation's whole-site pool (`curation_feed.site_pool`) follow it. - **What All leaves out**: sensitive content (`hide_sensitive`, beside `hide_muted` / `hide_fewer`), unless the viewer chose to see it (`users.all_shows_sensitive`, "Show it in All and For You" in Settings > Content; off by default, never for a visitor, never on the Child filter: `shows_sensitive`). - **Not applied** on a guild's own page, a profile, Following, search or a direct link: going there is a choice (the line mutes draw). Trending is one list for everyone, so it counts nothing sensitive (`hide_sensitive(..., None, ...)`).
- **An anonymous post is never judged by whose it is**: `hide_sensitive` and the Child filter (`visibility._not_by_sensitive_account`, `user_hidden(..., account_flag=False)` for an anonymous item) only leave a post out for its author's account when it is not anonymous, or the gap would say which anonymous posts are a sensitive account's. A sensitive account's new posts are marked sensitive when written (`sensitive.marks_post` in `submit_post`, and `edit_post` can't unmark them), anonymous or not, so they leave by their own mark.
- **A sensitive account acts like a sensitive guild**: a "Sensitive content" chip on the profile header (`.profile-x-sensitive` in both stylesheets), its new posts blurred, the whole account hidden for Child-filter viewers (`user_hidden`, `filter_users`, `filter_posts`, `filter_comments`), no ads on its posts or profile (`ads.account_allows`).
- **Who sets it**: the member ("My account is sensitive", `POST /settings/sensitive_account`) and a guild's guildmasters (the existing switch, `mod_bid_settings_sensitive`). **Admins (level 3) can force it** (`POST /admin/sensitive/user`, only below their own level; `POST /admin/sensitive/guild`, written to the guild's public mod log): `sensitive_forced` locks it on, the owner's switch is drawn disabled and refused with a 403 (`sensitive.owner_refusal`), and the account or the guild's guildmasters are told. Unlocking clears the lock only; the owner decides again.
- **Caches**: the viewer's choice and their own account flag drop that viewer's feed caches at once (`muting.clear_cached_feeds`). Other viewers' cached All / For You lists catch up within their 5 to 15 minutes when an account or guild is marked.
- `users.is_nsfw` is an old column nothing reads; it is not this flag.
- Tests: `tests/test_sensitive.py` (the rules and the filter on SQLite, the anonymous promise), `tests/test_sensitive_assets.py`.

## Circles (legacy app)

An account shares a post or a story with **everyone** (Public) or with **some of its circles** (the owner's choice, 2026-10-15). It has three kinds (`circles.kind`): **Friends**, automatic, everyone it follows who follows it back right now (no members are stored: `circle_store.viewer_circle_ids` asks the follows when something is read; its row, kind `friends`, is made the first time it is chosen, `ensure_friends`); **custom** circles it names and fills itself ("Family", "Uni friends in Spain"; 20 at most, 500 people each, `tier` member); **paid** circles people pay coins to be in every 30 days (`tier` subscriber; **making one needs Premium**, `has_premium_no_renew`, 5 at most; one that exists keeps renewing whatever happens to the owner's Premium). A Circle guild's circle is kind `guild` (below). Rules (pure) in `helpers/circles.py`; the database side in `helpers/circle_store.py`; routes in `routes/circles.py`; tables `circles` (`name`, `kind`), `circle_members`, `circle_payments`, `post_circles`, `story_circles` (migrations `2026-10-10_circles.sql` and `2026-10-20_many_circles.sql`, mirrored in `schema.sql`).

- **Who sees what** (`circles.can_see`, `circle_guard.may_see`): Public, everyone; a post or story for circles (audience **4**, its circles in `post_circles` / `story_circles`), its author, admins from level 4 and **anyone in ANY of its circles right now** (a custom circle's active members, a paid circle's subscribers whose paid days are ahead, Friends when the two follow each other). A block either way hides it (and ends the follows and the memberships). An audience nobody knows is seen by nobody but the author (fail closed): the old 1 (Subscribers) and 2 (Close Friends) no longer exist. A post whose circles were all deleted is its author's alone.
- **Nobody is told they were put in a custom circle, and nothing they see names one**: adding someone sends nothing, the post's eye says "Shared with a circle" (`Submission.circle_label`, `circles.viewer_label`), the gate page and a story say the same, `/circles/in` lists only paid circles and Circle guilds, the follow lists never count custom members, and the profile has no "In their Circle" badge any more. The author is told which circles ("Friends and Family": `circles.shared_label`). A paid circle's name is shown to its subscribers and on the owner's profile and gate page (they choose to join it). A paid circle's name in a notification goes through `circles.plain_name` (it is markdown).
- **Only the owner changes their own circles**: an owner's circle is named by the address (`/api/circles/<id>/...`) and checked to be theirs (`_mine` -> `circle_store.owned`; someone else's is a 404); every store function that changes a circle takes the owner's id; a form never names an owner or a circle (`tests/test_circles_assets.py`). The chosen circles of a post or story are resolved with `circle_store.resolve(db, v.id, tokens)` (`friends` or an id of one's own: anyone else's circle is refused like a made-up one). Names are unique per owner ignoring case (`circles_name_key`, and `_name_taken` in Python, since SQLite's `lower()` is ASCII), plain text up to 40 characters (`parse_name`), never "Friends".
- **Paid circles**: subscribing is `POST /api/circles/<id>/subscribe` (the owner comes from the circle), cancelling `/cancel`. **Access is a date, not a job**: a subscriber's access is `renews_utc` (`tier_of`: strictly in the future), so when it passes they are out even if `scripts/renew_circles.py` is late or down. Cancelling keeps access until that date and stops renewals; subscribing again before it just resumes (no charge). **A subscriber renews at the price they signed up at** (`circle_members.price_coins`). Price 0 takes nobody new. A paid circle is deleted only once nobody has paid days left in it, and its `circle_payments` rows stay (`circle_id` becomes NULL; earnings are counted by `owner_id`).
- **Coins move in exactly two statements** (`circle_store._pay`): `UPDATE users SET coin_balance = coin_balance - :c WHERE id = :p AND coin_balance >= :c` (the check and the charge are one statement: a balance can never go negative and two payments cannot spend one coin) and the credit to the owner. The routes `flush()` the member's pending ORM changes first (`has_premium` renews from coins) and `refresh(v)` after, or a stale `coin_balance` would be written back. No refunds, no site fee, 1 to 100 coins per 30 days; the owner's coins land straight on their balance. The store builds no SQL from text (no f-strings) and commits only in `renew_due`.

- **Renewals**: `scripts/renew_circles.py` (own supervisord program `ruqquscircles`, hourly; `PYTHONPATH=. python scripts/renew_circles.py --once` by hand) settles each due subscriber on its own (`renew_due` commits per member; its events carry the circle's name).

Each entry shows **the text the item had when it was deleted**: the owner chose a public log WITH the text, knowing it is a public copy of what people deleted. It reads `content_edit_history` rows with `action = 'delete'` (written by `delete_post_pid` and `delete_comment`; a partial index keeps it quick, migration `2026-10-10_deletion_log.sql`). One row per deleted item: the forwards a deleted post takes down with it write none, so an entry names the guilds the post had been forwarded to.

- **What it never lists**: anything not public to begin with (`Submission.post_public` false: Circle posts and private-guild posts, and the guild must not be private or banned), anything a moderator or admin removed (`is_banned`, `hidden_by_guild`, `purged_utc`), anything an admin obliterated (the `ObliterationRecord` check, and `previous_title` / `previous_body_html` are NULL after the scrub: that scrub stays authoritative), and anything the viewer's word filter hides (`filter_posts` / `filter_comments`; the forwarded-guild names go through `filter_boards`).
- **Anonymous items** show the deleter as Anonymous (`anon_hidden(item, v)`; the name comes from the history row's actor and only when not hidden, never from `.author`) and are left out of a `?user=` list (`anonymity.hide_anonymous`). A new filter that names one author needs the same line.
- **Stored HTML is the only HTML drawn** (`media_free(previous_body_html) | safe`, sanitized when it was written; `without_media` swaps its pictures and sounds for a `[picture]` / `[sound]` marker, since deleting a post detaches its uploads and the addresses would only show broken pictures); the title and link are escaped.
- **It is a paged list, not a feed**: no `#posts` / `.posts`, so `infinite_scroll.js` does not engage; Prev / Next stay.
- `?guild=` and `?user=` of an unknown, banned, private or word-filtered guild or user are one 404 (never confirms a private guild). `filter_comments` has its own subselect on `Submission`, which is why the comment query joins its parent post through `aliased(Submission)`.
- Not covered: mass deletes from "delete my account" write no history rows. Where a guild's moderators hid or removed something is that guild's **Moderation log** (`/+guild/mod/log`, public): it now takes `?show=all|posts|comments|exiles` (`SHOW` in the helper maps each to `ModAction` kinds) and links to `/log/deleted?guild=`. The log is linked from the footer and the account menu.
- Tests: `tests/test_deletion_log.py` (the rules), `tests/test_deletion_log_assets.py`.

## Guild limits (legacy app)

An account may lead at most **5 guilds** and the accounts on one **network** at most **5 between them** (`ruqqus/helpers/guild_limits.py`; it was 10 per account). Both only stop a **new** guild: creating one, accepting a mod invitation, a siege (and the admin siege on someone's behalf); nobody is made to step down and an account over the limit keeps what it has. Site admins (level 3+) are exempt.

- **Two halves, deliberately.** `User.can_join_gms` is the cheap per-person count (`boards_modded` filtered by `is_siegable`) that every page already pays for through `can_make_guild` (the sidebar). The network check is a query, so it is **only** asked where a guild is added, through `User.gm_limit_refusal()` -> `guild_limits.check(g.db, user)`. Never call `check` from a property a page reads.
- **What "on a network" means**: an account's addresses are `users.creation_ip` plus its `login_events.ip` of the last 90 days; the accounts on them are every account that signed up or logged in from one of those addresses in that window; the guilds counted are the distinct guilds those accounts lead (accepted, not rescinded), leaving out banned and deleted accounts (a temporary ban still counts), banned guilds and siege-protected ones.
- **Messages**: to the account itself they name the limit; about another account (an invitation, an admin siege) they only say "@x can't lead another guild right now.", because the reason could be who shares an address. Never name another account or an address.
- **Every new way of creating a `ModRelationship` must ask the limit** (`tests/test_guild_limits_assets.py` counts the five creators and the places that ask). The per-person number in templates is the Jinja global `GUILD_LIMIT_PER_PERSON`.
- **Known risk**: a shared network (school, VPN exit, carrier NAT, a family) can stop a legitimate member from leading a guild. There is no override flag; add one (an admin-set cap on the user) only if it happens. The address is the real client address only as far as the deployment says which proxies to trust (`TRUSTED_PROXY_HOPS`, `TRUST_CF_CONNECTING_IP`: `helpers/client_address.py`).
- Tests: `tests/test_guild_limits.py` (the rules and the real SQL on SQLite), `tests/test_guild_limits_assets.py`.

## Guild channels (legacy app)

Text and announcement channels inside a guild, the first part of making guilds work like Discord servers (the owner's choices, 2026-11: unencrypted and moderated channels in every guild, a removed message's text kept out of the public log, a guild-wide chat mute on the old `chatbans` table). Rules (pure) in `helpers/guild_channels.py`; SQL in `helpers/guild_channel_store.py` (plain `text()`, tested on SQLite); upkeep in `helpers/guild_channel_sync.py` and `helpers/guild_channel_access.py`; routes in `routes/guild_channels.py`; tables `guild_channels`, `guild_channel_reads`, `guild_channel_posts`, `guild_channel_reports` (migration `2026-11-04_guild_channels.sql`, mirrored in `schema.sql`).

- **A channel is a Matrix room made by the bot, and it is not end-to-end encrypted in any guild.** A guild's posts are plain text even in a Circle guild, and encrypted rooms can't be rated, slowed, reported by text or removed by content. Up to `MAX_CHANNELS` (20) a guild, `MAX_MEMBERS` (10,000) in a room. `kind` is `text` or `announcement` and never changes (`voice` is reserved in the CHECK for the voice channels still to come). The room's power levels: members send, react and take back their own; in an announcement room only the people at 50 send (the guildmasters with the content permission who are in it: `guild_channel_store.writer_ids`, set on their first open and again about hourly by the sync step). Stickers and polls are the bot's alone.
- **Every message goes through the site** (`POST /api/guilds/channels/<id>/messages`): who may write, the burst limit (`PER_MINUTE`), the daily count, slow mode (Redis `SET NX EX` per person and channel, guildmasters exempt), the word filter's rating, then `matrix.send_as` with the **signature** `guild_channels.site_mark` over the room, the sender, the rating, a one-time nonce and the text. **A member can still write to the room from their own Matrix client** (Synapse limits a session's own sends, about ten at once and then one every five seconds; `rate_limited: false` is only for the site's own masqueraded sends, which is why the site counts for itself): `routes/chat.py` `_guard_guild_channel` removes any message without a valid signature for its sender or whose nonce was already used (`gc:n:<nonce>` is made by the site, `gc:u:<nonce>` claims it with one set-if-absent, so a copy of someone's signed message, a replay of your own and a lowered rating all fail; the same event delivered again is fine), any reaction that isn't an emoji, and any other event type. Edits are therefore not offered (an edit would be unsigned): delete and write again. Taking your own message back is seen by the webhook and blanks its stored text. Only a valid message moves `last_activity_utc`.
- **Who reads and writes** is a ladder per channel (`read_level`, `write_level`: `members` = joined the guild or approved or a guildmaster, `approved`, `mods`); writing is never looser than reading and an announcement channel is `mods` (content permission). Always required to read: a guild the person may see (`Board.can_view` as `guild_visible`, `board_hidden`), not exiled (`Board.has_ban`; **`subscribe_board` doesn't check exile, so the channel gate does**), not a bot. A suspended account or one muted in the guild can read, not write. **A refusal to read says nothing but "This channel isn't available."** (a 404), except "Join the guild to read its channels." for a member-level channel of a public guild.
- **No row per member.** `guild_channel_reads` has a row only for people who opened a channel, and that row is also who is in its Matrix room (people join by opening it: `POST /api/guilds/channels/<id>/join`, never all at once when a guild is joined, because each join is two blocking Matrix calls). Unread is a count of messages, not a clock (migration `2026-11-06_guild_channels_unread.sql`): a channel counts its messages (`activity_seq`, one UPDATE per message however big the guild, made by the webhook, which also marks the writer as having read it) and a person's row holds the count they last read (`last_read_seq`), so a message sent in the same second as a read is still news; the broadcast channels' counter per member would be a write per member per message.
- **Taking people out**: at once when someone leaves the guild, is exiled or unapproved (`guild_channel_access.remove_from_rooms`, called from `unsubscribe_board`, `mod_ban_bid_user` and `mod_unapprove_bid_user`, best effort inside savepoints), and by the sync step in `scripts/recomputes.py` (`guild_channel_sync.run`, `MAX_KICKS` a cycle) for everything else: a guild that went private or was banned, a channel that was tightened or closed, a deleted or banned account, and anyone who hasn't opened the room for `IDLE_DAYS` (they come back by opening it). `who_should_leave` asks the same `read_refusal` rule as the routes, a thousand people at a time. The sync step also blanks the stored text of messages older than `KEEP_TEXT_DAYS` unless a report is open. Synapse's own message retention (`retention:` in `homeserver.yaml`) is not switched on: turn it on to bound the Synapse database of busy channels.
- **Moderation, with the guild's own flags**: `config` makes, changes, orders and deletes channels (`/+<guild>/mod/channels`, plain forms with the form key, no script); `content` removes messages (`matrix.redact_as_bot`, from the channel's page or a report), works reports and **mutes people in the guild's channels using the old `chatbans` table** (`Board.has_chat_ban` is the same check; the dead `perm_chat` / `public_chat` pages stay gone, and `tests/test_audit_fixes_assets.py` still pins that). Members report a message once each (`guild_channel_reports`, never shown who) and delete their own. **The mod log names the channel and the writer but never the removed message's text** (`channel_message_remove`; the owner chose this over the other logs' public text, 2026-11), beside `channel_create`, `channel_edit`, `channel_delete` and the old `chatban_user` / `unchatban_user`. Channel names, topics and rules are rated together into `word_severity` when saved and on a rescan (`rescan_severities`, called by `word_filter_store.rescan`); a viewer whose filter hides one sees "A channel".
- **Blocks, mutes and the word filter in a shared room**: a block doesn't remove anyone (it would reveal it), exactly as in group chats. `GET /api/guilds/channels/<id>/senders?ids=` answers names only for people who wrote in that channel (`authors_among`: no way to look an account up) and marks whom the viewer blocked ("A message from someone you blocked") or muted (left out); a name their filter hides reads "A member". The client hides a rated message the way a public broadcast channel's is hidden. Anonymity doesn't arise: channels have no anonymous messages.
- **Where it shows**: a guild's **Chat** tab (`guild/chat.html`, `guild_tabs`, `guild_has_chat`: signed-in readers of a guild with channels) draws the channel list and frames `/chat?embed=1&single=1&room=<room>`, the same chat client with its list hidden and its header cut down to its buttons (`.chat-single`); the chat page has a **Guilds** tab (`GET /api/chat/conversations?status=guild`, up to 200 channels of the guilds you are in that you may read; the client asks for it at most every 15 seconds because it is the dearest list). `assets/chat_src/src/guild_channels.js` (names as they appear, the line under the composer), `ui.js` and `index.js` (`gchannel`: no typing or read receipts to a whole channel, no calls, quote through the site, a guildmaster's Remove). Needs a rebuild of the chat bundle (`docker compose build ruqqus`).
- **Part 2 (migration `2026-11-05_guild_channels_polish.sql`)**:
  - **Threads** are Matrix's own (`m.thread`): `POST .../messages` takes `thread=<root event id>`, which must be a live message of the channel that is not itself in a thread (`thread_refusal`, one level deep, as Matrix's are; `guild_channel_posts.thread_event_id`). The client keeps thread messages out of the channel's list, shows "N messages in thread" under the root (the server's aggregated count or the loaded ones) and opens the thread in a panel over the messages (`client.relations` for the older ones). The UI says "thread" and "messages", never the banned word.
  - **Pinned messages**: a guildmaster with the content permission pins (`MAX_PINS` 10, `guild_channel_pins`, `channel_pin` / `channel_unpin` in the mod log); the list is `GET .../pins`, drawn through the viewer's word filter, blocks and mutes. **A pinned message keeps its stored text** (`blank_old_text` skips it); a removed message loses its pin and its mentions.
  - **Categories** (`guild_channel_categories`, up to `MAX_CATEGORIES` 10, named and ordered by config guildmasters; deleting one keeps its channels, `category_id` goes NULL): the Chat tab and the Guilds list group by them, uncategorised first.
  - **@mentions**: `@name` in a message (`parse_mentions`, at most `MAX_MENTIONS` 5 a message) is recorded (`guild_channel_mentions`, a badge on the channel until it is opened) and told as an ordinary notification (`send_notification`, after the message is committed, names stripped of markdown by `circles.plain_name`) **only to people who may read the channel, in no block with the writer, who haven't muted the writer or the channel**; one notification per writer, person and channel an hour (`notice_due`, Redis), the mention itself always counts. There is no @everyone.
  - **A member's own mute of a channel** (`guild_channel_prefs.muted_until`: 1, 8 or 24 hours, or until turned on): no unread dot, nothing in the navbar total, no mention notification. Nobody else is told.
  - **Rules to accept**: a channel with `rules_gate` and rules asks everyone but guildmasters to accept the rules before they can write (`guild_channel_rules_ack` holds the SHA-256 key of the exact text: change the rules and everyone is asked again); reading is not gated. A gate with no rules is refused.
  - **Search** (`GET .../search?q=`, 30 a minute): every word, in this channel, among messages whose text is still kept (**the last 90 days**, `KEEP_TEXT_DAYS`: search reads the same stored text reports use, so blanking it ends search too); a rated message the viewer's filter hides, a removed one and anyone they muted or blocked are left out. Results are read in place; there is no jump to the message.
  - **The navbar's chat badge** adds the channels you have **opened** that have news (a muted one has none) and your unread mentions (`guild_channel_store.unread_total`, one query over `guild_channel_reads`); a channel you never opened doesn't count, so the badge never needs the list of every guild's channels.
- **Voice channels and stage channels (part 3, migration `2026-11-07_guild_voice.sql`)**:
  - **Voice channels** are persistent call rooms to drop in and out of, on the call machinery (`routes/calls.py`, `call_store`, `rtc/mesh.js`, the call window): the channel's `matrix_room_id` is the silent encrypted room Spaces and calls use so browsers learn each other's devices (`create_space_room`); `chat_room` has a third kind, `voice` (`guild_channels.voice_room`), asked again at every join and heartbeat. **Read** says who may see the channel and who is in it, **write** says who may speak. **Audio only, 8 people** (`AUDIO_MAX`: each person uploads one stream per other, always through the relay: the owner's no-media-server rule). No ringing and no `call.started` for the guild; no 4-hour call limit (the room's keys are refreshed on each heartbeat, one person's stay is limited to `VOICE_MAX_SECONDS`, 12 hours); joins are limited to `VOICE_JOINS_PER_HOUR` an account instead of calls started; nothing is written into the room when the last person leaves.
  - **A block keeps two people out of one call** (`voice_blocked`: a join across a block says only "This voice channel isn't available right now.", never who). Leaving the guild, being exiled or muted ends your part within one heartbeat, as in group calls.
  - **A voice room holds only the people in the call**: `voice_enter` puts you in it on joining, `voice_exit` takes you out on leaving, and the sync step takes out anyone in the room but not in the call after `VOICE_GRACE` (the roster is read from Redis: `roster_of`). Whoever may see the channel sees who is in it (`GET /api/calls/status` answers `who`; names and pictures, never an account the viewer is in a block with). The chat client shows a **card** (`renderVoiceCard`: who is in it, a Join button that opens the existing call window) in place of a thread of messages; a voice channel has no messages, pins, threads or search (`_messages_only`).
  - **Stage channels** show a Space: a guildmaster gives the Space's post address (`space_post_id`) and the channel's page and card show whether it is live, coming up or ended, with a link to its own page (`/space/<id>`, which keeps its own rules: a reader who may not open the post sees "No Space is shown on this stage right now"). A stage has no Matrix room (its row holds a `stage:<random>` placeholder, never used) and no readers, so the sync step skips it.
- **Roles (part 4, migration `2026-11-08_guild_roles.sql`)**: rules (pure) in `helpers/guild_roles.py`, SQL in `helpers/guild_role_store.py`, the guildmasters' page `/+<guild>/mod/roles` in `routes/guild_roles.py` (config permission, form key, mod log: `role_create` / `role_edit` / `role_delete` / `role_assign` / `role_unassign`). A role is a name in the **flair palette** (`guild_flair.COLOURS`: a chip beside the writer's name in channels, drawn by the existing `.flair-chip` rules), up to `MAX_ROLES` 20 a guild and `MAX_MEMBERS` 500 people in one, with three permissions: **not slowed by slow mode**, **remove messages** and **pin messages** (in channels the person may read; reports, mutes and channel setup stay with guildmasters). A role may be given only to someone in the guild (joined, approved or a guildmaster), not exiled, not a bot; **leaving the guild or being exiled takes a person's roles** (`remove_from_rooms(..., drop_roles=True)`; unapproving doesn't). Role names are rated by the word filter (a viewer whose filter hides one sees no chip).
  - **What a role says about a channel** is set on the channel (its edit form: for each role, read and write as the channel's own rules / allow / deny; a voice channel's are "see" and "speak"; none on a stage). A person's roles are combined and **allow beats deny** (`guild_roles.resolve`); an allow lets them over the channel's ladder, a deny stops them under it, and allowing writing allows reading. **A role never gets round the absolute refusals** (a guild the person may not see, an exile, a bot, a hidden guild name: `read_refusal` checks them first) and never takes a guildmaster's own access. The viewer's roles come with every channel row (`_STANDING`: `role_allow_read` ... `role_pin`), so a list is still one query; the sync step reads the same overwrites (`overwrites_for_users`), so someone a role let into a guildmasters-only channel isn't taken out of its room, and one a role denies is. An announcement room's writers (power level 50) include the people in a role that may write there, once they are in it.
- **Auto-moderation (part 5, migration `2026-11-09_guild_channels_extras.sql`)**: a guild's own rules for its channels (`guild_chat_settings`, pure rules in `helpers/guild_automod.py`, set on the Channels page by config guildmasters, `automod_settings` in the mod log): an account must be N days old, a person must have been in the guild N days to write and N days to send a link (`member_since`: the earlier of joining and approval), and up to 50 words or phrases matched as whole words in any case. Checked in the message route after the write right and before anything is counted; **guildmasters are never held to it**; a refusal never says which word. It is on top of the site's word filter, which stays on for every reader.
- **Bots feeding an announcement channel**: a config guildmaster links an approved bot account (`status = 'approved'`, a bot's own page says who runs it) to an announcement channel (`guild_channel_feeds`, up to `MAX_FEEDS` 3; a new feed starts **after the bot's latest post**, never its history). `scripts/recomputes.py` runs `helpers/guild_channel_feeds.run` each cycle: at most 3 new public, live, original posts per bot per run and `FEED_PER_DAY` 50 a channel a day, each sent as the bot's own Matrix account (`provision_bot` makes its chat account on the site's books and never adopts an orphan Synapse account) as "<title>\n<link>", **signed, rated and recorded like anyone's message** so the word filter, reports and removals apply; its cursor only moves once a message went, so a Matrix failure retries. A bot in the room is at power level 50 (`writer_ids` includes feed bots in the room; `set_writers`). `channel_feed_add` / `channel_feed_remove` are logged.
- **A Circle guild's channels are the subscriber lounge**: a Circle guild is private for good and its members are approved contributors who pay the founder, so its channels follow the private-guild rule (`guild_visible`: contributors and guildmasters only; leaving or lapsing takes a member out of the rooms, `remove_from_rooms` and the sync step) with no code of their own. A personal paid circle (on a profile) has no chat: that is not built.
- **End-to-end encrypted channels** (`guild_channels.encrypted`, only a text channel of a private or Circle guild, chosen at creation and never changed, `MAX_ENCRYPTED_MEMBERS` 500, everyone who may read it may write in it, no rules to accept: `encrypted_refusal`): the room is megolm-encrypted like a group's and written and read in Chat from the member's own browser (`onSend` skips the site's route; the guild Chat tab says "Open in Chat" instead of framing it, since the frame has no keys). **The site can't read it, so it has no word filter, slow mode, pins, search, reports, threads, @mention notifications or kept text** (`_plaintext_only` refuses them). What the site still does: the room is only for people who may read **and** write (the site can't stop a muted person writing in an encrypted room, so a muted person is not in it: `join` refuses them, mute takes them out, `who_should_leave` puts them out); the webhook (`_guard_encrypted_guild_channel`) keeps it to encrypted messages, emoji reactions and taking back your own, and **removes an encrypted event beyond `PER_MINUTE` from one person** (a second limit on top of Synapse's own per-session one, for a guild's own sake); a guildmaster with the content permission **removes a message by its event id** (`event_sender` asks Matrix whose it was, for the log; the bot redacts it) without ever reading it. Names come from `members_among` (the people in the room). Someone new can't read what was said before they came: their device never had its keys.
- **Not built, on purpose or yet**: video, screen sharing and more than 8 people in a voice channel (it needs a media server), jumping to a search result, @everyone, a chat for a personal paid circle, threads and search in encrypted channels (the site can't read them), the guild's channels in the API's guild JSON, a custom role's own colour beyond the flair palette, Synapse message retention (`retention:` in `homeserver.yaml`; it would bound the Synapse database of busy channels). Deleting an account leaves its row in the rooms until the sync step kicks it (`gone`).

## Shared drafts and collaborative posts (legacy app)

Between Google Docs and Wikipedia (the owner's choices, 2026-10-17): several people write one **shared draft** at the same time, every character is credited to whoever typed (or pasted) it, the draft is published as a **collaborative post** that its authors keep improving, the authors decide together who joins under rules they can change, and anyone can **fork** a public one. A new feature beside co-authored posts (which are unchanged). Rules (pure) in `helpers/collab_rules.py`; the text engine in `helpers/collab_ot.py` (and its browser copy `assets/js/collab_ot.js`, checked against the same vectors, `tests/data/collab_ot_vectors.json`); who typed what in `helpers/collab_authorship.py`; SQL in `helpers/collab_store.py`; routes in `routes/collab.py`; pages `templates/collab/*`; the editor `assets/js/collab_editor.js`. Migration `2026-11-01_collab_posts.sql`, mirrored in `schema.sql`.

- **Live co-editing is server-authoritative OT on plain markdown.** The browser diffs a field before and after each input into one op (keep / insert / delete, lengths in **UTF-16 units**, never splitting an emoji) and sends it with the revision it was made on (`POST /api/collab/<id>/ops`, one request out at a time, a `key` so a resent op is applied once). `collab_store.commit_op` locks the row, brings the op past every op since that revision (`transform`, the incoming op's insert first), applies it to the text and to the authorship runs, and stores it **stamped with the signed-in user** (the browser never names an author). The live topic `collab:<id>` (authors only) carries **the revision number only**; each browser asks `GET …/ops?after=` (author-checked again) and brings those ops past its own waiting edits. A base more than 500 revisions old, or an op that doesn't fit, reloads the draft. Live carets are not built.
- **Who typed what** is runs of `[user_id, length]` per field (`collab_authorship.apply`), so credit is exact and survives other people's edits, leaving and forks. **Drafts are private**: a draft, its ops and its working "who wrote what" (`/collab/<id>/written_by`) are for its current authors only (`_doc_or_404`, a 404 for anyone else). **Once published it is public**: `/post/<id>/written_by` (the text escaped, each stretch tinted from the fixed `.collab-tint-0..7` palette with "Typed by" on hover, shares that add up to 100) and `/post/<id>/revisions` (one per publish, a +/- diff), for whoever may read the post (`live_comments.readable_post`). Keystrokes before publishing never become public.
- **Decisions are proposals** (`collab_proposals`, `collab_votes`): add an author, remove one, change the rules, delete the published post, and publish when the rules say so. **Default rules** (`DEFAULT_RULES`): every counted author agrees; an author not active on the site for 6 months isn't counted (`users.last_active_utc`, stamped at most daily by `wrappers._note_active`, backfilled from sign-ins); any author may publish; a proposal closes undecided after 30 days. The authors can change them to majority or two thirds, another window (a week to 12 months, or never), voting on publishing; **changing the rules always needs every counted author**. `collab_rules.clean_rules` stores only known values. The proposer's yes is recorded; the subject of a removal doesn't vote or count; if only one author counts, they decide alone (the panel says who isn't counted, never when they were last seen). Counted again at every vote, join and leave, and every cycle of `scripts/recomputes.py` (`settle_open_proposals`). A passed add still needs **the invitee to accept** (`/collab/invite/<id>`, 30 days). Never added: a bot, a deleted or suspended account, anyone in a block either way with **any** author ("@x can't be added.", the block never named); at most 50 authors, 20 proposals a day and 3 open at a time per author in a draft. A new proposal is told only to the authors whose vote counts, its outcome only to whoever made or voted on it (the panel shows the rest). Edits (`collab_ops`) are pruned by `helpers/retention.py`: the text and its authorship live on the draft. Anyone may leave; **what they typed stays credited**; a draft with no authors closes (its post stays).
- **Publishing goes through the site's own machinery**: the first time through the real `POST /api/vue/submit` in this process as the publishing author (`_post_as`, the scheduler's way: every posting rule, throttle and ban applies), onto their profile; after that through `posts.apply_post_edit` (the edit itself, moved out of `edit_post` unchanged) with the publisher as the one who edits. Every author's own linked uploads in the text are attached (`media.attach.sync` takes a list of owners; in the draft, a picture shows only to whoever uploaded it until published). The other current authors are the post's **accepted co-authors** (`_sync_coauthors`), so bylines (more than five: "and N others"), profiles and Following work unchanged. **A collaborative post is never edited, deleted or given co-authors directly** (`COLLAB_EDIT_REFUSAL`, `COLLAB_DELETE_REFUSAL`, `coauthors._collab`): deleting it is a proposal, done by `posts.delete_post_as` as the proposer. Collaborative posts are public and never anonymous, for circles or with a poll.
- **Forks** (`/collab/fork/<post>`, signed in, public posts only, 10 a day) copy the latest published revision **with its authorship runs**, so the original typists stay credited ("(from the original)"); the forker is the only author; "Forked from" shows on the post and its revisions. Private ops are never copied.
- Entry points: the **Post | Write with others** tabs above the Create a post card (`partials/composer_modes.html`; not the account menu: the owner wanted shared drafts in the post area) lead to `/collab` (your drafts, invitations, "New shared draft"); `collab/list.html` and `collab/editor.html` extend `submit.html` so they are the same page as Create a post (the card with avatar, large title, post toolbar, attach row, forwarding, "More options", the bottom bar, the rules card); the post menus' `collab_item` / `collab_button` (Who wrote what, Revisions, Open the shared draft, Fork) and the post page's `collab_mark`. Which posts are collaborative is cached per worker for 30 s (`helpers/collab_view.py`).
- **A shared draft carries the post options a regular post has** (the owner: it lacked many): a link, who can comment, content disclosure, sensitive and guilds to forward to, kept as one JSON text in `collab_docs.options` (migration `2026-11-03_collab_options.sql`, mirrored in `schema.sql`; `collab_rules.clean_options` / `check_options` / `post_fields`, `collab_store.options_of` / `set_options`), saved by any author through `POST /api/collab/<id>/options` (the last save wins; `assets/js/collab_options.js`) and carried in `_snapshot` so a publish proposal publishes the options it was asked with. The first publish sends them through the real `/api/vue/submit` (guilds are forwarded then); later publishes pass them to `apply_post_edit` as a `MultiDict` (guilds are not forwarded again). GIF and emoji buttons in the editor insert through `insertAtCaret`, which fires `input`, so the OT engine sees them. **Not offered, on purpose**: circles, anonymous, co-authors, polls, Spaces and live threads. `tests/test_collab.py`, `tests/test_collab_assets.py`.
- Tests: `tests/test_collab_ot.py` (convergence, the JS copy through `node`), `tests/test_collab.py` (authorship, rules, the SQL on SQLite), `tests/test_collab_assets.py`.

## One vote per post across its copies (legacy app)

A forward is an independent copy of a post in a guild (own votes and comments, `repost_id` points at the original). So that one person can't vote on the original and on every copy, a person may hold an **active** vote (`vote_type` 1 or -1) in at most one live member of a post's **family**: the original plus every row whose `repost_id` points at it (forward copies and the legacy pre-Forward resubmits). The original counts as one of the copies; a forwarded comment becomes a new post with no family. Start with `ruqqus/helpers/vote_copies.py`.

- **The vote route asks first**: `api_vote_post` calls `vote_copies.refusal(g.db, v, post, now)` after the removed/deleted/archived refusals and before anything is written, and answers `403 {"error", "voted_in"}` (the message names where the other vote is: "the original post" or "+guild"). **Taking a vote back (`x=0`) is never checked by this rule**, so it frees the person to vote on another copy (the removed / deleted / archived refusals before it still apply to every vote). A refused vote writes and commits nothing.
- **Race-safe without a schema change**: `refusal` first takes `pg_advisory_xact_lock(user, family)`, released by the route's commit, so two simultaneous votes on two copies by one account queue and the second sees the first. A unique index can't be added over the duplicate rows that already exist, which is why the rule lives in the route and not the database.
- **Live members only**: a vote on a removed or deleted copy, or one in a banned guild, doesn't count (it is out of every feed). A vote on an archived copy does (frozen but real; the message then says it can't be changed any more).
- **The post's author is exempt.** They get an automatic upvote on the original and on every forward copy (`_build_standalone_submission(auto_upvote=True)`, deliberately kept) and keep voting on all of them. Their vote is not marked as automatic, which is why the exemption is by author rather than by vote.
- **Votes cast before the rule are left alone.** The rule only refuses to add or change a vote while another active one exists in the family, so someone with votes on several copies can remove any of them but not change one. `PYTHONPATH=. python scripts/report_cross_copy_votes.py` (read-only) counts them, authors apart from everyone else.
- **On the page**: `vote_copies.attach` (in `get_post` and `get_posts`, one query per page) sets `post._voted_elsewhere`; `Submission.voted_elsewhere` is what the templates read. A post the viewer has voted on is never locked (they must be able to change or remove that vote). Locked arrows (`.vote-locked`) carry no `upvote-button` / `data-id-up` markers, so `register_votes` never binds them, and a click shows the message (`voteLocked`). The arrows are **optimistic** (they and the score change before the server answers), so `upvote` / `downvote` take a `snapshotVote` and `post_toast(url, callback, onError)` puts it back when the vote is refused. This applies to comment votes too.
- A new place that creates a **hand** vote on a post must go through `refusal`; `tests/test_vote_copies_assets.py` lists every place that creates one. Alt accounts and comment votes are not covered.
- Tests: `tests/test_vote_copies.py` (the rules and the real SQL on SQLite), `tests/test_votes_copies_route.py` (the route, with the harness's stand-in for the helper; `tests/test_votes.py` is unchanged), `tests/test_vote_copies_assets.py`.

## Polls (legacy app)

A post can carry a poll: the post's title is the question, 2 to 4 options (40 characters each), one vote per member (final, never changed), a length from a fixed list (1 hour, 6 hours, 1 day, 3 days, 7 days). Start with `ruqqus/helpers/polls.py` (the rules, no I/O); `helpers/poll_store.py` is the database side and `routes/polls.py` the vote route.

- **A poll belongs to the PRIMARY post, and every copy votes the same poll.** `polls.post_id` is `primary_post_id(post)` (`repost_id or id`, shared with co-authors and community notes): a guild forward and a repost show, vote and count the one poll, whoever forwarded it. Never copy a poll onto a forward and never look one up by a copy's own id; `POST /api/poll/<pid>/vote` takes any copy's id and resolves it. A forwarded comment becomes a new post and has no poll.
- **Creating**: the composers send `poll_option` (repeated) and `poll_hours`. `submit_post` checks them before the `Submission` exists (400, like co-authors) and makes the poll right after the post and before any forward copies it. The field is the `post_options.poll_field` macro, used by Create a post (a page of its own: it loads `poll_composer.js` itself), the feed composer and the Create post panel; a closed panel's fields are disabled so they send nothing. Drafts keep an unfinished poll (`poll_options` / `poll_hours` in the draft's options) and scheduling needs a whole one (`require_poll`); a scheduled post's length counts from when it is published. A poll is not editable after posting.
- **The word filter counts the options**, or a profane option would be a way round it: `apply_post_severity` / `post_severity` take `extra=` (plain text) and every place that rates a post passes the options: `submit_post` (twice), `create_forward_post` (from the primary's poll), `edit_post`, and the re-scan loop. A new place that rates a post must do the same (`tests/test_polls_assets.py` checks every call).
- **Voting** needs a login (`@is_not_banned`), the form key, a post the caller may see (`post_hidden`, `board.can_view`, not removed or deleted) and a live primary post, before the poll closes and before the caller's own vote (the unique `(poll_id, user_id)` settles a race with a 409). The author may vote. With `back` (the plain form) it redirects to the post; otherwise it answers with the re-drawn poll as `html`, which `assets/js/poll.js` swaps in (it parses it, never `innerHTML`, and stops the click reaching the card's stretched link).
- **Counts are shown to** whoever has voted, the author, and everyone once the poll has ended; a visitor on a running poll sees login links. The counts (and `total`) are `null`, in the page data and in `post.json`'s `poll`, whenever they are not shown. **Nobody is ever shown who voted for what**: only the viewer's own vote (`mine`) is marked.
- **A page of posts gets its polls in a few queries**: `poll_store.attach` at the end of `get_posts`; a post loaded another way is looked up on first use (`poll_of` in templates). The poll is drawn by `partials/poll.html` (`poll_block(p, v)`) under the body and community note of a card and of a post page.
- Tests: `tests/test_polls.py` (the rules), `tests/test_polls_assets.py` (schema, vote guards, primary resolution, word filter sites, drafts, composers, templates, both stylesheets).

## Tips (legacy app)

A tip moves coins from the tipper to the author (`gift_post_pid` / `gift_comment_pid` in `routes/paypal.py`) and is **seen on the post** as the total coins tipped (the coin in the post's action row, `partials/post_actions.html`, on the feed card and the post page; comments show theirs with a `.tip-badge`). Tips are anonymous: nothing shows who tipped. Rules in `ruqqus/helpers/tips.py`, SQL in `helpers/tips_store.py` (tested on SQLite).

- **Every tip is one `award_relationships` row with its `coins`** (the old one-per-person constraints are gone; rows from before 2026-10-13 count as 1 coin). A post keeps `tip_coins` (every coin, what it shows) and `tip_boost` (what counts for ranking), worked out again by `tips_store.recompute_post` on each tip.
- **The boost is ranking only**: `rank_hot` and `rank_best` (Postgres functions) add `tip_boost` to `upvotes - downvotes`, so tips lift a post in Hot, Best, For You and curations (`curation_feed.mix_score` counts it with votes). **Never in `score()`, `score_top`, the Top sort or the number shown on a post**: that stays an honest vote count. A new place that ranks by votes must decide about `tip_boost` (`tests/test_tips_assets.py`).
- **A bot's post takes tips** (the owner, 2026-10-20: coins can lift a bot's post). Whoever gets the coins is `tips.recipient_id`: a **member bot**'s go to the member who runs it (`bot_owner_id`, who is told, "your bot's post"), a **site bot**'s to nobody (`coins.spend` alone: spent, only the lift, nobody told). For a member bot the owner stands in for the author in the boost rules (`tips.answerable_id`, `tips_store.answerable_for`): the owner's own tips and their second accounts' never lift it (the coins come back), and the owner gets no coin in the action row on their bot's posts (`v.id != author_of(p, v).bot_owner_id`) and a 403 from the route. A refused or gone owner (deleted, banned, in a block with the tipper) is "This bot can't take tips right now." A bot's comment never takes one (`gift_comment_pid` still refuses: bots don't comment).
- **Per person**: each tipper whose tips count adds `min(20, 10 + 2 × floor(log2(their coins on the post)))` upvotes' worth. Tips count only from accounts at least 30 days old, not banned or deleted, not the author, and **sharing no address with the author** (`guild_limits.addresses_of`), or a second account would be a free boost (the coins come back). The coins move either way. A forward copy's tips lift that copy; the coins go to the original author.
- **The routes**: coins are read with `tips.parse_coins` (1 to 1,000, a 400 otherwise); the coins, the tip row, the post's totals and its stored `score_hot` / `score_best` are one transaction, committed **before** `send_notification` (which commits on its own). "Tip" is the coin in the action row (never on one's own, an anonymous, a removed or a deleted post, or one whose author's account is deleted; elsewhere the count shows but does nothing).
- After changing the rules, `PYTHONPATH=. python scripts/recompute_tip_boost.py --once`. Migration `2026-10-13_tips.sql`.
- Tests: `tests/test_tips.py`, `tests/test_tips_store.py`, `tests/test_tips_assets.py`.

## Feed filters: Post type and the Advanced filter (legacy app)

Beside Regional / Language / Categorical, the left sidebar's Filters has **Post type** (a dropdown of ticks) and **Advanced filter** last (a popup modelled on X's Advanced search). Both narrow **All, For You and Following only** (never a guild page, a profile, search or the API's listings) and live in the session (`feed_post_types`, `feed_filter`) like the other three. Rules (pure) in `helpers/feed_filters.py`, conditions in `helpers/feed_filter_sql.py`, routes `GET /post_type?types=` and `GET /feed_filter` (`?clear=1`) in `routes/front.py`, which save and go back to `base_feed`.

- **Post type** is `POST_TYPES`, the one list (key, label, group): text, links, pictures, videos, sounds, polls; forwarded to guilds, for circles; co-authored, collaborative, anonymous; live / upcoming Spaces and Space recordings. Ticked types are OR'd. A new type needs its entry there and its condition in `type_condition`, nothing else. A guild copy is the post it copies (its poll, Space, co-authors through `coalesce(nullif(repost_id, 0), id)`); collaborative posts are not "co-authored" though their authors are co-authors; a Space recording is `record` with a `replay_asset_id` (the Spaces area's own rule).
- **The Advanced filter is search**: its fields are written as search operators (`query_text`) and parsed by `search_query.parse`, names looked up with `search_filters.resolve` **one at a time** (`prepare`): a name the viewer may not see, or that doesn't exist, is left out with the same notice either way ("No guild called +x. It is left out of the filter."). `from:` keeps search's anonymity rule. Any of these words and Mentioning have no operator and are kept beside the query.
- **One card per post**: a feed hides a guild copy behind its original (`feed_family`), so `in:+guild` / `in:#topic` also match a post with a live copy there (`_guild_condition`). **A copy in a private or banned guild never makes its public original match** "Forwarded to guilds" or a topic (it would hint the guild exists; the share counts follow the same rule); a guild the viewer named themselves counts.
- **Only narrows**: `feed_filter_sql.apply` runs after each feed's own visibility rules, in `frontlist`, `User.idlist` and `User.for_you_idlist`, which take `feed_filter=` (a frozen `FeedFilter`, part of the memoize key) and join `SubmissionAux` **once** for it and the word filter. A filtered feed has no site-wide pinned post.
- **The session is a cookie that also holds the sign-in**: a cookie over 4 KB is dropped and signs the member out, so the limits are small (`MAX_WORDS`, `MAX_NAMES`, `PHRASE_CHARS`) and `compact` stores only the fields that are set.
- **UI**: the sidebar rows and rail icons (`openSidebarFilter('post_type' | 'advanced')`; the Advanced filter is a popup at every width), `_sidebar_filter_macros.post_type_body` (grouped rows with `data-keep-order`, so ticking doesn't re-sort them), `post_type_filter_modal.html` (phone sheet), `partials/advanced_filter_modal.html` (a plain GET form refilled from `feed_filter_form`), the phone pills and the notices in `home.html`.
- **Default filters** (members only, `users.feed_defaults`, JSON): "Save as my default" at the end of the sidebar's Filters (and in the Advanced filter sheet's footer on phones) stores all five filters as the session has them (`POST /settings/feed_defaults`, form key, `action=save|reset|clear`). `_apply_saved_defaults(v)` copies them into the session **once per session** (`feed_defaults_for`), from `_resolve_active_filters` and `_stored_feed_filters`; after that the sidebar's changes last for the session only, until "Reset to my default". `feed_filters.read_defaults` checks every part again on the way in (regions against `REGION_CENTROIDS`, languages, categories against `ALL_SUBCAT_IDS`, `parse_types`, `compact`); unreadable JSON is no default. The sidebar line says "Your default", or offers Reset / Forget (`feed_defaults_state`).
- Tests: `tests/test_feed_filters.py` (rules, the SQL on SQLite, `prepare`), `tests/test_feed_filters_assets.py`. The `~*` mention match runs only on Postgres.

## Bells (legacy app)

Finer than following (the owner's choice, 2026-10-20). Rules and SQL in `helpers/bell.py` (tested on SQLite), the table `bell_rings` (migration `2026-11-12_defaults_descriptions_bells.sql`, pruned after 90 days by `helpers/retention.py`).

- **An account's bell** (`follows.get_notifs`, turned on beside "Following"; unfollowing deletes the follow and so the bell): you are told when the account **posts** (`submit_post`, as before, at most `MAX_RINGS` followers), **forwards** a post or a comment to an open guild, **reposts** a post or a comment, **goes live in a Space**, or **shares a story**. A Space's post rings as a new post when it is made, so scheduling one is that ring. Never for the account's own anonymous post or comment; a story for circles reaches only its circles (`circle_store.eligible_ids`), a Space only people who may read its post and were not already told by a reminder or a post follow (`_followers_who_may_read`), a forward or repost only of something anyone may open (never into or from a private or Circle guild).
- **A guild's bell** (`subscriptions.get_notifs`) rings **only for its guildmasters' announcements**: a post they herald (`mod_distinguish_post`, when turned on), a post they pin (`mod_toggle_post_pin`), a new event (`guild_event_create`). It no longer rings for every post in the guild (`submit_post` has no guild ring). A private or Circle guild rings only its approved members and guildmasters.
- **Who is rung** (`account_ring_ids`, `guild_ring_ids`): never the actor, anyone in a block with them either way, a deleted or suspended account, someone who muted the account or (guild) muted the guild or is exiled from it; a private or nofollow account rings nobody. At most `MAX_RINGS` (1,000) a thing.
- **One thing rings once** (`claim`: `bell_rings` UNIQUE (actor, kind, target); a guild's rings use the guild's id): heralding or pinning a post again, or a toggle off and on, never rings twice.
- **A notice names who did it and links to it, never a title or text** (`account_notice`, `guild_notice`): the page it opens applies every rule. It is one system message with a notification row per person (`alerts.send_to_many`, one commit), sent from `ring_account` / `ring_guild` **after the route's own commit**, best effort (a failure is logged and rolled back; the action stands).
- Tests: `tests/test_bell.py`, `tests/test_guild_mute_assets.py`.

## Addresses of posts and comments (legacy app)

An item's address reads as an extension of whoever owns it, with **no title slug** (it changed with every edit of the title) (the owner, 2026-10-20). `ruqqus/helpers/permalinks.py` (pure) builds and reads them; `Submission.permalink` / `Comment.permalink` use it.

| Item | Address | Anonymous |
| --- | --- | --- |
| A post on a profile | `/@alice/post/<id>` | `/post/<id>` |
| A guild copy | `/+pets/@carol/post/<id>`: the guild owns its comments, carol forwarded it (`comment_forwarded_by`, `forwarded_by`, else the author) | `/+pets/post/<id>` |
| A comment | `/@bob/comment/<id>`, the comment's own author (the page shows it in its post's thread) | `/comment/<id>` |

- **An anonymous item never carries a name, whoever looks**, and an anonymous copy never its forwarder either (naming other forwarders only would mark the author's own copies).
- **The name is decoration**: the id decides what is shown. One page per kind answers every address an item has ever had (`post_base36id_with_comments` in `routes/posts.py`, `post_pid_comment_cid` in `routes/comments.py`: the new forms, the old `/post/<id>/<slug>`, `/+guild/post/<id>/<slug>`, `/post/<pid>/<slug>/<cid>` and the short links), and anything but the item's own address gets a 301 to it (`canonical_redirect`, query kept) **only after the page's own checks** (Circle gate, private guild, hidden, banned guild): a redirect names the author, so it must never answer for something the reader may not open. For an anonymous item it is the same whatever name was typed. The API paths are never redirected.
- **Every reader of an address uses `permalinks.parse`** (quote cards, `get_from_permalink`, `links_to_post`, the chat card's matcher in `ui.js`), so the old forms in stored text keep working. A mention is only the bare `/@name` (the mention scanners and the word filter's `_NAME_LINK`): a link to someone's post names nobody and its words are rated.
- A notice that must not name a Space's host links to `/space/<id>`, never to its post's address. `tests/test_permalinks.py`.

## Prefixes: + @ # & (legacy app)

The same four symbols mean the same thing in the search box, in post / comment / bio / description text, in `in:` and `from:`, and in typed lists (the owner's choice, 2026-10).

| Symbol | Names | In the search box | In text | In `in:` |
| --- | --- | --- | --- | --- |
| `+` | a guild | guilds (`+pets`) | link to the guild | `in:+pets` |
| `@` | an account | accounts | link, and a notification | `from:@alice` |
| `#` | a **topic**: a site category or subcategory | the guilds in the topics whose name holds the text | link to `/topic/<slug>` (Explore, filtered) | `in:#gaming`: posts in those guilds |
| `&` | a **public curation** | public curations by name or slug | link (a private one only for its owner) | `in:&news`: the curation's guilds and its accounts' non-anonymous posts |

- **A topic** (`helpers/topics.py`, pure; `get_topic` in `helpers/get.py`): the slug is the name in lowercase letters and digits (`Film & TV` is `filmtv`); a category, a subcategory and a same-named subcategory elsewhere are one topic (`#news`, `#filmtv`). Invisible and NSFW categories, subcategory 0 ("Uncategorized") and 108 (`UNLISTED_SUBCAT`, left out of every guild list) are never topics. **`#word` is a link only when a topic exists**, so ordinary hashtags stay text (`TopicMention` in `helpers/markdown.py`, `\w{2,25}` so `#pc` and `#qa` work). `CATEGORIES` is loaded once at start-up without a session: never read `SubCategory.visible` from it (`topics.shown` is the same rule with the category at hand).
- **Search box** (`routes/search.py`): the first character picks the search; `#` and `&` no longer fall through to the post search (quote them to search the words). `#` lists guilds through `listable_boards` (the one rule for who may be shown a guild in a list: word filter, banned only for admins, Circle guilds only for members; `+` uses it too). `&` lists **public** curations only, never a private one (its owner included), leaves out those whose owner is deleted or banned, and applies the word filter as names are drawn (curations keep no rating: `profile_about.shown_curations`). Cards are `partials/explore.html` `curation_card` / `board_listing.html`.
- **`in:`** (`search_query` / `search_filters`): the prefix of the value picks the scope; `Part.refs` holds a topic's subcategory ids and `Part.ref` a curation's id; unknown or private names are the usual "no such..." notice (`NO_TOPIC`, `NO_CURATION`), never a hint that a private curation exists. A curation matches through `curation_feed.member_condition`, which never matches an anonymous post through its author.
- **Typed lists**: the Categorical lists (sidebar, phone sheet, curation form) accept `#gaming` / `#filmtv` (`filterSidebarList`). Typed guild-name fields keep `+` (they name guilds).
- Tests: `tests/test_topics.py`, `tests/test_search_query.py`, `tests/test_search_filters.py`.

## Search (legacy app)

The post search takes words, `"phrases"`, `-words` and operators: `from:@user`, `in:+guild`, `since:` / `until:` / `after:` / `before:` / `on:` (UTC days; `before:` and `after:` leave the day out), `has:link|image|video|audio|poll`, `lang:en` (or `lang:english`), `domain:`, `url:`, `is:forward|ai|partnership`, `min_votes:`, `min_comments:`; most take a minus. Words match the title **and** the text. Start with `ruqqus/helpers/search_query.py` (the rules, no I/O).

- **`OPERATORS` is the one list.** The help page (`/help/search`, `templates/help/search.html`) is drawn from it. A new operator needs its entry there and its condition in `helpers/search_filters.py` (`_condition`), nothing else.
- **Who may see what stays in `routes/search.py`'s `searchlisting`**, after `search_filters.apply`: word filter, mutes (skipped only for a positive `from:`: `Query.for_one_author`), deleted and removed, `post_public` / mod / contributor, blocks, banned guilds, `BoardBlock`, `filter_level` in the memoize key. The query runs under `curation_feed.limited` (5 s); a slow one shows `TOO_SLOW`.
- **Anonymity**: `from:@x` uses `anonymity.hide_anonymous`; `-from:@x` leaves out only x's **non-anonymous** posts, or `cats` against `cats -from:@x` would show which anonymous posts x wrote. `from:` matches the original author only (not co-authors).
- **A name the viewer may not see reads as one that does not exist** (`find_account`, `find_guild`: deleted, private, suspended, word-filtered, blocked either way; private, Circle, banned or word-filtered guilds): one notice, `NO_ACCOUNT` / `NO_GUILD`. A search with a problem shows the notices and does not run.
- `Query` is frozen and made of tuples: it is the cache key. Positive word matches keep the columns bare so the trigram indexes answer them (`submissions_body_trgm_idx`, migration `2026-10-11_search_body_index.sql`, `CONCURRENTLY`, outside a transaction); negations coalesce. The results page shows a chip per operator with a remove link and an **Advanced search** form (`form_fields` / `compose`, sent back as `adv=1`), on both `/search` and `/+guild/search`.
- **Comment search** (`?type=comments`, the **Posts | Comments** switch on `/search` and `/+guild/search`; `helpers/search_comments.py`, `comment_searchlisting` in `routes/search.py`, `search_comments.html`): the same text and operators, over `comments_aux.body` (the column `comment_body_trgm_idx` covers). Operators that describe a comment are kept (`from:`, `in:` = where its post sits, the dates, `min_votes:`, `is:ai`, `is:partnership`); `has:`, `lang:`, `domain:`, `url:`, `flair:`, `is:forward`, `min_comments:` are dropped with a notice. A search must hold a word of at least 3 letters, a phrase, or a positive `from:` / `in:` (`search_comments.problem`), runs under the same 5 s `limited()` guard and is memoized with `filter_level` in the key. **Who may see what is the site's comment-list rule** (`comment_idlist`) plus the post search's: the word filter, mutes (not on a positive `from:`), blocks of the comment's author **and** its post's, removed and deleted comments and posts, banned guilds, a guild the viewer muted, and posts that aren't public (a non-public post, such as one for Circles, is found only by its author, the guild's mods and contributors). A system message (no post) is never found. Anonymity as in the post search: `from:@x` never finds x's anonymous comments, `-from:@x` leaves out only the non-anonymous ones, so the two can't be compared to tell which were x's. Each page of ids is loaded with `get_comments` and **a comment whose ancestor the viewer's filter hides, or whose post they may not open, is dropped afterwards** (`comments_for`), so a page can come up short. Sorts: Top, New, Old. `tests/test_search_comments.py`, `tests/pg/test_comment_search.py`.
- Not built: `OR`, region in search, operators in guild (`+`) or account (`@`) search.
- Tests: `tests/test_search_query.py` (the rules), `tests/test_search_filters.py` (the conditions on SQLite, with the anonymity promise), `tests/test_search_assets.py`.

## Curation algorithms (legacy app)

A curation can have its own algorithm: which posts it shows and in what order (`curations.algorithm`, JSON). Start with `ruqqus/helpers/feed_algorithm.py` (the rules, stdlib only).

- **Members never write code, patterns or SQL.** A spec is only ever made by `feed_algorithm.clean` (fixed names, bounded numbers, plain words) and stored with `feed_algorithm.dump`; read it with `curation.algorithm_spec`. `helpers/curation_feed.py` turns a spec into the query: words become LIKE text with their wildcards escaped (`like_pattern`), sites are checked host names. A new option needs: the name in `feed_algorithm` (`DEFAULT`, `clean`, `from_form`, `describe`), its condition in `curation_feed.apply`, and the field in `templates/curations/algorithm_form.html`.
- **What a spec holds**: source (`members`: the curation's guilds and accounts; `site`: every public post as All, with an age limit of a month or less), words a post must / must not mention (title and text), kinds of post, sites linked to, minimum votes / comments, age, things left out (bots, made with AI, paid partnership, forwarded copies), **accounts and guilds left out** (`exclude_users`, `exclude_guilds`, below), and the order: Hot, New, Top, Most discussed or the member's own mix (`MIX`: weights for votes and comments, how fast posts fade, boosts, at most N posts per author or guild on a page).
- **Who may see what is not the algorithm's business**: `_curation_ids` in `routes/curations.py` applies the word filter, private guilds and blocks before `curation_feed.apply`, for every curation. An account's anonymous posts never match through the account (`curation_feed.member_condition`), and the "per author" limit treats every anonymous post as nobody's (`feed_algorithm.spread`).
- **Leaving accounts and guilds out of ONE curation** ("Leave out these accounts / guilds" in the algorithm form; the curation's own list, **never the owner's mute list** (`usermutes`, `BoardBlock`), which is a separate thing that follows the owner): up to `MAX_EXCLUDED` (50) of each, stored as **ids** inside the algorithm JSON (a name can change hands; no table, no migration; `feed_algorithm._ids`). The route turns typed names into ids (`_left_out_ids` in `routes/curations.py`, through `search_filters.find_account` / `find_guild`, so a name the owner may not see is "No account called @x." and never confirms a private or Circle guild; an account the owner blocked is still theirs to leave out) and hands `from_form` the ids; the form shows names back (`_left_out_names`). `curation_feed.leave_out` applies it inside `apply` (every curation) and `drop_left_out` to what an outside feed server named: guilds by `board_id`, accounts through `muting.exclude_authors`, the rule under a member's mutes: **an anonymous post of an excluded account stays** (dropping only those would tell the owner which ones it wrote), a post co-authored with it goes, and its forward copies go in every guild (a copy keeps the original `author_id`). Where the account is also a member, the exclusion wins. **The public text counts only** ("Leaves out posts from 2 accounts and 1 guild.": `left_out_line`): names would expose private or Circle guilds, word-filtered names and a statement about a person. **A fork gets the rules, not the list** (`without_left_out`). It is plain filtering, so it still makes the spec non-default (the curation then uses its own `rank`, like a words-only one). `tests/test_curation_exclusions.py`.
- **Rules of one's own run under a 3 second limit** inside a savepoint (`curation_feed.limited`); a slow one shows a notice (`FeedTooSlow`), never a hung page. An own mix ranks the newest 1,000 matching posts (`MIX_POOL`).
- **Everyone who can see a curation can read its rules**: `feed_algorithm.describe` is shown on the curation page ("How this curation picks posts"). A fork copies the algorithm and the filters (not the leave-out list, which `describe` only counts). Creating a curation offers "Start from" (`PRESETS`) and lands on the edit page; the form saves without script, `assets/js/curation_algorithm.js` adds the starting points and the live preview (`/&<slug>/preview_algorithm`, which saves nothing).
- A sort the viewer asks for (`?sort=`) wins over the curation's order; a curation with no algorithm of its own behaves as before.
- **Outside feed servers** (mode `server`, as Bluesky's custom feeds; `helpers/feed_server.py`): the curation names a server that answers `GET <address>?limit=100[&cursor=...]` with `{"posts": ["<post id>", ...], "cursor": "..."}` (documented for members at `/help/feed_servers`).
  - **The server only orders.** `_server_ids` puts every id it names through `_viewable` (the same rules as any feed) before `get_posts`; a sort in the address does not apply.
  - **Nothing about the viewer is sent**, ever: `feed_server.ids_for` takes no viewer, and one list is kept for everyone in Redis (120 s; 500 posts at most; three failures in a row pause a server for 10 minutes and its last good list is shown; 30 requests a minute per host for the whole site).
  - **Every fetch of a member's address goes through `helpers/safe_fetch.py`** (bot feeds too: `helpers/feed_fetch.py` calls its `check_url`, `vetted_address` and `_Pinned` at every hop) and nothing else: https only, the usual port, no credentials, every address the name resolves to must be public, the connection goes to the address that was checked, no redirects, 3 seconds, 64 KB. A new feature that fetches an address a member typed must use it too. **A link a member posts** (the title suggestion `/submit/title`, the link preview in `thumbs.py`) is read through `helpers/page_fetch.py`: the same guard at every redirect hop (at most 3), an http:// address read as https://, the body read only for the kinds asked for (2 MB of a page, 8 MB of a picture), 10 seconds in all. The older fetchers in `embed.py` (oEmbed and the social sites' own pages) still use plain `requests` (bug hunt 2026-10: their hosts are fixed lists, so not member-chosen; moving them is planned).
  - `FEED_SERVER_ALLOW_LOCAL=1` lifts that guard for a test server on the local machine (set in `docker-compose.yml`; never on a live site). `FEED_SERVERS_ENABLED=0` switches the feature off. An admin (level 4) can take a curation off its server from its page; the page always says, uncollapsed, that an outside server ranks it.

## Bot accounts (legacy app)

A **bot** is an account that posts by itself, approved by an admin (level 3) at **`/admin/bots`**. **Two kinds of bot account** (`bots.kind`, `bots.KIND_LABELS`; a third kind, `SELF`, is a member's own account posting automatically: below), by the owner's rule: a **site bot** costs nothing to run (it reads free feeds, at least one: `bots.kind_refusal`), is proposed by anyone and, once approved, **belongs to nobody**: `owner_id` and `users.bot_owner_id` are NULL, the admins run it and its profile says "Automated by <site>". A **member bot** needs its member to run it (a bot key for their own script, e.g. for X, or a paid source), stays theirs, may also read approved feeds and says "Automated by @owner". Rules (pure) in `ruqqus/helpers/bots.py`; SQL in `helpers/bot_store.py` (plain `text()`, tested on SQLite with tables built from `schema.sql`); routes in `routes/bot_accounts.py`; tables `bots` (with `kind`, `proposed_by_id`), `bot_sources`, `bot_seen` and `users.is_bot` / `users.bot_owner_id` (migrations `2026-10-15_bots.sql` and `2026-10-16_site_bots.sql`, mirrored in `schema.sql`). For members: `/help/bots`, drawn from the limits (Jinja global `bot_rules`).

- **Proposing** (Settings > Bots, `settings_bots_apply`): a member in good standing (30 days old, not suspended; `bots.owner_refusal`) proposes up to 3 at a time (`active_count`: their member bots not rejected plus their site-bot proposals still waiting); admins are held to neither the age nor the count, and may tick **Approve it now** (that is how admins make site bots). A proposal carries the kind, the name, what it posts (for the admins), a plain-text bio (no links), a **profile picture and a banner** (opened with PIL and checked: PNG, JPEG, GIF or WebP, 8 MB, `_image`; stored in the site's S3 bucket like a member's avatar, `User.set_profile` / `set_banner`, then the CSAM check with the proposer answerable), feeds and guilds. `proposed_by_id` is kept for the admins and to tell the proposer of the decision; it is never shown.
- **Who may change a bot is `bots.may_manage`** (`_manageable` in the routes, anything else a 404): an admin, any bot that is not rejected; a member, their own member bot, and a site bot they proposed **only while it waits**. Before approval an admin may also **rename** it (`admin_bot_rename`) and **change its kind** (`admin_bot_kind`: a site bot needs a feed; a member bot's owner is its proposer); both are refused once it was decided. Pictures, banner, bio, feeds and guilds are edited on the bot's page by whoever may manage it. Whoever is told of a decision is `bots.responsible_id` (the owner, or the proposer of a site bot); after approval a site bot has nobody to tell (pauses, failing feeds and admin decisions notify only member-bot owners).
- **A bot account is a `users` row made when the bot is proposed** (it reserves the name; the sign-up name rule), with `is_bot`, `bot_owner_id` (member bots only), `tos_agreed_utc` and a password hash that never verifies (`UNUSABLE_PASSWORD = "!"`). **Nobody logs into a bot**: `login_post` refuses it like a wrong password, so it is never anyone's alt (`check_for_alts` only runs at login) and the spam guard's "ban every alt" can't reach its owner. Until it is approved its profile is a 404 except to its owner or proposer and admins (`User.bot_shown_to`); a rejected or withdrawn bot's account is deleted (it never posted) and a rejected `bots` row keeps the name and the admin's note.
- **Its profile says who runs it** (`partials/profile_header.html`, `User.bot_kind`, `User.bot_owner`): "Automated by <site>" for a site bot, "Automated by @owner" for a member bot, with the robot icon; no Chat button. Every bot post carries `is_bot` (stamped from the account in `submit_post`, not only from the header), so the viewer setting **Hide bot content** (`hide_bot`) and trending's bot filter cover them.
- **One rule decides whether a bot may post**: `submit_post` asks `_bot_refusal` -> `bots.post_refusal` for every bot account, whichever way the post comes: approved (not pending, rejected or paused), for a member bot an owner who is not suspended or deleted, `BOTS_ENABLED` on, under `DAILY_CAP` (40) posts today (`bot_store.count_post` after each post). It answers 403 with `bot_refusal: "wait"` (the cap, the switch) or `"stop"`; the options a bot may never use are refused with a 400 (`option_refusal`: anonymous, a Circle audience, co-authors). Posts are public, on the bot's profile, forwarded to the bot's chosen guilds under each guild's rules (`disallowbots` now also reads the account, and is no longer case-sensitive). The posting throttle applies as to anyone.
- **Never, by account and not only by header**: comment (`api_comment`), vote (`routes/votes.py`), chat (`/api/chat/start` refuses a bot either way), share in the creator fund (`_ELIGIBLE`), or lead a guild (`User.can_join_gms` is false and `gm_limit_refusal` answers "person", which covers every way of making a `ModRelationship`). Moderation is unchanged: report, remove, ban the bot (`User.ban`), mute or block it.
- **Feeds are its sources** (`bot_sources`, at most 5): RSS 2.0, RSS 1.0, Atom and JSON Feed. Each item becomes a **link post: its title and its link, nothing copied from the page**; an item with no title (Bluesky, Mastodon) takes the start of its text. The posted link drops its tracking parameters (`bots.clean_link`: `utm_*`, the BBC's `at_*`, click ids; `ref`, `si`, `feature` stay), but the item's key is made from the link as the feed gives it, so items seen before keep their keys. A source the bot was proposed with is approved with it; **one a member adds later waits for an admin** (`pending_sources`), one an admin adds is approved at once (`add_source(approved_by=)`); removing one is immediate. Pause and resume; **a bot an admin paused is resumed by an admin only** (`paused_by_admin`).
- **Fetching**: `helpers/feed_fetch.py` through `safe_fetch`'s guard (`check_url`, `vetted_address`, `_Pinned`) at **every** hop, at most 3 redirects, conditional GET (ETag / Last-Modified, a 304 costs nothing), 2 MB, 10 s, never this site's own host (`bots.own_host`). `safe_fetch.py` itself still follows no redirects (pinned). `FEED_SERVER_ALLOW_LOCAL=1` also lets a local test feed be read. **Parsing**: `helpers/feed_items.py`, pure, with **`defusedxml`** (entity declarations and anything external are refused: no expansion bombs, no XXE); up to 100 items, an http(s) link required, titles cleaned and cut to 280 (`bots.clean_title`).
- **The runner**: `scripts/run_bots.py` (supervisord `ruqqusbots`, every 60 s; `PYTHONPATH=. python scripts/run_bots.py --once` by hand) claims due sources (`bot_store.claim_due`, `FOR UPDATE OF s SKIP LOCKED`, a 5-minute lease) and hands each to `helpers/bot_runner.run_source` (Flask-free, tested with stand-ins). **The first read of a source marks its backlog seen and posts only its newest 3** (`FIRST_READ`); after that new items go oldest first, at most 3 a run (`PER_RUN`). An unseen item dated more than 2 days back (`bots.is_stale`, `STALE_AFTER`; undated items never are) is marked seen and never posted: the promos a feed keeps (the BBC's "Sign up now") and old stories put back. Each post goes through the real `POST /api/vue/submit`, in-process, as the bot (a one-off session), with `X-User-Type: Bot`, `no_repost=1` and **the bot's own loopback address** (`bots.loopback_for`: unique per bot, never 127.0.0.1), so bots never share the posting throttle's per-address bucket and never share an address with a member (`guild_limits.addresses_of`). What an answer means is `bot_runner.classify`: posted, duplicate (seen), wait (429/503/the cap: tried again), guild (posted again without forwarding, the reason recorded), refused (seen, the reason recorded), stop (suspended, not approved: the bot is paused and a member bot's owner told). Only a member bot asks for its owner's standing. **Each feed is read as often as it safely can be** (`bots.next_interval`, not a fixed time): never more often than `FLOOR_MINUTES` (5), nor than the feed asks (`feed_asks`: RSS `<ttl>`, `sy:updatePeriod` / `sy:updateFrequency`, kept in `bot_sources.asked_minutes` because a 304 has no body) or its server asks (`server_asks`: `Cache-Control: max-age`, `Expires`); a read with nothing new stretches the wait by half up to `QUIET_MAX_MINUTES` (60), and the first read with something new goes back to the shortest. The BBC's feed says `<ttl>15</ttl>`, so it is read every 15 minutes. `check_minutes` is the current interval and the bot's page says it (`cadence_label`). A 429 or 503 with `Retry-After` is waited for exactly (`retry_wait`, a day at most); other failed reads back off (doubling, a day at most); after 10 in a row the source pauses. Reading more often never posts more: the per-read and daily caps are unchanged. Migration `2026-10-19_feed_intervals.sql`. Seen items are kept 90 days. **Never copy `submit_post`'s logic into the runner.** `BOTS_ENABLED=0` stops it all (`.env.example`, `docker-compose.yml`).
- **Pages**: Settings > Bots (`/settings/bots`: "Your bots", "Site bots you proposed" and the proposal form, which reads each feed once to check it is one) and `/settings/bots/<name>` (`settings_bot.html`: the admins' panel with rename, kind, approve and reject while it waits; picture and banner; feeds with their state and last error, add / remove / start again, approve / reject for an admin; keys; bio and guilds; pause / resume; **Withdraw** a waiting proposal, or switch off for good: the account is deactivated and its posts stay). Every change is a POST with the form key. Admin > Bots (`/admin/bots`, linked from the admin page with a waiting count, `bots_waiting`): proposals with their kind and an **Open and edit** link, a live **Check the feed now** (`?check=<source>`), approve or reject with a note, feeds added later, running and paused bots with pause (with a reason) / resume, and **Make a site bot**. Decisions taken on a bot's page come back to it (`next=page`).
- **Bot keys** (member bots only; for X and any owner-run script; `/help/bots#keys`): **X has no feeds and its terms forbid scraping, so the site never reads X**; the owner's own script, with the owner's own X access, posts each tweet's link (drawn as X's own embed) through a key. A key is a `ClientAuth` for the bot account through one of the owner's **own** apps (`author_id == v.id`, Settings > Apps), made on the bot's page by its owner once it is approved (`_is_owner`: a member bot whose `owner_id` is the caller; admins may revoke but never create), at most `MAX_KEYS` (2): scopes identity, read, create, update, delete (`KEY_SCOPES`: never vote or guildmaster), a refresh token shown once (`no-store`), no code. The script uses the documented `POST /oauth/grant` (`grant_type=refresh`) for an hour's access token and posts with `/api/v1/submit`, which is `submit_post`, so every bot rule above applies. Revoking deletes the grant; switching the bot off deletes its keys. A member bot needs no feeds for this. Deleting or editing an app is its author's alone (`delete_oauth_app` / `edit_oauth_app` were open to anyone signed in; `tests/test_oauth_apps_assets.py`).
- **Several bots and feeds per member**: up to `MAX_BOTS` (3) bot accounts, each reading up to `MAX_SOURCES` (5) feeds, plus the automated posting of their own account (below), which never counts against the 3.
- **A member's own account can post automatically too** (the owner, 2026-10-21; a third kind, `SELF`, "Own account", migration `2026-11-21_self_automation.sql`): a `bots` row whose `user_id` **is the member's own account** (`owner_id` and `proposed_by_id` the same). The member keeps using the account as themselves (it is not `users.is_bot`: they comment, vote, chat and lead guilds as always), and the runner posts their approved feeds' items **as them**, through the same `submit()` (a session made in-process, never a sign-in: no history row, no new-sign-in email) with the bot header. Set up in Settings > Bots, "Post automatically from your own account" (`POST /settings/bots/automate`, `bots.self_refusal`: one per account, 30 days, good standing; a rejected one is replaced); an admin approves it and every later feed, as for a bot. **Which posts are automated** is `bots.is_automated`: a bot account's every post, and a header post from an account with a SELF row (`posts._automation`); those get the bot rules (`_bot_refusal` with the member as owner, `option_refusal`, the `DAILY_CAP` count, which the member's own posts never touch), `submissions.is_bot` (the robot mark, Hide bot content, trending's exclusion) and no creator fund points (`creator_fund_store`: votes on and comments on an automated post earn nothing; the member's own words under it do). A header post from any other account is only marked, as before. **The spam guard is split** (`submit_post`): an automated post is compared with automated posts only, skips the link-similarity check (one feed's links share a site; the runner never posts an item twice) and is **refused with a 409** (the runner marks the item seen) instead of suspending anyone; a person's own posts, when their account also posts automatically, are compared with their own posts only and still trip the ban as before. This also stops a feed bot account being suspended by its own feed's similar links. **A SELF row's account is a person's**: switching it off (`settings_bot_delete`) or a rejection removes only the row and its feeds (`forget_bot`), never the account, its posts or its own apps' grants; rename and kind changes find no bot account (`is_bot=True`) and no bot becomes SELF; the picture, banner, bio, display name and key routes 404 for it (`_not_self`), and its page shows only feeds, guilds, pause and "Stop posting automatically". A username change renames its row (`bot_store.rename`), account deletion ends it (`account_cleanup`), the data export lists it. Its profile shows "Some posts are automated" (`automates(u)`, an approved, running row), linking to `/help/bots#own-account`.

## Call relay and live updates (legacy app)

The ground under calls, group calls and Spaces (the owner's choices, 2026-10-16): **no media server**. Audio and video go browser to browser, and **every** connection goes through the site's own TURN relay (coturn, open source) so members never learn each other's IP addresses. **Calls** and **Spaces** stand on it.

- **Microphone and camera only on a call's or a Space's own page** (`/call/<room>`, `/space/<id>`): `helpers/device_access.py` gives `__main__.after_request` its `Permissions-Policy` (the older `Feature-Policy` was dropped: it listed features browsers don't know); every other page, `/chat` and its side panel included, says no. A call runs in a window of its own because the site reloads on every page, and a frame never gets more than the page around it allows, so do not "fix" this by allowing the side panel frame.
- **The relay** (`coturn` in `docker-compose.yml`, pinned; `coturn/turnserver.conf.template`): browsers get one-hour credentials from Synapse (`turn_uris`, `turn_shared_secret_path`, `turn_allow_guests: false` in `synapse/homeserver.yaml`), made from a secret coturn shares. `scripts/gen_dev_env.py` writes `TURN_SHARED_SECRET` to `.env` and renders `coturn/turnserver.conf` and `synapse/turn_shared_secret` (untracked, LF line endings: coturn would read a CR as part of the secret). It **relays to no address but its own** (every address is `denied-peer-ip`; `--allowed-peer-ip=$(hostname -i)`, added by compose, and on a live site `allowed-peer-ip=<public ip>`), where two members' relayed connections meet: since every member's connection is relayed, nothing else is needed, and the relay can't be used as a free proxy. compose refuses to start coturn without its rendered config. Only port 3478 is published; the relay ports and its metrics stay on the compose network. Per-credential and server-wide quotas and 1.5 Mbps per allocation. UDP relay only (`no-tcp-relay`).
- **It reveals the server's address** (the owner accepted this): TURN's UDP ports can't go through Cloudflare. On a live site the relay gets a DNS-only hostname (`turn.<site>`), the origin's firewall must accept 80/443 **from Cloudflare's addresses only**, and coturn runs with the host's network, `external-ip`, TLS on 5349 and a `turns:` URI (the template's header lists it all). This repo can't enforce the firewall: check it before calls are switched on.
- **It must cost nothing**: `TURN_MONTHLY_GB` is what the relay may send in a month. `scripts/turn_usage.py` (`ruqqusturn`, every 5 min) reads coturn's own counters (`TURN_METRICS_URL`: bytes sent to clients and to peers; they restart at 0 with coturn, `turn_usage.advance`) into `turn_usage` (one row per month, migration `2026-10-21_turn_usage.sql`). `helpers/turn_usage.py` is the rule the call and Space routes will ask (`turn_usage_store.call_state`): video off from 80%, nothing starts from 100% until the 1st ("Calls are paused until 1 November."). **It fails closed**: no allowance, or no reading for 30 minutes (the job is down), is paused. The job imports the app before `requests` (gevent patches ssl first).
- **Live updates** (`GET /api/live/events`, `routes/live_events.py`; rules in `helpers/live_bus.py`): one Server-Sent Events stream per tab, for whatever must show at once (an incoming call, who is in a call or a Space, live comments). Publish with `live_bus.publish_to_user(r, user_id, kind, data)` or to a topic (`topic_channel("space:12")`); each gevent worker holds one Redis pattern subscription and hands events to its open streams. **A topic is closed until it has a guard** (`live_bus.register_topic(prefix, guard)`, asked when a stream opens); a member's own channel needs none. An event carries only what its publisher put in it, so never publish something a listener of that channel may not see. **The stream never touches the database** (no `g.db`, no `stream_with_context`: the request's session is closed as usual while it streams), keeps alive every 25 s (under Cloudflare's 100 s), ends after 10 minutes (the browser reconnects), keeps 50 events for a slow tab (oldest dropped), and allows 6 streams per member per worker (a 7th ends the member's oldest, which is almost always a page already left; the browser reconnects with backoff and closes its stream on `pagehide`). **A guard is asked when a stream opens**, so wherever access to a topic ends call `live_bus.revoke(r, user_id, topic)` (removed from a draft, a Space, a group's call): the hub takes the topic off that member's open streams at once. Flask-Compress must never be given `text/event-stream`.

## Chat encryption (legacy app)

- **Two locked copies** in `chat_identities` (`key_blob_password`, `key_blob_recovery`, `key_salt`): the sign-in and sign-up forms (`data-chat-prekey`, `assets/js/chat_key.js`) derive a pre-key from the password in the browser (PBKDF2) and leave it in `localStorage` (`uqqus_chat_prekey`) for the chat page, which unlocks the recovery key with it and then deletes it: a new device needs nothing typed. Declining a request leaves and closes its room.

The user directory is off, a profile is readable only by people who share a room with it, and members can't set a chat name or picture (`enable_set_displayname: false`): **the chat name is the @handle**, set by the bot through the module's own address (`POST /_synapse/client/uqqus/display_name`, appservice token only, site accounts only, no control or direction characters; `matrix_client.set_display_name`, `helpers/chat_devices.sync_name`), "Deleted account" once deleted, the site's name for the bot; `PYTHONPATH=. python scripts/sync_chat_names.py --once` names everyone (after deploying or restoring). **A new chat feature that makes a room, invites, names a room, sends state, uploads or sends a call event must do it through the bot** (`matrix_client`, `_as_headers()`, never `?user_id=`): the browser would be refused. `tests/test_synapse_rules.py` (the rules without Synapse, the config, and a tripwire on the client's calls).

## Account security (legacy app)

- **Other sign-ins end when a credential changes** (`helpers/account_sessions.end_other_sessions`): a sign-in is a cookie holding the account's `login_nonce`, refused once the account's is higher (`wrappers.get_logged_in_user`), and form keys are made from it too. It is raised by a new password, two-factor switched on or off, a password reset by email (whose token holds the nonce, so **the reset link works once**) and "log out all other devices". The browser that made the change takes the new number into its cookie and stays signed in. A new place that changes a credential calls it.
- **Signing in from another site's page is refused** (login CSRF; `helpers/same_origin.py`, the top of `login_post`): a POST to `/login` whose `Origin` is another host (or `null`) or whose `Sec-Fetch-Site` is `cross-site` is a 403. A request with neither header (an app, a script, the tests) is let through; it isn't this attack. `?redirect=` / the form's `redirect` only ever leads to a path on this site (`helpers/redirects.same_site`).
- **Two-factor** (`User.mfa_secret`): an authenticator code is accepted **once** (`helpers/totp.py`: `matched_step`, `claim` in Redis `totp:<user>:<step>` for about two minutes); every route uses `User.accept_2fa`, never `validate_2fa` (`tests/test_mfa_backup_assets.py` fails on one). Two-factor already on **is not replaced** by "password + a code from a new device" (turn it off first). **Backup codes** (`mfa_backup_codes`, rules `helpers/mfa_backup.py`, SQL `helpers/mfa_backup_store.py`, migration `2026-11-15_mfa_backup_codes.sql`): ten one-time codes of ten characters (no 0/O/1/I), shown **once** when two-factor is switched on or when made again (Settings > Security > Backup codes: password and a current authenticator code; every earlier code, used or not, stops working), kept only as a salted SHA-256, spent with one conditional UPDATE. A backup code signs in **without turning two-factor off**. The older derived recovery code (`User.mfa_removal_code`, which does turn it off) works only for an account that has never made codes (`legacy_code_allowed`). Turning two-factor off deletes the codes. The table has no foreign key to `users` (the project's rule); `account_cleanup` removes the rows and the data export gives only a count. No "too many wrong codes" lock exists beyond the sign-in throttle (`throttle_check_ip`).
- **Sign-in history** (Settings > Security > Recent sign-ins, `helpers/sign_in_history.py`): the last ten sign-ins of the account: time, country (Cloudflare's `cf_country`; "Tor network" for T1) and a browser label (`helpers/user_agents.py`: a fixed list, "Chrome on Windows", never the raw header). `login_events.user_agent` (migration `2026-11-16_login_user_agent.sql`) is written at sign-in and sign-up. **The address is never selected for the page.** Retention (`helpers/retention.py`): the address and browser text are erased after **90 days** (what the address checks read, `guild_limits.WINDOW`), the row after **410 days**: **not sooner than 400**, because `helpers/regions.py` reads a year of country and region to decide whether an account has moved (`tests/test_sign_in_history.py` pins the two together).
- **New-sign-in emails** (`helpers/signin_alerts.py`, `templates/email/new_signin.html`, `users.signin_alerts` default on, migration `2026-11-17_signin_alerts.sql`): an account with a **verified email** is emailed when a sign-in comes from a country, or a browser and system, it has not used in 90 days; never for its first sign-in, at most one a day (Redis `signin_alert:<user>`), worked out BEFORE the sign-in is recorded and sent after it by a greenlet that cannot stop the sign-in. Sign-ins from before the browser text was kept judge the country only. The email names the browser, country and time, never the address. Turning the setting off needs the password. A new thing sent by email must not carry an address or say anything about a password.
- **Email** (`ruqqus/mail/mail.py`): `MAILGUN_KEY` (no key: nothing is sent and nothing crashes), `MAILGUN_DOMAIN` (default `mail.<the site's address>`), `MAIL_FROM` (default `<SITE_NAME> <noreply@domain>`); requests time out after 15 s; `send_mail_quietly` never raises. The layout `email/default.html` links to this site, not to ruqqus.com.
- **Block lists** (`helpers/blocklist.py`; `GET /settings/blocks/export`, `POST /settings/blocks/import`, both 5 a day): `block_account` is **the one routine** behind the Block button and the import (not yourself, not the site's account (id 1), not a deleted one, `on_block_created`, `circle_store.end_between`, follows ended both ways); `tests/test_circles_assets.py` pins that it is the only place a `UserBlock` is made. The file is `kind,username` (`block` or `mute`); a plain list of names is blocks. At most 200 names, 30,000 characters. **The report is counts only** and a name that doesn't exist, can't be blocked (you, the site's account, a deleted account) or could not be a username all read as "not found". The result travels in the address as four numbers only, so a link can never put text on the page.
- **A page drawn for a visitor passes `v=None`** (`tests/test_audit_fixes_assets.py::test_every_page_is_drawn_with_a_viewer` scans every `render_template`): the layout reads `v.has_premium`, and Jinja raises on an attribute of an undefined name but not of None. The password-reset success page crashed on this until 2026-10-21.
- Tests: `tests/test_mfa_backup.py`, `tests/test_mfa_backup_assets.py`, `tests/test_user_agents.py`, `tests/test_sign_in_history.py`, `tests/test_signin_alerts.py`, `tests/test_blocklist.py`, and on the real app `tests/pg/test_account_security.py`, `tests/pg/test_blocklist.py` (the pg fixtures clear leftover throttle, sign-in-alert and TOTP keys from Redis once per session, and use random addresses: Redis outlives a database made again and ids start over).

Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
