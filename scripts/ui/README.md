# UI checks (legacy app)

Screenshots and an accessibility pass of the running site, for checking UI work before and after a change.
Dev-only: nothing here is loaded by the site.

1. Run the site (`docker compose up`) against a **scratch** database, never real data, and fill it:
   `PYTHONPATH=. python scripts/seed_ui_fixtures.py` (inside the container; it refuses any database not named
   `ui_preview`, `ci_*` or `test*`). It writes `.fixtures.json` here with the ids of the posts below.
2. `npm install` here (the browsers come from Playwright's cache: `npx playwright install chromium` if missing).
3. `SHOTS_LABEL=before npm run shots`, make the change, `SHOTS_LABEL=after npm run shots`, and compare
   `shots/before/<page>/<width>-<theme>.png` with `shots/after/...` (390, 768, 1280 and 1440px, light and dark).
4. `SHOTS_LABEL=after npm run axe` writes the serious and critical axe findings to `reports/axe-after.json`.

`SHOTS_ONLY=all,post-thread` and `SHOTS_WIDTHS=390,1280` narrow a run while iterating. `UI_BASE_URL` points it somewhere other than http://localhost. The pages are listed in `pages.ts`.

**Languages** (`i18n.spec.ts`): `I18N_LABEL=before npm run i18n` switches every ready language (a visitor with the footer
switcher, the signed-in viewer through Settings > Content), checks `<html lang dir>`, and measures every piece of text
on the pages above at 390 and 1280px against the English render: cut off, wrapping where English took one line,
sticking out of its box, much wider than in English, and the page scrolling sideways. It writes
`reports/i18n-<label>/<lang>.json`; `PYTHONPATH=. ../../.venv/bin/python i18n_summary.py <label>` (from the repo root:
`scripts/ui/i18n_summary.py`) lists the labels behind them and their catalogue entries. `I18N_LANGS=fr,de`,
`I18N_PAGES=all,profile` and `I18N_WIDTHS=390` narrow a run. It sets the viewer back to English at the end.

**The light language** (`light.spec.ts`, `npm run light`): measures, in real pixels, that the light never lowers text's contrast (a message you sent must stay AA at the top, middle and bottom of a scrolled thread, and is darker toward the bottom), that a primary button is a flat fill whose hover and press only darken it, that a new message glints once and nothing runs on a clock on load, and that `prefers-reduced-motion`, forced colours and `prefers-contrast: more` switch the effects off. axe cannot see an overlay, so this is the check for it.

**Glass** (`glass.spec.ts`, `npm run glass`): measures in a real browser that the blur is real (stripes behind a dialog's card come out flat, and show when the blur is taken off), that no ancestor of a glass card is a backdrop root at any frame of an open, that a feed card's menu is glass and on top of the next card, that every glass surface is solid and unblurred under reduced transparency (set through the DevTools protocol: Playwright has no option), more contrast and forced colours, that the sensitive-content cover works from the keyboard, and that Block asks in the frosted sheet, makes no request until told to, can be undone and leaves no dialog, backdrop or scroll lock behind. It unblocks the fixture account it uses even if it fails.

**Sizing and spacing** (`sizing.spec.ts`, `npm run sizing`): measures what CSS can only claim, because 36px in a rule can still render 35.6 or 38. The bar is 56px (52 in Compact) with 36px controls, 14px glyphs on a 36px pitch and a 32px avatar; the account menu is 264px wide with 36px rows, a 56px profile row and 8px of inset, scrolls itself in a short window, and grows with the largest Text size without cutting anything off; on a touch screen it is a top sheet attached to the bar with 44px rows and the page dimmed under it. Also under a finger: the phone's sort bar stays clear of the feed's tabs, a visitor's bar is the same 56px, round icon buttons stay round, the editor's toolbar stays one row and an anchor styled as a button centres its label. Nothing scrolls sideways at 390px and the small text links have a 24px target.

**Shells** (`shells.spec.ts`, `npm run shells`): one page per page shell (the feeds, settings and Create post and a guild's mod page, help and legal, About and Donate), at 1280 and 390px, must show the same 56px fixed glass bar with the mark, Noto Sans, a flat button and no sideways scroll; the member shells' icon rows are the same 36px targets on a 36px pitch starting at the same place; the help bar's phone menu opens into 36px rows and closes; and the docs photo leans blue, not the old purple. Add a page here when a new shell is made.

**The type scale** (`type_scale.spec.ts`, `npm run typescale`; CLAUDE.md "Type scale"): every visible piece of text on 26 member pages is on a step of the scale (12 / 13 / 14 / 15 / 18 / 22px at the 14px root) or in the documented exceptions (the heading ladder above 22px, `code`, badges, the logo), at the default and at Extra large text; the right sidebar's box titles are the left sidebar's small label, and the top bar is still 56px. A page with a size on no step lists it with its element and text. It needs `scripts/ui/seed_sidebar.py` for the curation page it opens.

**The left sidebar** (`sidebar.spec.ts`, `npm run sidebar`; CLAUDE.md "The left sidebar's state and rhythm"): measures in a real browser that rows are 40px and 2px apart (44 under a finger), headings 28px with 8px to the first row and 16px between sections, every label starts at one x, a list stops at five rows with one "See all", the selected feed is a light shade of the site's blue with the 3px bar kept, its label in the blue (as a narrowing filter's is) and all unchanged on hover, and a filter that is narrowing the feed has the wash and a 34px ring in the site's blue that is centred (read from the pixels at 4x) and shows on the page and on the wash (2.5 / 2.2:1 in light, the site colour's exception for graphics, 3:1 in dark), with nothing moving; the filter panels' search boxes are 32px under the 40px row, and a category heading is a row's own font in bold with its subcategories one tick step in beneath it and its state label on a line under its name; it is only on the three feeds, a tick not yet applied marks nothing, and it holds on the rail, in forced colours, in Compact, at Extra large text and right to left. It needs `scripts/ui/seed_sidebar.py` (`ui_sidebar`: 40 guilds, curations with a very long and an Arabic name) as well as the fixtures, and the dev site's `I18N_PSEUDO=1` for the right-to-left run (`ui_lang=ar-XB`, as a visitor: a member's own language wins over the cookie). It sets its filters through the context's request API, never by navigating, because a page's sub-requests race the session cookie.

**The public Log** (`log.spec.ts`, `npm run log`; CLAUDE.md "The Log"): run `PYTHONPATH=. python scripts/ui/seed_log.py` in the container first (a guildmaster's hide, an admin's removal, an exile, an account ban and a guild change, each marked `ui-log-demo`, and a private guild's hide that must not appear; `--remove` takes them out). It checks, as a visitor at 390 and 1280px in both themes, that a hide shows who, where, the rule and the reason and never the post's title, that the private guild's decision is not on the page, that the tabs and the filter fields are targets of at least 24px, that nothing scrolls sideways, and axe (the white label on the site's own button fill is the owner's accepted exception); then that a signed-in member reads the same page, `/log/deleted` lands on it, and a guild the reader can't see answers 404. It also opens `/@ui_carol/log` (the log of one account: the exile, no title, no private guild) at both widths in both themes, and an account that isn't there has no log.

**Overlaps** (`overlap.spec.ts`, `npm run overlap`; CLAUDE.md "Sizing and spacing"): visits the same 26 member pages as the type scale (`pages.ts` `SITE_PATHS`) and reads every box's real rectangle, then fails on two sibling boxes (not floated or positioned) that intersect by more than 1px, on a control closer than 4px to a box of another kind in the same column, and on an opened sidebar filter panel whose last control is closer than 6px to the next row. It also opens what only exists opened: the four filter panels in the left sidebar (from 992px) or the phone's filter sheets, Create post's `<details>`, and the account menu. Boxes are as laid out: clipped to scrolling or `overflow: hidden` ancestors, a negative-margin hit area netted out, closed `<details>` skipped, absolutely positioned and fixed subtrees skipped, labels and hints that sit close to their field on purpose exempt. A finding that is meant goes in `ALLOWED` with the reason (the vote stack, the feed composer's title under its pill row, "Show more" links, the phone guild banner's bell under Leave); text outside its box, a box outside the viewport and sideways scroll are printed, not failing. The default run is five setups (390 touch, 768, 1280 light, 1280 dark, 1280 at Extra large text) and takes about 10 minutes; `OVERLAP_FULL=1` is 390 / 768 / 1280 / 1440 in light and dark at both text sizes (about 30 minutes), `OVERLAP_REPORT=1` prints every finding that is not in `ALLOWED` and fails nothing. The page's rate limit answers a burst with a bare page, so a visit retries (3 s, 6 s...). Run it after any change to spacing, size or layout tokens; mutation-check a new rule by taking its fix out (the Apply button's `margin-bottom: .5rem` in `_nav.scss` is what the spec first caught).

**The Edit profile pop-up** (`profile_edit.spec.ts`, `npm run profile-edit`; CLAUDE.md "Profile header"): in a real browser, the button and the "⋯" item open the pop-up without leaving the profile and give the focus back; Save is off until something differs from what it opened with; closing with changes (Esc, the X) asks "Discard changes?" inside the pop-up and Keep editing keeps them; one Save sends exactly one request and the profile reads every change after the reload (with the "Saved" toast), and the spec puts the profile back; a refusal is told beside its field with `aria-invalid` and the focus on it, and changes nothing; every account has both camera buttons (no Rep is asked for a picture any more); a phone gets a sheet from the bottom with 44px targets; with no script the button is still the link to Settings; axe finds nothing serious in the open pop-up in light and dark. The upload cases need `ui_profile_edit`: run `PYTHONPATH=. python scripts/ui/seed_profile_edit.py` in the container first (the `User` model stamps "now" as `created_utc`, so the seed writes the age that gives the right to pictures). **The dev site has no storage bucket, so a picture cannot be stored there**: those cases hold the failure to what was promised (the old picture stays, the text still saves, the pop-up says which part failed); the success path is `tests/pg/test_profile_edit.py` with storage faked. It signs in through the real form twice (limited to 6 a minute), so leave a minute between full runs, and **the route is limited to 20 saves an hour per account** (a run spends about 7 of `ui_viewer`'s): after several runs, a 429 shows as "Too many saves" and the refusal case fails; clear the limiter's keys with `docker exec ruqqus-redis-1 sh -c "redis-cli --scan --pattern '*settings_profile_edit_post*' | xargs -r redis-cli del"`. The spec writes to `ui_viewer` and puts it back in a `finally`: a crash mid-run leaves it changed. `seed_profile_edit.py --remove` takes the upload account out again.

**The money page** (`money.spec.ts`, `npm run money`; CLAUDE.md "Coins and money"): `/admin/money` as `ui_traffic_admin` (run `scripts/ui/seed_traffic.py` in the container first), in each of the ad status's three states, at 390 and 1280px in both themes: twelve figures, none reading None, no sideways scroll, nothing off the screen, no id in the page, the link to AdSense there (never followed), nothing serious from axe. Shots go to `shots/money/`.

**Video consent** (`consent.spec.ts`, `npm run consent`; CLAUDE.md "Video consent"): run `scripts/ui/seed_consent.py` in the container first (the fixtures have no players; it writes `.fixtures_consent.json`, which with `scripts/` bind-mounted is already beside the spec). On a visitor's first load and scroll it records every request to another host, every cookie and every storage key against its lists, and fails on anything else, on any player frame before a press or an Allow, and on a banner that shifts anything, covers or sits under the phone's bottom bar, or runs off the screen: at 390 and 1280px, light and dark, left to right and right to left. Nothing goes to `POST /consent/video` before the reader answers; once they do, the spec holds the answer to arriving through that route and replacing what the script wrote (a browser clock 30 days slow tells which of the two wrote the cookie), to a failed request being silent, to a later answer not being overtaken, and to another site's form being refused. Chromium has no seven-day cap, so the cap itself is not what this shows. It also holds what the banner offers (a press loads one player, Allow, Not now, taking it back, what the reopened banner says), the back button (a page really out of the back-forward cache, in the full Chromium: `npx playwright install chromium` gives it, and these tests fail unless `pageshow` said `persisted`), the line in the shortest boxes at the largest text, a thumbnail as the disclosed gap, who is asked (`CF-IPCountry` is sent to try countries; the dev site sends none, which means asked), every Cookie choices link, a Space's replay and a story's video. Player addresses are answered by the spec, never fetched, and the ad tag is a stand-in put into the page, because automated loads of the real one are invalid traffic: that it waits for Google's message is checked against the stand-in only. Screenshots go to `shots/consent/`.

**Ads** (`ads.spec.ts`, `npm run ads`; CLAUDE.md "Ads"): needs a second copy of the site with a made-up client id, because the dev site has no AdSense settings, and `scripts/ui/seed_ads.py` run first; the top of the spec says how, and if the image is older than the running container's packages, `docker commit` it and run that. **The age question** (`age.spec.ts`, `npm run age`; CLAUDE.md "Age declaration"): run `scripts/ui/seed_age.py` in the container before each run (an answer can't be taken back, so a run uses its accounts up). **The count of page requests** (`traffic.spec.ts`, `npm run traffic`; CLAUDE.md "Traffic"): run `scripts/ui/seed_traffic.py` in the container first (made-up numbers in the scratch `site_traffic`, the admin `ui_traffic_admin`; `--remove` takes every count out again). **QR sign-in** (`qr_login.spec.ts`, `npm run qr-login`; CLAUDE.md "QR sign-in"): run `scripts/ui/seed_qr_login.py` in the container before each run (the spec runs it again between tests, through `docker exec`, because one address spends the routes' per-minute limits long before the checks are done). **Two accounts in one browser** (`chat_session.spec.ts`, `npm run chat-session`; CLAUDE.md "Chat encryption"): the chat client keeps every device it holds in one index (`uqqus_chat_devices`), each with a crypto store locked with a key the site gives only to a signed-in page of that account, and its token only sealed. The spec holds that another account's device and store are never used on the chat page, a call window or a Space, and are KEPT for that account (signed out, no sealed token), while its waiting messages, sealed for that account alone, are never used and go when another account opens chat here (`token.js readWaiting`, the plan's rule); every Log out link (a feed, settings, the chat page itself, the phone menu) leaves no token the site gave anywhere in `localStorage` or `sessionStorage` (it reads them off the wire, `/api/chat/token`, and looks for each), no pre-key and no waiting messages, keeps the store, and also does so on a sign-in already gone and when the answer is lost; a tab left open stops at once and can't take the next account's session with it; another account opening chat beside a chat tab leaves one client; two tabs opening together end with one current device (a second may be made: either kept `removed`, or, when its page lost chat to the other while it asked, signed out with the site and never written to the index, `token.js` dropMinted); a store that isn't its device's own gets one new device and is kept as `broken` (made by overwriting the entry's recorded `ed`, so `openCryptoStore`'s identity check fires: the page's handling of the wasm's unpickling refusal of a wrong storage key is driven under node, `tests/test_chat_keeper.py`; the refusal itself is seen in the browser by spec 1); deleting an account clears its devices and stores and leaves another account's, and a wrong password clears nothing; signing back in through the real form takes up the same device with nothing typed and reads a message sent just before logging out and three sent to it while it was out (the chat plan's spec 4, first half); the store a log out leaves is locked: every object store of both its databases is read, the device's id is in no record and the account's only in `tracked_users`, which the crypto library keeps in clear with the people the account chats with (the privacy page says so); a device signed out meanwhile is replaced, and its store, which never unlocked and so holds nothing, is found empty and deleted by the page's sweep (`harvest.js` sweepEmpty); a chat tab whose device is signed out from another browser's Settings > Chat apps says why once, reloads at most once, starts again as a new device and, once unlocked, takes the old store's keys and deletes it: B writes in a new group while that tab's key uploads are blocked, and the new device reads the message, and the backup's count rises on the same version, only because the harvest imported the old store's key (the chat plan's spec 5); a message sent while an account has no chat device anywhere stays unreadable afterwards, harvest or not (spec 4's second half: recorded, the gap the plan leaves); a shared browser keeps one account's devices through another's turn, holds the ads for the other (the real `partials/ad_hold.html` expression, run in the page), gives the other no store key and hands the devices back (spec 6); a password change and Log out everywhere in another tab spare this sign-in's chat tab, which renews through the site with a fresh form key and no reload, and sign the account's other browser out, whose guild Chat tab frame (`single`, framed as `guild/chat.html` frames it) then says it was signed out, never a blank frame (spec 9); a refused sign-in leaves no pre-key while a real one keeps it for chat, in its own tab's storage, for that tab and its side panel, and chat in a new tab asks for the password once. Spec 8 (`ui_chat_d`, id 90708): a reset by email (the link made by the app in the container, no mail), then on the laptop the new device's password doesn't open the copy; "I don't have it: start over" leads to "Start over?", which promises nothing back (Start over can't finish on this chat server), and Cancel keeps the old store `removed` with `x`; then the recovery code unlocks it, the harvest brings in the message whose upload was blocked, the backup count rises and the old store goes. **Start over itself is never pressed**: on this chat server it fails half way for an account whose cross-signing is already set up (Synapse wants a sign-in stage the site's accounts don't have, so the key backup is deleted and the keys stay; 90707 was spent finding that), see CLAUDE.md "Chat encryption". The spec keeps `ui_chat_d`'s recovery code in `.auth/ui_chat_d.code` when its chat is first set up and unlocks with it whatever password an earlier run left the key locked with; lose that file and the account can't unlock again (give it a new id in the seed). Run `scripts/ui/seed_chat_session.py` in the container before each full run (`ui_chat_a`, `ui_chat_b`, `ui_chat_c`, `ui_chat_d`, `ui_chat_gone`, only in `ui_preview`; `ui_chat_b` follows the other three both ways, so the groups the harvest specs start are joined at once, and each run's groups are aged out of the 10 a day): it makes them, makes the deleted one again (the deletion test skips itself otherwise), puts every password back, resets the 5 Spaces a day and the sign-in limits, signs the accounts' chat devices out on the chat server (through the site's own queue) and clears their site chat devices, sign-outs and ended sign-ins. Each account is set up through the real form once; after that each test gets a session cookie of its own, signed by the app in the container (`docker exec`, `RUQQUS_CONTAINER`, default `ruqqus-ruqqus-1`), because a Log out ends its sign-in for good on the server and a saved cookie can't be put back after one. It also holds that a log out can't be undone by answers that were on their way. Run it with the chat server up and the dev site on `ui_preview` (its accounts are only there: a `docker-compose.override.yml` setting the `ruqqus` service's `DATABASE_URL` **and** `DATABASE_CONNECTION_POOL_URL` to `postgresql://postgres@postgres:5432/ui_preview`, removed after: the app connects to the second first, and docker-compose.yml sets it, so with only the first the site stays on the real dev database; the seeds check the one the app will use); repeated runs spend sign-ins, limited to 6 a minute (and a 429 heats the address), and every run adds devices to the accounts on the dev chat server. **Its renewal specs need tokens that end within minutes**: set `CHAT_TOKEN_REPORT_SECONDS=90` in the same override (never in `.env` or `docker-compose.yml`: dev and specs only), so every token is reported as lasting 90 s and the keeper renews it 30 to 60 s after it came; they fail at once, saying so, without it. They are the chat plan's specs 1 (its renewal parts: Log out everywhere from another browser puts a lost laptop's chat on the sign-in page at its next request, its last token dead for `whoami` and `/sync`, its store kept, and that store, opened in the page as the chat page opens it, refused with no key and with 32 zero bytes ("unpickling") and opened with its real key, which the member's signed-in phone fetches: `store_probe.js`, which the spec builds with the chat bundle's own esbuild and packages and puts in the page as a module; then the harvest: B writes in a new group (so no older device of C's ever had its key) while the laptop's key uploads are blocked (`room_keys/keys` aborted); the phone opens chat only after the laptop's device is gone and can't read that message; and when the laptop signs in again through the real form its new device, unlocked by the sign-in's pre-key with nothing typed, reads that message only because the harvest imported the old store's keys, the backup's count rises on the same backup version, the old store's databases and entry go within 30 s, and the ad hold is off), 2 (a chat tab and a call window answered by the other account renew for four minutes with no reload, one renewal of a kind at a time, 2 to 8 each, a message arriving after every chat renewal; then a side panel in a second tab takes chat over just after a renewal and starts with the keys only, no renewal), 3 (one `/sync` answered 401 on the token a page started with: one renewal, no reload, the same device, messages still coming; refused on a renewed token instead, the keeper's guard against the SDK's retry loop would reload) and 9 (whose renewal is now the real timed one, sent with the stale form key). Spec 2 takes about six minutes.

**Sign in anywhere, see your history** (`chat_history.spec.ts`, `npm run chat-history`; CLAUDE.md "Chat encryption"): run `scripts/ui/seed_chat_session.py` in the container first, every run (it puts the passwords back and signs the accounts' chat devices out). `ui_chat_h` writes in a 1:1 chat, a group and an encrypted channel for circles on one browser, `ui_chat_b` writes back, and a browser that never had chat, signed in through the form, reads every line with nothing typed, in a second tab too, each conversation opened from the list as a member opens it (a page load per conversation asked the site for 100 requests a minute and met a 429, which is how the chat page's "Loading…" for good was found); then a password changed through Settings > Security re-locks the chat key in that browser (the form sends `chat_key_blob`), that browser's chat carries on, the first browser's chat device is signed out, and a third browser signing in with the new password reads everything with nothing typed. The password is put back the same way; a run that stopped between the two leaves the key locked with the other one, and the next run's first browser starts the chat over (its earlier messages in the 1:1 room are then unreadable for good, so only the rooms a run makes are held to "nothing unreadable"). The helpers it shares with `chat_session.spec.ts` are `chat_helpers.ts`. Resets by email, Start over and the rescue are `chat_session.spec.ts`'s specs 8, 10 and 11.
